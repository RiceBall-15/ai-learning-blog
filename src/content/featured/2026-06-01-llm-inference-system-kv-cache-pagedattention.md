# LLM 推理系统深度解析：从 KV Cache 到 PagedAttention

## 前言

当我们在使用 ChatGPT、Claude 等大语言模型时，每一次流畅的对话背后，都是一套精心设计的推理系统在高效运转。LLM 的推理并非简单的"输入文本→输出文本"，而是一个涉及复杂内存管理、调度策略和硬件优化的系统工程。

本文将深入剖析 LLM 推理系统的核心技术，从最基础的 KV Cache 原理出发，逐步揭示 PagedAttention、连续批处理等关键技术的设计思想与实现细节。理解这些技术，对于构建高效、低成本的 AI 推理服务至关重要。

## 1. LLM 推理的基本原理

### 1.1 自回归生成的本质

LLM 的文本生成是一个**自回归**过程——每次生成一个 token，该 token 又成为下一次生成的输入：

```
输入: "Hello"
Step 1: "Hello" → 生成 "world"
Step 2: "Hello world" → 生成 "!"
Step 3: "Hello world!" → 生成 "<eos>"
```

在 Transformer 架构中，这个过程涉及两个关键阶段：

| 阶段 | 计算内容 | 计算特点 | 瓶颈 |
|------|----------|----------|------|
| Prefill（预填充） | 处理所有输入 token | 并行计算，计算密集 | 计算 bound |
| Decode（解码） | 逐个生成输出 token | 串行计算，内存密集 | 内存 bound |

### 1.2 KV Cache 的必要性

在 Transformer 的 Self-Attention 机制中，每个 token 的生成需要计算 Query (Q)、Key (K)、Value (V) 三个矩阵：

```python
# 不使用 KV Cache 的朴素实现
def naive_attention(input_ids, model):
    # 每次都重新计算所有 token 的 K 和 V
    for i in range(len(input_ids)):
        q, k, v = model.forward(input_ids[:i+1])  # 重复计算！
        output = attention(q, k, v)
    return output
```

这种方式的问题显而易见：**每次生成新 token 时，都会重新计算所有历史 token 的 K 和 V，造成大量冗余计算。**

KV Cache 的解决方案是：**缓存已计算的 K 和 V 矩阵，新 token 只需要计算自己的 K 和 V，然后与缓存的历史 K、V 进行注意力计算。**

```
┌─────────────────────────────────────────────────────────┐
│                    KV Cache 工作原理                     │
│                                                         │
│  Step 1: 处理输入 "Hello world"                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐               │
│  │ Q Hello │  │ K Hello │  │ V Hello │  ← 计算并缓存   │
│  └─────────┘  └─────────┘  └─────────┘               │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐               │
│  │ Q world │  │ K world │  │ V world │  ← 计算并缓存   │
│  └─────────┘  └─────────┘  └─────────┘               │
│                                                         │
│  Step 2: 生成 "!"                                      │
│  ┌─────────┐  ┌─────────────────────┐               │
│  │  Q !    │  │ K Cache [Hello,world]│  ← 复用缓存     │
│  └─────────┘  └─────────────────────┘               │
│               ┌─────────────────────┐               │
│               │ V Cache [Hello,world]│  ← 复用缓存     │
│               └─────────────────────┘               │
└─────────────────────────────────────────────────────────┘
```

### 1.3 KV Cache 的内存开销

KV Cache 带来了巨大的性能提升，但也引入了显著的内存开销。以 LLaMA-70B 为例：

| 参数 | 值 |
|------|-----|
| 模型参数量 | 70B |
| 层数 | 80 |
| 注意力头数 | 64 |
| 头维度 | 128 |
| 每 token KV Cache 大小 | 2 × 80 × 64 × 128 × 2 bytes = 2.5 MB |
| 4096 token 上下文 | 2.5 MB × 4096 ≈ 10 GB |

**对于 70B 模型，仅 KV Cache 就需要约 10GB 内存（4K 上下文），这还没算模型参数本身！**

## 2. 内存碎片化问题

### 2.1 传统实现的问题

传统的 KV Cache 实现采用**预分配连续内存**的方式：

```
内存分配示意（传统方式）
┌─────────────────────────────────────────────────────────┐
│ Request 1 (4096 tokens)                                 │
│ ███████████████████████████████████████████████████████ │
├─────────────────────────────────────────────────────────┤
│ Request 2 (1024 tokens)                                 │
│ ████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │
├─────────────────────────────────────────────────────────┤
│ Request 3 (2048 tokens)                                 │
│ ████████████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │
└─────────────────────────────────────────────────────────┘

░ = 浪费的内存（预留但未使用）
```

这种设计存在两个严重问题：

**内部碎片（Internal Fragmentation）**：为长序列预分配最大长度的内存，但短序列只使用一小部分，造成大量内存浪费。

**外部碎片（External Fragmentation）**：请求完成后释放的内存块大小不一，无法被新请求高效利用。

### 2.2 碎片化的影响

在实际生产环境中，内存碎片化会导致：

| 问题 | 影响 | 量化指标 |
|------|------|----------|
| GPU 利用率低 | 大量内存被浪费 | 利用率通常只有 30-50% |
| 并发数受限 | 可服务的请求数减少 | 并发能力下降 2-3 倍 |
| 吞吐量下降 | 需要更多 batch 来填满 GPU | 吞吐量损失 20-40% |

## 3. PagedAttention：革命性的解决方案

### 3.1 核心思想

PagedAttention（由 vLLM 提出）借鉴了操作系统中**虚拟内存和分页**的思想来管理 KV Cache：

```
┌─────────────────────────────────────────────────────────┐
│              PagedAttention 内存管理                     │
│                                                         │
│  逻辑视图（每个请求的 KV Cache）                         │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐               │
│  │ Block 0 │→│ Block 1 │→│ Block 2 │  (Request 1)    │
│  └─────────┘  └─────────┘  └─────────┘               │
│                                                         │
│  ┌─────────┐  ┌─────────┐                              │
│  │ Block 3 │→│ Block 4 │  (Request 2)                 │
│  └─────────┘  └─────────┘                              │
│                                                         │
│  物理内存（GPU 显存）                                    │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ Block 0 │  │ Block 1 │  │ Block 2 │  │ Block 3 │ │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘ │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐ │
│  │ Block 4 │  │ (free)  │  │ (free)  │  │ (free)  │ │
│  └─────────┘  └─────────┘  └─────────┘  └─────────┘ │
│                                                         │
│  Block Table（映射表）                                   │
│  ┌──────────────────┬──────────────────┐              │
│  │ Request 1: [0,1,2]│ Request 2: [3,4]│              │
│  └──────────────────┴──────────────────┘              │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键设计

**分块存储**：将 KV Cache 分成固定大小的 block（如 16 个 token），每个 block 独立存储。

**按需分配**：只分配实际需要的 block，不预留额外内存。

**非连续存储**：一个请求的 KV Cache 可以存储在物理上不连续的 block 中，通过 Block Table 进行映射。

**写时复制（Copy-on-Write）**：当多个请求共享相同的 prompt 时，可以共享同一份 KV Cache block，只在修改时才复制。

### 3.3 写时复制的威力

在实际应用中，多个请求经常共享相同的 system prompt：

```
┌─────────────────────────────────────────────────────────┐
│              写时复制 (Copy-on-Write)                    │
│                                                         │
│  Request 1: [system_prompt] + [user_query_1]           │
│  Request 2: [system_prompt] + [user_query_2]           │
│  Request 3: [system_prompt] + [user_query_3]           │
│                                                         │
│  内存布局：                                              │
│  ┌──────────────────┐                                  │
│  │ System Prompt    │ ← 三个请求共享                    │
│  │ Blocks [0,1,2]   │                                  │
│  └──────────────────┘                                  │
│         │          │          │                        │
│         ↓          ↓          ↓                        │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐              │
│  │ Query 1  │ │ Query 2  │ │ Query 3  │              │
│  │ Block [3]│ │ Block [4]│ │ Block [5]│              │
│  └──────────┘ └──────────┘ └──────────┘              │
│                                                         │
│  传统方式需要 3 × (3+1) = 12 blocks                    │
│  CoW 方式只需要 3 + 3 = 6 blocks（节省 50%）           │
└─────────────────────────────────────────────────────────┘
```

### 3.4 性能对比

| 指标 | 传统实现 | PagedAttention | 提升 |
|------|----------|----------------|------|
| 内存利用率 | 30-50% | 90%+ | 2-3x |
| 并发请求数 | 受限于预分配 | 按需分配 | 2-4x |
| 吞吐量 | 基准 | 提升 2-4 倍 | 2-4x |
| 首 token 延迟 | 基准 | 持平或略优 | - |

## 4. 连续批处理策略

### 4.1 静态批处理的局限

传统的静态批处理（Static Batching）将多个请求打包成一个 batch，一起处理：

```
静态批处理示意
┌─────────────────────────────────────────────────────────┐
│ Batch 1: [Req1, Req2, Req3, Req4]                      │
│                                                         │
│ Prefill 阶段: 处理所有输入                               │
│ ████████████████████████████████████████████            │
│                                                         │
│ Decode 阶段: 逐 token 生成                              │
│ Req1: ████████████████░░░░░░ (完成，但等待 Req4)        │
│ Req2: ██████████████████████ (完成，但等待 Req4)        │
│ Req3: ████████████████████████████ (完成)               │
│ Req4: ████████████████████████████████████ (最后一个)   │
│                                                         │
│ ░ = GPU 空闲但无法利用（等待整个 batch 完成）            │
└─────────────────────────────────────────────────────────┘
```

**问题**：当一个 batch 中的请求长度差异很大时，短请求必须等待长请求完成，造成 GPU 资源浪费。

### 4.2 连续批处理（Continuous Batching）

连续批处理（也称为 Iteration-level Scheduling）在每个 decode 迭代后动态调整 batch：

```
连续批处理示意
┌─────────────────────────────────────────────────────────┐
│ Iteration 1: [Req1, Req2, Req3, Req4]                  │
│ Iteration 2: [Req1, Req2, Req3, Req4]                  │
│ Iteration 3: [Req1, Req2, Req3, Req4]                  │
│ Iteration 4: [Req2, Req3, Req4, Req5]  ← Req1 完成，   │
│              Req5 加入                                  │
│ Iteration 5: [Req2, Req3, Req4, Req5]                  │
│ Iteration 6: [Req3, Req4, Req5, Req6]  ← Req2 完成，   │
│              Req6 加入                                  │
│ ...                                                    │
└─────────────────────────────────────────────────────────┘
```

**核心优势**：

1. **提高 GPU 利用率**：短请求完成后立即释放资源，新请求可以加入
2. **降低平均延迟**：请求不必等待整个 batch 完成
3. **提高吞吐量**：GPU 始终保持高利用率

### 4.3 调度策略

连续批处理的核心是调度器的设计：

```python
class ContinuousBatchScheduler:
    def __init__(self, max_batch_size, max_tokens):
        self.waiting_queue = []      # 等待调度的请求
        self.running_batch = []      # 正在处理的请求
        self.max_batch_size = max_batch_size
        self.max_tokens = max_tokens
    
    def schedule(self):
        """在每个 decode 迭代后调用"""
        # 1. 移除已完成的请求
        self.running_batch = [
            req for req in self.running_batch 
            if not req.is_finished()
        ]
        
        # 2. 尝试从等待队列添加新请求
        while (len(self.running_batch) < self.max_batch_size 
               and self.waiting_queue):
            next_req = self.waiting_queue[0]
            
            # 检查是否有足够的内存
            if self.can_admit(next_req):
                self.running_batch.append(next_req)
                self.waiting_queue.pop(0)
            else:
                break  # 内存不足，等待
        
        return self.running_batch
    
    def can_admit(self, request):
        """检查是否可以接纳新请求"""
        # 估算需要的 KV Cache blocks
        estimated_blocks = self.estimate_blocks(request)
        available_blocks = self.get_available_blocks()
        return estimated_blocks <= available_blocks
```

### 5.2 关键优化技术

**Flash Attention**：

Flash Attention 是一种高效的 Attention 计算实现，通过优化 GPU 内存访问模式来提升性能：

```
传统 Attention:
┌─────────────────────────────────────────────────────┐
│  Q, K, V → 计算 QK^T → Softmax → × V → Output     │
│            ↑ 需要存储完整的 N×N 注意力矩阵            │
│            内存复杂度: O(N²)                         │
└─────────────────────────────────────────────────────┘

Flash Attention:
┌─────────────────────────────────────────────────────┐
│  Q, K, V → 分块计算 → 在线 Softmax → 累加输出        │
│            ↑ 不需要存储完整注意力矩阵                  │
│            内存复杂度: O(N)                          │
│            IO 复杂度: O(N²d²/M)  (M 为 SRAM 大小)   │
└─────────────────────────────────────────────────────┘
```

**Tensor 并行与 Pipeline 并行**：

对于超大模型，需要将模型分布到多个 GPU 上：

```
Tensor 并行（同一层切分）:
┌──────────┐  ┌──────────┐
│ GPU 0    │  │ GPU 1    │
│ Layer[i] │  │ Layer[i] │
│ Head 0-3 │  │ Head 4-7 │
└──────────┘  └──────────┘

Pipeline 并行（不同层切分）:
┌──────────┐  ┌──────────┐
│ GPU 0    │  │ GPU 1    │
│ Layer 0- │→│ Layer 31- │
│ 30       │  │ 60       │
└──────────┘  └──────────┘
```

### 5.3 量化与压缩

在生产环境中，量化是降低推理成本的关键技术：

| 量化方案 | 精度 | 内存节省 | 性能影响 | 适用场景 |
|----------|------|----------|----------|----------|
| FP16 | 16-bit | 2x | 无 | 基线方案 |
| INT8 | 8-bit | 4x | 极小 | 通用场景 |
| INT4 (GPTQ) | 4-bit | 8x | 较小 | 成本敏感 |
| INT4 (AWQ) | 4-bit | 8x | 较小 | 更高质量 |
| GGUF (Q4_K_M) | 混合 | 6-8x | 中等 | 本地部署 |

## 7. 总结

LLM 推理系统的设计是一个复杂的系统工程问题。从本文的分析可以看出：

1. **KV Cache 是推理优化的基石**：通过缓存历史计算结果，避免重复计算，大幅提升推理效率

2. **PagedAttention 解决了内存管理难题**：借鉴操作系统虚拟内存的思想，实现了高效的 KV Cache 管理，内存利用率从 30-50% 提升到 90%+

3. **连续批处理是吞吐量提升的关键**：通过动态调度，GPU 利用率可以接近满载，吞吐量提升 2-4 倍

4. **量化是成本优化的利器**：INT4 量化可以在几乎无损的情况下将内存需求降低 4-8 倍

理解这些技术原理，对于构建高效、低成本的 AI 推理服务至关重要。无论是使用现有的推理引擎（如 vLLM、TensorRT-LLM），还是自研推理系统，这些基础知识都是不可或缺的。
