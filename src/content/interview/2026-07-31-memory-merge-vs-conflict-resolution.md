# 去重合并 vs 冲突裁决：记忆治理里最容易混为一谈的两件事

> 「长期记忆如何避免越记越乱？」这题几乎必问。大部分人会答「算相似度，相似就合并」。
>
> 这个答案只覆盖了**一半**，而且被追问一句就会露馅：
>
> > 「用户上周说在上海、这周说在杭州，相似度不高，你的合并逻辑管得住吗？」
>
> 记忆写入环节其实在做**两件完全不同的事**。分不清这两件事，是「看过方案」和「真做过治理」的分界线。

## 一、两个概念的本质区别

### 概念 A：去重合并（Consolidation / Dedup）

```text
场景：同一个事实被说了两次
  「我喜欢杭州」 + 「我很喜欢杭州这个城市」

判定依据：语义相似度高（sim ≥ mergeHigh）
动作    ：合并成一条（更新语义、保留版本链）
目的    ：防「同一件事存 N 遍」→ 存储膨胀 + 召回时重复刷屏
```

### 概念 B：冲突裁决（Conflict Resolution）

```text
场景：两个事实互相矛盾
  city = 上海（上周） vs city = 杭州（这周）

判定依据：同一槽位 / 同一属性，值不同
动作    ：按策略选 winner，loser 打 tombstone
目的    ：防「自相矛盾」→ 人格分裂式回答
```

### 一句话钉死区别

> **合并** = 「这俩是**一回事**，并成一条」
> **冲突** = 「这俩**互相矛盾**，选一个赢」

## 二、最关键的反直觉点：相似 ≠ 冲突

这是本篇的核心，也是面试里最能体现深度的一句。

**两条可以很相似但不冲突**：

```text
「喜欢杭州」 + 「喜欢杭州的西湖」
  → 相似度高，但不矛盾 → 该合并或共存，不需要裁决
```

**两条可以不相似但冲突**：

```text
「我吃素」 vs 「我爱吃牛排」
  → 向量相似度未必高（用词、主题都不同），但语义明显矛盾
  → 该裁决，但相似度检索可能根本不会把它们放在一起比较
```

**所以结论是**：

> **光靠向量相似度判不出冲突。相似度只回答「像不像」，不回答「矛不矛盾」。**

这也解释了为什么只做「相似就合并」的系统，一定会出现精神分裂式回答——它从来没有检测冲突的机制。

## 三、冲突怎么检测（面试深挖必答）

冲突检测按记忆类型分两条路，可靠性完全不同。

### 路径 ①：Profile 槽位冲突（结构化，主力，可靠）

```text
同一 slot 出现不同 value → 直接判定冲突
  例：slot=city，旧值=上海，新值=杭州 → 冲突，走裁决策略

优点：结构化，判定确定、可靠、可审计
```

### 路径 ②：自由文本冲突（语义矛盾，兜底，尽力）

```text
不能只看相似度，要判「语义是否矛盾」
  灰区相似度 → LLM 判定 { 同一条？ / 矛盾？ / 无关？ }
  例：「用户吃素」vs「用户爱吃牛排」→ LLM 判矛盾

优点：能抓自由文本矛盾
缺点：依赖 LLM，非 100% 可靠
```

### 由此得出一条重要设计启示

> 结构化槽位是冲突治理的**主力**（可靠），自由文本冲突靠 LLM **兜底**（尽力而为）。
>
> 所以设计上要**尽量把「可能冲突的偏好」结构化成 Profile 槽位**，而不是让它散落在自由文本里。

这句话是资深信号——它说明你不只是在「处理冲突」，而是在**通过数据建模减少不可靠的冲突判定**。

## 四、完整决策流水线（把两件事串成一张图）

```text
新记忆 newMem 到达：

  ┌─ 是 Profile 槽位类？
  │    ├─ 无同 slot 旧值 → 直接写入
  │    ├─ 有旧值且相同   → 忽略（已知，不重复写）
  │    └─ 有旧值且不同   → ★ 冲突裁决（选 winner，loser tombstone）
  │
  └─ 是 Episodic / Semantic？→ 向量 top1 相似度分带
       ├─ sim ≥ mergeHigh → ★ 去重合并（同一事实，并入版本链）
       ├─ 灰区            → LLM 判 { 同一条→合并 / 矛盾→冲突裁决 / 无关→新建 }
       └─ sim < mergeLow  → 新建
```

看这张图就清楚了：**合并走「相似度高」的路，冲突走「同槽位不同值」或「LLM 判矛盾」的路，灰区由 LLM 分流到三个出口**。

这才是写入环节的完整逻辑，不是「相似就合并」一句话。

## 五、冲突裁决策略：按风险分级，不一刀切

```text
slot = city，旧值 = 上海(observedAt=t1)，新值 = 杭州(observedAt=t2)

ConflictPolicy:
  LWW(observedAt)   最后写入获胜 → winner=杭州，loser=上海 → tombstone
  置信度加权         按抽取置信度选 winner
  双留历史           都保留，召回时按时间/置信度排序
  人工复核           高风险槽位不自动覆盖，转人工
```

**分级原则**：

- 普通偏好（city / food / tone）→ LWW 即可
- 高风险槽位（身份 / 支付 / 住址）→ **人工复核，不自动覆盖**

能说出「按风险分级」比只说「用 LWW」高一档——它体现了你知道自动化的边界在哪。

## 六、版本链：合并不是覆盖

合并要能回滚，所以不是覆盖旧值，而是**追加 + 指针**：

```text
MemoryRecord {
  id, slot, content, importance, observedAt,
  version, prevVersionId,                 // 链表指针
  status: ACTIVE | SUPERSEDED | TOMBSTONE
}

mergeIntoVersionChain(old, new):
  new.prevVersionId = old.id
  new.version       = old.version + 1
  old.status        = SUPERSEDED          // 旧版保留可回滚，但不参与召回
  new.status        = ACTIVE

  if chainLen(new) > maxChainLen:         // ★ 防爆炸
    compactOldVersions(new, keep=N)       // 保留最近 N 版 + 首版，中间归档

rollback(m):
  prev = findPrev(m, status=SUPERSEDED)
  prev.status = ACTIVE;  m.status = SUPERSEDED   // 一步回退
```

**为什么要防爆炸**：频繁改口的用户（比如反复调整偏好）会让版本链无限增长，拖慢查询、膨胀存储。必须有 `maxChainLen` 截断 + 定期 compaction。

## 七、灰区 LLM 裁决用强制 schema

```text
if mergeLow ≤ sim < mergeHigh:            // 灰区：拿不准是不是同一条
  verdict = llm.judge(new, top1, schema={ same_fact: bool, reason: str })
  if verdict.same_fact: mergeIntoVersionChain(top1, new)
  else:                 createNew(new)
```

两个细节：用**强制 schema**（布尔字段）避免解析自由文本；`reason` 落日志，供离线复盘阈值是否合理。

## 八、阈值怎么定（别拍脑袋）

```text
mergeHigh 太高 → 该合的不合，重复记忆堆积
mergeHigh 太低 → 不该合的合了，语义混淆（更严重）

定法：离线扫参
  用标注集（哪些该合、哪些该新建）扫阈值，看合并准确率
  灰区（两阈值之间）交给 LLM 仲裁，避免硬阈值误判
```

**一条重要的取舍原则**：

> **宁可漏合（多一条重复，后续 consolidation 再并），不可错合（跨语义污染，且难发现）。**

因为漏合的代价是「存储多一条 + 召回可能重复」，可恢复；错合的代价是「两个不同事实被并成一条乱码」，且用户投诉时你很难定位。

## 九、生产踩坑

### 坑 1：用户改口后回答精神分裂

**现象**：用户上周说喜欢上海，这周改口杭州，Agent 回答里两个都提。
**根因**：新旧偏好都还在，没有冲突裁决机制（只做了合并）。
**修复**：槽位冲突裁决（LWW）+ loser tombstone。
**验证**：改口后只召回新值。

### 坑 2：跨用户误合并（安全红线）

**现象**：A 用户召回到疑似 B 用户的记忆。
**根因**：合并时的相似检索**没带 scope 过滤**，把别的用户的相似记忆当成 top1 合并了。
**修复**：

```text
合并前的相似检索强制带 scope（租户 / 归属主体 id）
合并操作断言 old.scope == new.scope，违反即报警并阻断
跨 scope 永不合并
```

**验证**：合并审计日志无跨 scope 事件。

> 这是**安全红线**，比性能和准确率都优先。

### 坑 3：版本链爆炸

**现象**：某高频改口用户的记忆查询变慢、存储膨胀。
**排查**：该 slot 版本链长上千。
**修复**：`maxChainLen` 截断 + 定期 compaction。
**验证**：链长分布 P99 有界。

### 坑 4：合并依赖的向量是旧投影，会不会合错

这是个好问题，值得单独说清（也常被追问）：

**答案是不会合错，只会漏合。** 因为向量落后只影响「有没有找到该合的那条」——找不到就走新建分支，不会把不相关的合在一起。

防**合错**靠的是另外三道：scope 强过滤（跨用户绝不合）+ 灰区 LLM 裁决 + 版本链可回滚。

## 十、追问与反陷阱

| 追问 | 口径 |
|------|------|
| 合并和冲突是一回事吗？ | 不是。合并=同一事实去重（相似度高，并成一条）；冲突=矛盾裁决（同槽位不同值或语义矛盾，选 winner）。 |
| **怎么判两条是矛盾还是只是相似？** | Profile 槽位结构化直判（同 slot 不同 value = 冲突，可靠）；自由文本靠灰区 LLM 判「矛盾/同一/无关」。相似度判不了矛盾。 |
| 合并错了怎么办？ | 版本链可回滚 + 运营标错回写。 |
| 版本链会无限长吗？ | 会，所以有 `maxChainLen` 截断 + compaction。 |
| 阈值怎么定？ | 离线扫参 + 标注集，灰区交 LLM；原则是宁可漏合不可错合。 |
| 高风险槽位也自动覆盖吗？ | 不。身份/支付类转人工复核，按风险分级。 |

### 反陷阱

| 追问（陷阱） | 口径 |
|------|------|
| 「相似度高的就合并不就行了？」 | 「不行——相似度高只说明**是不是同一件事**（该合并），判不了**矛不矛盾**（该裁决）。『吃素』和『爱吃牛排』相似度未必高但矛盾；把冲突当合并处理，会把两个矛盾事实并成一条乱码。冲突要靠结构化槽位 + LLM 矛盾判定。」 |
| 「那你合并逻辑管得住用户改口吗？」 | 「改口不走合并，走**冲突裁决**——同一 slot 不同 value 直接判冲突，按 LWW 选新值、旧值 tombstone。合并和裁决是两条独立路径。」 |
| 「用向量最相似的那条来合并，会不会合错人？」 | 「会，而且这是安全红线。所以合并检索**强制带 scope**、合并操作断言同 scope，跨 scope 永不合并，并有审计。」 |

## 十一、一句话速记

> 记忆写入其实在做两件事：**合并（同一事实去重）**和**冲突裁决（矛盾选 winner）**。相似 ≠ 冲突——相似度只答「像不像」，判不了「矛不矛盾」，所以冲突要靠**结构化槽位直判**为主、LLM 判矛盾为辅；合并走版本链可回滚、防链爆炸，且跨用户永不合并。
