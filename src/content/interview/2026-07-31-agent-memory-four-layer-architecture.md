# 记忆到底分几层：四层记忆体系与层间流转

> 「你的 Agent 记忆怎么做的？分几层？」——这题只答「短期记忆和长期记忆」会显得停留在概念层。
>
> 真实的记忆系统是按**时效 + 用途**切的，四层各有自己的存储、TTL、召回方式和冲突特性。把这一层讲清，后面的冲突裁决和召回策略才有地基。

## 一、为什么必须分层

先说不分层的后果。朴素做法有三种，各有死穴：

- **把原始聊天全塞进 Prompt**：上下文爆炸、成本线性涨、首包变慢、模型「中间迷失」。不可持续。
- **只存会话级 Redis**：跨会话就忘了，且无结构、无检索、无治理。
- **什么都往向量库塞**：难事务（写一致性无法保证）、难治理删除（删了向量可能还有副本）、难冲突审计（用户改口了，新旧偏好都在，回答精神分裂）。

**分层的价值一句话**：

> 让「越记越乱」变得可控——**临时的不长期化，事件的可沉淀，偏好的可裁决**。

不分层就是一锅粥，过期的、矛盾的、噪声全混在一起，最后谁也说不清 Agent 为什么答错。

## 二、四层记忆

### ① 工作记忆 Working Memory（会话内，秒-分钟级）

```text
存哪：会话上下文 / 工作流变量（Redis 或进程内）
用途：当前 turn 的临时状态（用户刚说的、工具刚返回的）
TTL ：会话结束即释放 —— 不进长期库（太临时，不值得长期化）
召回：直接读，无需检索
```

类比：你现在脑子里正想着的东西。

### ② 情景记忆 Episodic Memory（跨会话，事件性）

```text
存哪：长期记忆库（关系库权威 + 向量投影）
用途：记住「发生过什么」——用户上周说要去杭州出差
TTL ：长期，按重要度衰减 + TTL
召回：语义向量召回（模糊匹配）
来源：从对话异步抽取
```

类比：「上周三我做了什么」。

### ③ 语义记忆 Semantic Memory（跨会话，事实性）

```text
存哪：与情景同库、不同 type
用途：记住「稳定的事实」——用户是程序员、对花生过敏
来源：情景记忆多次出现同类事实 → consolidation 沉淀为语义
召回：语义向量召回
```

类比：「我知道天是蓝的」——不记得是哪次学到的，但它是稳定知识。

**与情景的区别**（容易被追问）：情景是**某一次事件**，语义是**沉淀下来的稳定知识**。「上周说要去杭州」是情景；「这个人经常出差」是从多次情景沉淀出的语义。

### ④ 画像 / 偏好槽位 Profile（跨会话，结构化 KV）

```text
存哪：结构化槽位表（slot → value）
用途：结构化偏好 —— city=杭州, diet=素食, tone=正式
特点：槽位是「单值」或「有限多值」，天然会冲突（用户改口）
召回：按 slot 精确查 —— 不需要向量！
```

类比：一张个人信息表。

**这一层最特殊**：它是**唯一天然会冲突**的一层，也因此是冲突治理的主战场（详见下一篇）。而且它的召回是**KV 精确查**，毫秒级，不走向量——很多人误以为「记忆召回 = 向量检索」，这就是反例。

## 三、层间流转（分层不是四个孤岛）

```text
Working（会话内） ──── 异步抽取 ────▶ Episodic（事件）
Episodic（多次同类事件） ── consolidation ──▶ Semantic（稳定事实）
Episodic / Semantic 里的偏好信息 ── 结构化 ──▶ Profile 槽位
```

召回时按层取：

```text
Working             → 直接读会话变量
Episodic / Semantic → 走向量召回
Profile             → 按 slot 精确查（KV 查询，毫秒级）
```

## 四、四层对比总表（面试可直接画）

| 维度 | Working | Episodic | Semantic | Profile |
|------|---------|----------|----------|---------|
| 时效 | 会话内 | 长期衰减 | 长期稳定 | 长期，可改 |
| 存储 | Redis / 内存 | 关系库 + 向量 | 关系库 + 向量 | 关系库槽位表 |
| 召回方式 | 直接读 | 语义向量 | 语义向量 | **精确查 slot** |
| 冲突性 | 无 | 一般共存 | 偶有 | **天然冲突** |
| 治理重点 | TTL 释放 | 衰减 / 遗忘 | consolidation | 冲突裁决 |

## 五、为什么权威库是关系库，向量只是投影

这是记忆架构里最重要的一个取舍，几乎必被追问。

记忆系统同时有两个矛盾需求：

- **列表强一致**：管理台删了就必须没了；用户画像不能自相矛盾
- **语义检索**：模糊匹配「喜欢杭州」

而两类存储各有所长：

| | 关系库 | 向量库 |
|---|---|---|
| 事务 / 强一致 | 强 | 弱 |
| 治理删除 | 易 | 难（易残留） |
| 冲突审计 | 易 | 难 |
| 语义检索 | 弱 | 强 |

**结论**：让**关系库做权威**（唯一真相源，管事务、删除、冲突、列表），**向量做投影**（只负责检索，从权威派生）。这样强一致需求由权威库兜，检索需求由向量满足，**向量坏了能从权威重建**。

> **向量不能当权威**——因为它难事务、难治理删除、难冲突审计。这句话建议背下来。

### 双写怎么保证不丢：Outbox 投影

先写权威再写向量，中间崩了就丢投影。解法和工具调用的 Outbox 同源：

```text
// 同一个数据库事务
tx.begin()
  writeMemory(record)                             // 权威记忆
  insertOutbox(action=INDEX, memoryId, payload)   // 投影意图
tx.commit()

// worker 投影（至少一次）
worker.loop():
  for row in outbox.fetchUnsent():
    vectorStore.upsert(row.payload)               // 或 DELETE
    outbox.markSent(row)

// 对账 Job（修复不一致）
reconcile():
  orphans = vectorStore.findNotInAuthoritative()  // 向量有、权威无 → 删向量
  ghosts  = authoritative.findNotInVector()       // 权威有、向量无 → 补投影
  fix(orphans, ghosts)
```

**一致性口径（成熟表达）**：

> 关系库权威，向量是投影；链路至少一次投递；用业务幂等键和状态机防重；失败进 DLQ 补偿。**不吹 exactly-once，讲有效一次（幂等）**。

## 六、为什么不上 GraphRAG

被问「为什么不用知识图谱」时，要能讲清边界而不是跟风：

GraphRAG 适合**多跳知识图谱推理**（A 的主管是 B，B 在 C 部门）。但陪伴/助手类 Agent 的记忆冲突是**槽位问题**（city 槽位：上海 → 杭州），**不是多跳关系**。

上 GraphRAG 是**过度设计**——引入图谱建模、写入、运维三重复杂度，却解决错了问题。槽位冲突用冲突策略就够了。

**边界要诚实**：如果场景真是「大规模知识库多跳推理」，GraphRAG 才有用武之地。

## 七、生产踩坑

### 坑 1：「说过但下次忘了」

**排查链路**（按链路顺序逐段查，不要跳）：

1. **采集**是否到位？查采集 Outbox / 对账——可能根本没采到。
2. **抽取**是否成功？查抽取状态机——可能失败进了 DLQ。
3. **合并**是否误并？可能新记忆被错误合并进旧记忆（阈值太低）。
4. **召回**是否命中？可能提词没提对，或被 TTL / 衰减过滤掉了。

这条四段排查链本身就是加分项——说明你知道记忆是条流水线，不是一个黑盒。

### 坑 2：删了还能被想起

**根因**：只删了权威库，向量投影还在（孤儿向量）。
**修复**：删除走 tombstone + Outbox 投影 DELETE + 对账 Job 清孤儿。
**验证**：删除后抽检「不可再召回」+ 删除收敛指标。

### 坑 3：抽取把账单打爆

**根因**：抽取环节无并发门控，高峰期和在线对话抢模型配额。
**修复**：并发门控 + 闲时跑批。
**验证**：抽取成本占比可控，且不影响在线对话成功率。

### 坑 4：串用户数据（安全红线）

**现象**：A 用户的记忆被 B 用户召回到。
**根因**：召回请求没带 scope，或向量预过滤失效。
**修复**：请求**强制带 tenant/object scope**，双层过滤（向量预过滤 + 回表确认），**无 scope 直接拒绝**。
**为什么要双层**：不信任向量元数据，回表是第二道闸。

### 坑 5：幻觉记忆——记得用户没说过的事

**现象**：Agent 提到一件用户从没讲过的事。
**根因**：抽取时模型脑补，且无置信度门槛、无溯源。
**修复**：

```text
extractMemories(dialog):
  customId = hash(dialog.sessionId + dialog.turnRange)   // 幂等键：同段对话只抽一次
  if extractLog.exists(customId): return extractLog.get(customId)

  raw = llm.extract(dialog, schema=MemorySchema)
  out = []
  for m in raw:
    if m.confidence < minConfidence: continue            // ① 低置信丢弃，防幻觉
    m.provenance = {sessionId, turnRange, sourceQuote}   // ② 溯源：挂上原话
    out.add(m)

  extractLog.put(customId, out)
  return out
```

**验证**：抽取幻觉率（抽检 provenance 对不上原话的比例）。

> **这是记忆系统的头号隐患**：不是「忘」，是「**记错**」。绝不能假设 LLM 抽取 100% 准确。

## 八、追问与反陷阱

| 追问 | 口径 |
|------|------|
| 记忆分几层？ | 四层：Working / Episodic / Semantic / Profile，按时效与用途划分，各自存储、召回、冲突性不同，且可流转。 |
| 情景和语义记忆区别？ | 情景是「某一次事件」，语义是「多次沉淀出的稳定事实」。 |
| **为什么向量不能当权威？** | 难事务、难治理删除、难冲突审计、难列表强一致。向量是投影，可从权威重建。 |
| 双写如何不丢？ | 同库事务写权威 + 投影意图，worker 至少一次投递，对账 Job 修复。 |
| 和会话级 Redis 记忆差在哪？ | Redis 只管会话内；长期记忆跨会话、结构化、可检索、可治理删除。 |
| 为什么不上 GraphRAG？ | 冲突是槽位问题不是多跳推理，图谱是过度设计；真要多跳才用。 |
| 抽取会记错吗？ | 会，这是头号隐患。靠置信度阈值 + provenance 溯源 + 人工抽检。 |

### 反陷阱

| 追问（陷阱） | 口径 |
|------|------|
| 「记忆不就是把对话 embedding 存进向量库嘛」 | 「存进去只是最简单的一步。难在**抽取会幻觉**（要置信度+溯源）、**改口要冲突裁决**（策略+版本链）、**删除要收敛**（tombstone+对账）、**跨用户不能串**（scope 强过滤）。这些才是把记忆做成可运营数据产品的工程量。」 |
| 「怎么保证删干净了」 | 「删除是**收敛过程**不是一次操作：tombstone + 投影 DELETE + 对账 + 备份周期，用『删除后抽检不可召回』作验收指标。我从不承诺单步删干净。」 |
| 「分层是不是过度设计，一个向量库不够吗」 | 「不够。Profile 槽位召回是 KV 精确查、天然会冲突，用向量既慢又判不了冲突；Working 太临时不值得长期化。分层正是为了让各层用对的存储和对的治理手段。」 |

## 九、一句话速记

> 记忆分四层——**Working 不长期化、Episodic 记事件、Semantic 沉淀事实、Profile 管结构化偏好**；关系库做权威、向量只做投影（向量不能当权威）；写路径靠同库 Outbox + 对账保最终一致，口径上讲有效一次而不吹 exactly-once。
