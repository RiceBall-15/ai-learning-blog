# 工具调用为什么会重复发短信：副作用分级、幂等与 Outbox

> 上一篇讲了模型怎么选工具。这一篇讲**执行环节最容易出生产事故的地方**：工具调用失败了要不要重试？重试会不会让用户收到两条短信？
>
> 这题几乎是所有 Agent 岗位的必问题，因为它直接对应真实资损。

## 一、双花的根因：三重不确定性叠加

面试官问「工具调用失败重试会不会重复下单」，先别急着答「加幂等键」。**先把根因讲清楚**——为什么 Agent 场景比传统微服务更容易双花？

因为是**三重不确定性叠加**：

```text
① 编排重试：工作流节点超时，编排层重试整个节点
② 模型重问：模型这次给参数 A，重问可能给参数 B（LLM 有随机性！）
③ 网络抖动：请求发出去了，响应丢了 —— 不知道工具到底执行没
```

第 ② 条是 Agent 特有的。传统微服务重试，参数是确定的；Agent 里**重试往往意味着重新问模型**，而模型可能给出不同参数——于是「同一个业务意图」变成了「两个不同的调用」，连幂等键都对不上。

这是本篇最核心的洞察，也是 Outbox 方案的出发点。

## 二、副作用分级：不是所有工具值得同等对待

先分级，再决定重试策略。一刀切「全部重试」或「全部不重试」都是错的。

| 级别 | 类型 | 例子 | 重试策略 |
|------|------|------|----------|
| **R0** | 只读 | 检索、查询、查天气 | 可自由重试，无害 |
| **R1** | 幂等写 | upsert by key | 带幂等键重试 |
| **R2** | 非幂等写 | 发短信、扣次数、下单、退款 | **禁止盲重试**，落 Outbox 投递 |
| **R3** | 流式生成 | LLM token 流 | 优先取消，不盲目整段重放 |

```text
switch tool.sideEffectLevel:
  case R0: return callWithRetry(tool, args)
  case R1: return callWithIdempotencyKey(tool, args)
  case R2: return callViaOutbox(tool, args)
  case R3: return callStreamWithCancel(tool, args)
```

**面试价值**：能说出分级，说明你想过「重试的代价」，而不是无脑加 retry。

## 三、幂等键：为什么必须双层强制

```text
// 编排侧生成（稳定，不依赖模型）
Idempotency-Key = hash(runId, nodeId, loopIndex, toolName)

// 工具侧强制（对所有调用方生效）
服务端去重表：收到带 key 的请求 → 命中则返回上次结果，不重复执行
```

**为什么必须双层**（这是深挖点）：

- **只有编排侧不够**：工具可能被别的系统调用（另一个 Agent、运营后台、定时任务）。编排侧的 key 只能约束自己。
- **只有服务端不够**：如果编排层不带 key，服务端无从去重。

所以：**编排侧挡「自己的天真重试」，服务端挡「所有调用方与重启场景」**。

注意 key 的构成刻意**不含模型给的参数**——用 `runId + nodeId + loopIndex + toolName`，保证同一个业务意图在重试时 key 稳定。如果把参数 hash 进去，模型重问给了不同参数，key 就变了，去重失效。这正是第一节第 ② 条的直接对策。

## 四、Outbox：重放意图，而非重问模型

对 R2 非幂等工具，盲目重试不安全（可能重复执行），但又**不能不重试**（网络可能真丢了）。

解法是 **Outbox 模式**：

```text
// 同一个数据库事务
tx.begin()
  updateBusinessState(...)                        // 业务状态变更
  insertOutbox(intent = {tool, args, idemKey})    // 「要调用工具」的意图落库
tx.commit()

// relay 组件（至少一次投递）
relay.loop():
  for intent in outbox.fetchUnsent():
    try:
      result = tool.call(intent)                  // 带幂等键
      outbox.markSent(intent)
    catch e:
      retry(intent)     // ★ 重试的是「已落库的固定意图」，不是重新问模型

// 工具侧去重
tool.call(intent):
  if dedupTable.has(intent.idemKey):
    return dedupTable.get(intent.idemKey)         // 命中返回上次结果
  result = execute(intent)
  dedupTable.put(intent.idemKey, result)
  return result
```

### 关键差异（这是这一题的得分点）

| 维度 | 直接重试 | Outbox |
|------|----------|--------|
| 重试的是什么 | 重新问模型要参数 + 重新调用 | **已落库的固定意图** |
| 参数稳定性 | 模型每次可能给不同参数 | 意图固化 |
| 双花风险 | 高 | 低（服务端去重） |
| 一致性 | 难保证 | 意图与业务状态**同库事务** |

一句话：**意图固化了，重试就安全了。**

### 什么时候不该上 Outbox

Outbox 有成本（多一张表、多一个 relay、多一层延迟）。**只读和幂等工具直接重试即可**，别过度设计。按副作用分级决定，这本身就是权衡意识的体现。

## 五、人机协同（HIL）：高危工具的人工闸门

高风险工具（退款、删除数据、对外发布）不应该让模型自己拍板。做法是在 DAG 里插一个**可持久化的暂停态**：

```text
parkForHumanApproval(tool, args):
  // 暂停态必须持久化（扛服务重启）
  workflow.park(runId, nodeId, {tool, args, status = WAITING_HUMAN})
  return                                           // 节点挂起，释放线程

onHumanApprove(runId, nodeId):
  workflow.resume(runId, nodeId, decision = APPROVE)   // 继续执行工具

onHumanReject(runId, nodeId):
  workflow.resume(runId, nodeId, decision = REJECT)    // 走补偿或降级话术分支
```

两个设计要点：

1. **必须异步 parked，不能同步等待**。同步等待会占着线程池，而人工审批可能等几小时。这和 DAG「节点不在池内阻塞」的原则一致（系列第一篇）。
2. **parked 态必须持久化到 DB**。否则等待期间服务重启，工作流就丢了——审批回来发现没了。

## 六、为什么用 MCP 标准协议

工具接入碎片化的解法是标准化。MCP 定义「发现工具 → 调用工具 → 返回结果」的标准协议，工具方实现 Server，调用方用 Client。

**长期摊销的账**：N 个工具 × M 个 Agent

- 私有 SDK：**N × M** 套适配
- MCP：**N + M** 套

工具越多、Agent 越多，MCP 越划算。遗留系统（OpenAPI/HTTP）走适配器包成 MCP 节点，不必为老系统单独维护路径。

**边界要诚实**：工具极少且固定时，私有 SDK 更轻；MCP 的摊销优势只在规模上来后才显现。协议不成熟的风险用**适配层 + 审计 + 幂等**兜底，不是裸用。

## 七、生产踩坑

### 坑 1：超时重试导致重复短信 / 重复工单

**现象**：用户偶发收到两条相同短信，或工单被创建两次。
**排查**：Trace 里同一 `(runId, nodeId, toolName)` 有多次工具调用；确认是非幂等工具被盲重试。
**根因**：无 Outbox、无幂等键。
**修复**：R2 工具走 Outbox + 服务端去重表 + 幂等键。
**验证**：压测「工具超时 + 编排重试」场景，断言工具只执行一次。

### 坑 2：模型被诱导调用高危工具

**现象**：模型被 Prompt 注入骗去调了删除类工具。
**根因**：无白名单、无 HIL，模型选啥调啥。
**修复**：高危工具白名单 + HIL 人工确认 + 审计日志 + 参数 schema 校验 + 最小权限。
**验证**：注入用例集回归。

### 坑 3：工具很慢拖垮对话

**现象**：某工具 P99 很高，接入后对话首包被拖长。
**排查**：工具在主路径同步调用，且无超时、无软失败。
**修复**：工具放并行支路 + `SOFT_FAIL`（失败给降级话术继续），或改异步回调模式（先回「正在处理」，完成后回调）。
**验证**：首包回到预算内。

### 坑 4：MCP 连接泄漏

**现象**：长时间运行后连接数持续上涨，最终打满。
**排查**：Client 没有显式关闭。
**修复**：Client 池化复用 + 显式 close（try-finally）+ 活跃连接数告警。

### 坑 5：HIL 等待时服务重启，工作流丢失

**现象**：人工审批等了几小时，期间服务重启，审批回来发现工作流没了。
**排查**：parked 态只在内存。
**修复**：parked 态持久化到 DB，重启后恢复等待态。
**验证**：HIL 等待期间 kill 进程，重启后 resume 仍能继续。

## 八、追问与反陷阱

| 追问 | 口径 |
|------|------|
| 幂等键谁生成？ | 编排侧稳定生成 `hash(runId, nodeId, loopIndex, tool)`，工具侧强制校验。双层才可靠。 |
| 为什么 key 不含模型给的参数？ | 因为模型重问可能给不同参数，key 会变、去重失效。要用「业务意图」的稳定标识。 |
| Outbox 和直接重试差在哪？ | 意图与状态同库提交，重放的是**意图**不是重问模型；模型重问会给不同参数，所以直接重试本质不安全。 |
| 如何防 Prompt 注入骗工具？ | 参数 schema 校验 + 最小权限 + 白名单 + HIL + 审计。**执行在编排层，所以治理点在编排层**。 |
| 所有工具都上 Outbox 吗？ | 不。按副作用分级：只读/幂等直接重试，只有非幂等才值得 Outbox 的成本。 |
| MCP 不成熟为什么还用？ | 长期摊销（N×M → N+M）+ 适配层兜底；工具少时私有 SDK 更轻，规模上来才划算。 |

### 反陷阱

| 追问（陷阱） | 口径 |
|------|------|
| 「加个重试不就完了？」 | 「重试对只读无害，对非幂等是资损。而且 Agent 里重试常意味着**重新问模型**，参数可能变、连幂等键都对不上——所以要么带稳定 key 重试，要么走 Outbox 重放固定意图。」 |
| 「幂等键在客户端做就行了吧」 | 「不够。工具还会被别的系统调用、也会遇到重启场景，所以服务端必须有去重表强制。编排侧挡自己的重试，服务端挡所有调用方。」 |
| 「HIL 就是加个确认弹窗吧」 | 「难点不在弹窗，在**暂停态要持久化且不占线程**。同步等待会占满线程池，内存态会在重启后丢工作流——所以做成异步 parked + DB 持久化 + resume 回调。」 |

## 九、一句话速记

> Agent 工具可靠性的核心是「**按副作用分级，重放意图而非重问模型**」：只读随便重试，非幂等绝不盲重试——用「业务意图 + 稳定幂等键」同库落 Outbox，靠服务端去重实现有效一次；高危工具再加持久化的人工闸门。
