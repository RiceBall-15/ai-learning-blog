# 怎么证明你的改动真的有效：评测闭环与 ship gate

> Agent 迭代的常态是「改了 Prompt / 调了融合参数 / 换了召回策略」，每次改动都会让人产生「感觉变好了」的错觉——因为 LLM 输出有随机性，你问几次都觉得不错，但那可能只是采样方差。
>
> **资浅靠感觉迭代，资深靠可证伪闭环迭代。** 这是这一题的全部。

## 一、为什么这题是稀缺项

行业里一个反差很能说明问题：**有可观测的团队远多于有真评测的团队**。

「能看指标」是普遍的，但「能用固定评测集量化证明改动有效且无回退」是稀缺的。所以评测能力在面试里是区分「会调 Prompt」和「能负责 Agent 质量」的硬分界。

三种朴素做法各有死穴：

- **只有线上指标**：线上指标是「事后全局聚合」。改了召回融合后成功率没掉，但你不知道是「真没影响」还是「被别的高频路径淹没了」。**无法归因到具体改动。**
- **人工抽几条看效果**：样本小、有选择偏差（你倾向抽好的）、不可复现（下次跑模型给不同答案）。**无法回归。**
- **每次改动重跑线上对比**：线上流量有噪声、有周期性，AB 不预注册指标就会被 p-hacking（事后挑一个看着好的指标说事）。

所以要建的是：**在线分层归因 + 离线固定回归 + 标注飞轮**的可证伪闭环。

## 二、第一层：在线指标分层归因

单一「成功率」不够——掉了你不知道是网关限流、节点超时、召回降级还是工具失败。所以要**按链路分层**：

```text
网关层   限流拒绝率 / 熔断触发率 / 降级触发率 / 取消率
节点层   各节点 success / timeout / cancelled 分列
召回层   degraded 率 / 命中率 / 负迁移率
工具层   成功率 / 双花率 / schema 校验拒绝率 / HIL 通过率
对话层   首包 TTFT / 整段耗时 / token 消耗 / 流式中断率
```

两个关键治理点：

- **CANCELLED 与 FAILED 分列** → 取消不计入失败分母（否则告警噪声 + 成功率失真）
- **标签语义治理** → 模型名 / 产品线不要混用，否则指标不可比

### 再进一步：自动分层归因

分层是前提，但人肉翻四层仍慢。把「总下降」按失败原因分解，贡献最大的排最前：

```text
attributeDrop(metric=success_rate, t_now, t_base):
  drop = metric(t_base) - metric(t_now)
  contrib = {}
  for layer in [网关, 节点, 召回, 工具]:
    for cause in layer.failureCauses:
      contrib[cause] = (cause.fails(t_now) - cause.fails(t_base)) / total
  return sortDesc(contrib)

// 输出示例：[召回节点timeout:+0.21%, dense通道延迟:+0.19%, 网关限流:+0.01%]
// → 一眼指向召回层，MTTR 从「翻仪表盘」压到「看归因榜」
```

## 三、第二层：Trace 贯穿与脱敏快照

聚合指标不够，badcase 要能**复现**：

```text
一次对话的 Trace 结构：
  TraceId（贯穿编排 ↔ 记忆 ↔ 工具）
    ├─ Span: DAG调度   {runId, 画布版本, 节点执行序}
    ├─ Span: 召回节点  {query, topK结果, degraded?, 耗时}
    ├─ Span: 模型调用  {model, prompt摘要(脱敏), tokens, TTFT}
    ├─ Span: 工具调用  {toolName, args(脱敏), result, 耗时, idemKey}
    └─ Span: 记忆写回  {抽取结果, 合并决策, 冲突策略}

脱敏快照：存输入的脱敏版本（去 PII），用于复现；不存原始明文 → 隐私合规
```

**Trace 不只是日志，是 badcase 复现的「时间机器」。** 因为 LLM 有随机性，重跑不可复现，只能靠当时留下的完整上下文回放。

## 四、第三层：离线评测集与 ship gate（核心）

在线指标告诉你「现在好不好」，**离线回归告诉你「改了之后有没有变好/变坏」**。

```text
评测集构造：
  {query, 期望召回的记忆ID列表, 期望不召回的记忆ID列表}
  来源：运营标注的 BadCase + 人工构造的边界 case + 历史会话抽样
  ★ 隔离铁律：训练集与评测集按用户/会话隔离（防泄漏）

评测指标：
  Recall@K / Precision@K / MRR / nDCG
  错误合并率     不该合并的被合并了
  过期误召回率   tombstone / 过期记忆被召回
```

### ship gate 判定

```text
shipGate(change):
  evalSet  = loadVersionedEvalSet()          // ★ 版本化固定集
  scores   = { m: run(evalSet, change.candidate) for m in metrics }
  baseline = loadBaselineScores()
  regress  = [m for m in coreSLO if scores[m] < baseline[m] - tolerance[m]]

  if regress:
    return BLOCK(reason=regress)              // 任一核心 SLO 回退 → 阻断发版
  if anyNonCoreRegression(scores, baseline):
    warn()                                    // 非核心回退 → 告警不阻断，人工研判

  saveScores(change.version, scores)           // 可追溯到「集版本 × 改动版本」
  return PASS
```

**回归铁律**：每次改融合参数 / 衰减系数 / 提词 / 降级策略，**必须**跑固定集；核心指标回退则阻断发版。

一句话概括 ship gate：**versioned eval set + numerical score + regression alarm**。

## 五、第四层：LLM-as-judge 的严谨化

人工标注贵且慢，LLM-as-judge 可作规模化辅助——但它有**系统性偏见**，不是随机噪声：

```text
三类判官偏见：
  长度偏好   偏好更长的答案（即使更长并不更好）
  位置偏好   A/B 对比时偏向出现在特定位置的答案
  自我偏好   偏好与自己风格相似的答案

四招缓解：
  位置随机化      A/B 交换位置再判，只采正反一致的票
  多判官投票      多个模型 / 多个 prompt 判，取多数
  关键集人工校准  人工定标的 golden set 定期校准判官
  判官 prompt 迭代
```

```text
judgePair(a, b):
  votes = []
  for judge in judgePanel:                   // 多判官
    for (x, y) in [(a, b), (b, a)]:          // ★ 位置随机化：正反各判一次
      v = judge.compare(x, y)
      votes.add(normalize(v, swapped=(x==b)))
  consistent = [v for v in votes if positionConsistent(v)]   // 抵消位置偏好
  return majority(consistent) if consistent else TIE_NEEDS_HUMAN
```

**关键判断**：偏见是**系统性偏差**而非偶尔判错——它会持续偏向某类答案。所以 judge **只能辅助不能替代**人工：LLM 筛低分 → 人工复核；golden set 必须人工定标。

**口径红线**：不吹「准确率提升 X%」。没有大规模标注集前只报趋势 + 人工小样本，并标明来源。

## 六、第五层：标注飞轮

```text
在线发现问题 → 运营标注 BadCase / 错误记忆
  → 反哺评测集 + 冲突策略 + 抽取 Prompt
  → 离线回归验证 → 影子流量 / 小流量 → 全量

具体反哺路径：
  错误合并的 case   → 调合并阈值
  过期误召回的 case → 调衰减 / TTL
```

飞轮转起来，评测集越来越大、越来越准。而且**评测闭环的成本大头不在「跑评测」（固定集可控），而在「标注人力」**——飞轮转得越快越省人力。

## 七、第六层：Agent 特有指标

Agent 不只是「答案对不对」：

```text
工具双花率      同一意图被工具执行多次
记忆负迁移率    有召回比无召回满意度更差的比例（消融测）
Agent 空转轮数  反复调工具 / 自问自答不收敛
平均工具调用数  超阈值告警 = 可能空转
平均对话轮数    超阈值告警 = 可能没解决
```

这些指标比「答案对不对」更能暴露 Agent 特有的系统性问题——**答案对但过程差**的隐性失败。

## 八、负迁移必须用配对检验

```text
ablation(evalQueries):
  diffs = []
  for q in evalQueries:
    diffs.add(judge(answer(q, recall=ON)) - judge(answer(q, recall=OFF)))
    // ★ 同一 query 的配对差值，消掉 query 难度差异

  if mean(diffs) <= 0 or not significant(diffs): flag(NEGATIVE_TRANSFER)
  negTransferRate = count(d < 0 for d in diffs) / len(diffs)
```

**为什么不能比两组独立均值**：均值会被**少数大涨掩盖多数小跌**。要看配对差值的**分布**和负迁移率。

## 九、AB 实验纪律：预注册防 p-hacking

```text
预注册指标    实验前写明要看哪些指标、什么算「显著」
预注册样本量  提前算好需要多少样本才有统计效力
影子流量      先跑影子对比重叠率和人工分，再切小流量
消融          recall on/off 对比最终满意度（不只看召回命中率）
禁止          事后挑一个看着好的指标说「成功了」
```

不预注册 = p-hacking 温床，AB 结论不可信、团队之间必然扯皮。

## 十、生产踩坑

### 坑 1：成功率掉了但不知道哪层

**排查**：分层指标 → 网关正常，召回节点 timeout 上升，召回层 degraded 率上升 → 定位召回层；再拿一条 timeout 的 TraceId 回放 → dense 通道延迟飙升 → 根因是向量库某分片热点。
**修复**：回表走读副本 + 热点缓存。
**教训**：单一「成功率」无法归因，**分层是前提**。

### 坑 2：优化召回却伤了体验（负迁移）

**现象**：Recall@K 上升了，但用户满意度下降。
**排查**：只看命中率看不出来——命中率只证明「召到了」，不证明「有用」。做消融发现 recall on 的满意度 < off。
**修复**：提高相似度阈值 + 运营标错回写降权。
**教训**：**单指标会骗人**，要消融 + 同时看首包与满意度。

### 坑 3：删了记忆但用户仍投诉「还记得」

**根因**：只删了权威库，向量投影残留。
**修复**：tombstone + 投影 DELETE + 对账 Job。
**教训**：删除要有**验收指标**（删除后仍可召回的比例 → 0），不能「删了就完」。

### 坑 4：BadCase 无法复现

**根因**：LLM 有随机性，重跑给不同答案。
**修复**：靠 TraceId + 脱敏快照回放当时的完整上下文。

### 坑 5：AB 实验结论扯皮

**根因**：没有预注册指标和样本量，事后各挑各的。
**修复**：预注册 + 消融，事后不许加指标说事。

### 坑 6：Agent 空转多轮没人发现

**现象**：某类 query 下 Agent 反复调工具、5-6 轮才收敛，成本飙升但**成功率看着没问题**（最终答案是对的）。
**排查**：只看「答案对不对」看不出空转。加平均工具调用数 / 平均轮数指标，超阈值告警。
**修复**：工具超时走软失败降级 + 轮数上限早停。
**教训**：Agent 特有指标能暴露「答案对但过程差」的隐性失败。

### 坑 7：指标基数爆炸打爆时序库

**根因**：把高基数维度（如 userId）当成指标标签，笛卡尔积到百万级。
**修复**：高基数维度只进日志 / Trace，标签只留低基数聚合维度 + 预聚合。
**验证**：活跃时间序列数有界。

### 坑 8：评测集过拟合

**现象**：离线 Recall@K 一路涨，线上满意度不动。
**根因**：连续几十次调参都用同一评测集，参数被拟合到这个集。
**修复**：留出 **holdout 集**（只在发版前跑一次，不参与调参）+ 评测集定期轮换扩充 + 线上影子交叉验证。
**验证**：离线涨幅与线上影子涨幅的相关性。

### 坑 9：采样把 badcase 采丢

**现象**：用户报的 badcase 在 Trace 里找不到。
**根因**：一刀切采样率，低频 badcase 没被采到。
**修复**：**分层采样**——错误 / 降级 / 高延迟 / 低分请求 100% 采，正常流量才低采样。

### 坑 10：judge 升级后历史分数不可比

**根因**：judge 模型换了、无基准。
**修复**：judge 版本化 + 换 judge 时用 golden set 重新定标并对齐历史 + 每条分标注 judge 版本。

## 十一、面试四类题型都能用评测闭环应答

| 题型 | 典型问法 | 怎么答 |
|------|----------|--------|
| Agent 设计 case | 「Agent 4% 概率退错款怎么办」 | **eval 设计 + fallback + 度量计划**，不是换模型 |
| Live build 系统设计 | 边画状态图边讲 | 顺手讲清可观测埋点位置 |
| 生产失败复盘 | 「讲一个失败的 Agent」 | 用 eval 抓到的 silent failure，比背框架名字强 |
| 成本延迟推理 | token 预算 / p99 / 质量-成本-延迟三角 | 评测不只看质量，同时看成本与延迟 |

**最关键的一个陷阱**：被问「Agent 4% 概率退错款怎么办」，直接答「换更贵的模型」是错的。正确答案是「**先建 eval 量化这 4% 是什么场景 → 加 fallback 兜底 → 设度量计划监控是否收敛**」。

> **评测设计先于模型升级。**

## 十二、追问与反陷阱

| 追问 | 陷阱 | 口径 |
|------|------|------|
| 只有线上指标够不够？ | 以为够 | 「不够。线上是全局聚合，无法归因到具体改动、无法防负迁移。要离线固定回归集隔离变量。」 |
| LLM-as-judge 可信吗？ | 全信或全否 | 「可作辅助不可替代。三类偏见（长度/位置/自我）是**系统性偏差**不是随机噪声，要位置随机化 + 多判官 + golden set 人工校准。」 |
| **如何证明你改的有用？** | 只拿一个指标 | 「单指标会骗人（召回率升但满意度降 = 负迁移）。用**消融配对检验 + 固定回归集 + 核心在线 SLO 不回退**三重证据，且预注册指标避免事后挑数。」 |
| 「准确率提升了多少」 | 逼你报假数 | 「我不报准确率。没有大规模标注集前只报**趋势 + 人工小样本**，报数会标来源和置信区间，不靠印象。」 |
| 评测集会过拟合吗？ | 把评测集当万能标尺 | 「会。holdout 集只在发版前跑一次、不参与调参 + 定期轮换扩充 + 线上影子交叉验证。离线集必要不充分，最终裁判是线上。」 |
| 采样了 Trace，badcase 没采到？ | 以为采样均匀 | 「分层采样——错误/降级/高延迟/低分 100% 采（badcase 本就是异常，必采），正常流量才低采样。」 |
| judge 换模型历史分还能比吗？ | 当固定基准 | 「不能直接比。judge 要版本化，换 judge 用 golden set 重新定标对齐历史。」 |
| 「加个 userId 标签方便下钻」 | 忽视基数爆炸 | 「userId 是高基数维度，进标签会让时间序列数膨胀到百万级、打爆时序库。高基数下钻用 Trace，标签只留低基数聚合维度。」 |

## 十三、一句话速记

> Agent 迭代的资深分水岭是**用可证伪闭环取代「感觉变好」**：在线分层指标定位到层、Trace 脱敏快照复现 badcase、离线**版本化固定集做 ship gate**（核心 SLO 不回退则阻断发版）、LLM-as-judge 辅助但不替代人工、负迁移用**配对检验看分布不看均值**。而且面对「Agent 出错怎么办」，答案永远是**先 eval 量化再谈换模型**。
