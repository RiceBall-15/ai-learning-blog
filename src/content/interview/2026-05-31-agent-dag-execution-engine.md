# Agent DAG执行引擎：从理论到生产级工作流编排的完整指南

> **定位**：本文是面试方向10（高效任务调度）的深度补充，从零到生产级覆盖DAG执行引擎的完整知识体系。如果你已经在阅读任务调度文章，这篇将带你深入到DAG引擎的设计内核。

## §1 为什么Agent需要DAG执行引擎

### 1.1 从线性调用到有向无环图的演进

最原始的Agent实现是一条直线：思考 → 调用工具 → 再思考 → 输出结果。这个模型在简单场景下能跑通，但一旦进入真实业务——多源数据采集、多步推理、多Agent协作——线性模型立刻撞墙。

让我们看一个真实的演化过程：

**阶段一：线性Chain**
```
Query → LLM思考 → 搜索引擎 → LLM总结 → 输出
```
问题：LLM调用期间，搜索引擎空闲。如果有10个搜索源，总延迟 = 10 × 单次搜索延迟。

**阶段二：简单的并行/串行混合**
```
Query → LLM思考 → [搜索A | 搜索B | 搜索C] → LLM总结 → 输出
```
能并行了，但当搜索B的结果影响搜索D的查询策略时，简单的并行扇出模型就失效了。

**阶段三：DAG**
```
         ┌─→ 搜索A ──┐
Query → LLM ──────────→ 融合器 → LLM总结 → 输出
         └─→ 搜索B ──┘
```
DAG的精髓在于：**节点之间的依赖关系被显式建模，引擎自动推导出执行顺序和并行机会。**

### 1.2 DAG的三大核心优势

| 优势 | 说明 | 对比线性Chain |
|------|------|---------------|
| **自动并行** | 无依赖的节点自动并行执行 | 线性串行，延迟线性累加 |
| **依赖显式** | 数据流和执行顺序一目了然 | 依赖隐藏在代码调用栈里 |
| **可恢复** | 单个节点失败不影响已完成的节点 | 线性链从头重试，资源浪费 |

### 1.3 为什么不是通用状态机？

DAG不是万能的。它故意去掉了环（Cycle），这意味着它不支持循环推理。但在Agent场景中，大部分工作流是**确定性依赖**的——A的输出喂给B，B的输出喂给C，不太会出现"回到A重新来"的情况。这种"无环"的约束恰恰是DAG的力量：它让引擎能**静态分析**整个执行计划，在运行前就知道关键路径、最大并行度和资源峰值。

## §2 DAG核心概念

### 2.1 五个核心要素

```
┌─────────────────────────────────────────────────┐
│                 DAG 核心概念                      │
│                                                  │
│  ① Node（节点）     执行单元，封装一个任务         │
│  ② Edge（边）       节点间的数据/控制依赖          │
│  ③ Topology（拓扑）  节点和边构成的整体结构          │
│  ④ Topological Sort 拓扑排序，决定执行顺序          │
│  ⑤ Parallelism     并行度控制，约束同时执行的节点数  │
└─────────────────────────────────────────────────┘
```

**Node（节点）**：DAG中的最小执行单元。在Agent场景中，一个节点可能是一次LLM调用、一次工具执行、一次数据转换，甚至是一个子工作流。

**Edge（边）**：定义节点间的依赖关系。边携带数据——上游节点的输出沿边传递给下游节点。边分为两类：
- **数据边**：上游输出 → 下游输入（如搜索结果传给总结器）
- **控制边**：仅表达执行先后，不传递数据（如日志节点依赖初始化完成）

**拓扑（Topology）**：节点和边的完整结构。拓扑决定了整个工作流的骨架。

**拓扑排序（Topological Sort）**：将DAG转换为一个线性序列（或分层序列），使得所有依赖都满足。这是调度引擎的基础——只有拓扑排序后，才知道哪些节点可以立即执行。

**并行度控制**：拓扑排序后，处于同一"层级"的节点可以并行执行，但同时执行的节点数受资源限制。这就是并行度控制的作用。

### 2.2 关键路径与执行时序

DAG引擎的一个核心能力是**静态分析执行时序**：

```
拓扑分层示例：

Level 0:  [Query解析]           ← 立即执行
Level 1:  [搜索A, 搜索B, 搜索C]  ← 无依赖，并行
Level 2:  [融合器]              ← 依赖三个搜索全部完成
Level 3:  [LLM总结]            ← 依赖融合器完成
Level 4:  [输出格式化]          ← 依赖总结完成
```

**关键路径**（Critical Path）= DAG中最长的路径。在这个例子中，关键路径决定了总执行时间。引擎必须保证关键路径上的节点优先获得资源。

### 2.3 拓扑排序的算法选择

| 算法 | 时间复杂度 | 特点 | 适用场景 |
|------|-----------|------|---------|
| Kahn's算法 | O(V+E) | 基于入度，天然支持分层 | 生产引擎首选 |
| DFS后序反转 | O(V+E) | 简单，但不分层 | 调试和分析 |
| **并行拓扑排序** | O(V+E) | 输出为层级列表 | DAG调度器 |

Kahn's算法是生产引擎的标配——它在排序过程中自然地将节点分层，每层的节点可以并行执行。具体来说，Kahn's算法维护一个"入度为零"的节点集合，每次取出一个节点执行，同时更新其下游节点的入度。当多个节点同时入度为零时，它们自然形成一个可并行的层级。

### 2.4 DAG的表示方式

在工程实现中，DAG有两种主流表示方式：

| 表示方式 | 数据结构 | 优点 | 缺点 | 适用场景 |
|---------|---------|------|------|---------|
| **邻接表** | Dict[List] | 节省内存，遍历高效 | 不便检查边是否存在 | 大规模稀疏图 |
| **邻接矩阵** | 2D Array | O(1)查边，直观 | 空间O(V²) | 小规模稠密图 |

生产级引擎普遍采用邻接表——Agent工作流通常是稀疏图（每个节点的依赖不超过5个），邻接表的空间优势明显。

## §3 四种DAG执行模式对比

### 3.1 模式全景

```
┌─────────────────────────────────────────────────────────┐
│                   四种DAG执行模式                         │
│                                                          │
│  ① 串行模式          A → B → C → D                       │
│     线性依赖，零并行                                      │
│                                                          │
│  ② 并行扇出          A → [B, C, D] → E                   │
│     一对多分发，扇入汇聚                                   │
│                                                          │
│  ③ 条件分支          A → if/else → {B 或 C} → D           │
│     运行时动态决定走哪条路径                                │
│                                                          │
│  ④ 动态生成          A → 运行时生成 B' C' D' → E          │
│     DAG结构本身在运行时确定                                │
└─────────────────────────────────────────────────────────┘
```

### 3.2 详细对比

| 特性 | 串行模式 | 并行扇出 | 条件分支 | 动态生成 |
|------|---------|---------|---------|---------|
| **DAG静态/动态** | 静态 | 静态 | 半动态 | 动态 |
| **并行度** | 1 | N（扇出数） | 1（单分支） | 不确定 |
| **最大延迟** | Σ所有节点 | max(并行组) | 较长分支 | 不可预估 |
| **实现复杂度** | 低 | 中 | 中 | 高 |
| **调试难度** | 低 | 低 | 中 | 高 |
| **典型场景** | 简单RAG | 多源搜索 | 意图路由 | 子任务分解 |
| **框架支持** | LangChain | LangGraph | LangGraph + 条件边 | LangGraph动态图 |

### 3.3 条件分支的工程实现

条件分支是Agent DAG中最有价值的模式之一。核心问题是：**条件判断何时执行？**

- **静态条件**：在图构建时确定（如配置文件中的规则），引擎在调度前就知道走哪条路
- **运行时条件**：条件依赖上游节点的输出，必须在运行时动态评估

```
运行时条件分支示意：

         ┌─ [条件判断] ─┐
         │              │
    条件为true      条件为false
         │              │
    [Agent子任务A]  [Agent子任务B]
         │              │
         └──→ 汇聚 ←────┘
```

LangGraph中用`add_conditional_edges`实现，核心是传入一个**路由函数**，接收当前状态，返回下一跳节点名称。

### 3.4 动态生成：Agent DAG的终极形态

动态生成是最复杂但最强大的模式。典型的Agent框架（如AutoGPT、CrewAI）在运行时分解子任务，每个子任务构成一个新的节点。这意味着DAG的拓扑结构本身是运行时确定的。

工程挑战极其严峻：
- 引擎不能在启动时做完整的拓扑分析
- 必须支持**增量调度**——每完成一个节点，重新评估哪些新节点可以启动
- 内存占用不可控——DAG可能无限增长
- 子节点的依赖关系可能在运行时才确定（如Agent决定需要调用某个工具）
- 错误恢复更复杂——动态生成的节点没有预定义的检查点位置

生产级解决方案：
- 设置**最大节点数**（如100）和**最大深度**（如20）作为安全边界，超出时强制终止
- 采用**沙箱隔离**——动态子图在独立的State空间中运行，不影响主图
- 实现**渐进式检查点**——每生成N个新节点就保存一次，防止内存无限增长
- 引入**超时熔断**——动态图执行超过阈值自动终止，返回已收集的部分结果

## §4 生产级DAG引擎设计

### 4.1 五阶段生命周期

```
┌─────────────────────────────────────────────────────────┐
│               生产级DAG引擎五阶段生命周期                   │
│                                                          │
│  ① 任务注册    将工作流定义为DAG结构                        │
│       │                                                   │
│       ▼                                                   │
│  ② 依赖解析    拓扑排序 + 循环检测 + 关键路径分析            │
│       │                                                   │
│       ▼                                                   │
│  ③ 调度执行    按拓扑层级分发执行，控制并发度                 │
│       │                                                   │
│       ▼                                                   │
│  ④ 结果聚合    汇总各节点输出，传递给下游                    │
│       │                                                   │
│       ▼                                                   │
│  ⑤ 错误恢复    失败节点重试、降级、熔断                      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 任务注册：声明式 vs 编程式

生产系统通常支持两种注册方式：

**声明式（YAML/JSON）**：适合运维和配置驱动的场景
```yaml
workflow:
  name: multi_source_rag
  nodes:
    - id: query_parser
      type: llm
      model: gpt-4
      prompt: "解析用户查询意图"
    - id: search_web
      type: tool
      tool: web_search
      depends_on: [query_parser]
    - id: search_knowledge
      type: tool
      tool: vector_search
      depends_on: [query_parser]
    - id: merger
      type: code
      function: merge_results
      depends_on: [search_web, search_knowledge]
    - id: summarizer
      type: llm
      model: gpt-4
      depends_on: [merger]
```

**编程式（Python API）**：适合需要运行时动态构建的场景
```python
# LangGraph风格的编程式注册
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
graph.add_node("query_parser", parse_query)
graph.add_node("search_web", web_search)
graph.add_node("search_knowledge", vector_search)
graph.add_node("merger", merge_results)
graph.add_node("summarizer", summarize)

graph.add_edge("query_parser", "search_web")
graph.add_edge("query_parser", "search_knowledge")
graph.add_edge("search_web", "merger")
graph.add_edge("search_knowledge", "merger")
graph.add_edge("merger", "summarizer")
```

### 4.3 依赖解析：不只是拓扑排序

生产级引擎在依赖解析阶段要做三件事：

1. **循环检测**：如果A→B→C→A，DAG不成立。用DFS检测回边（back edge），有回边则报错
2. **关键路径计算**：每个节点赋予估算执行时间，用动态规划求最长路径。关键路径上的节点获得更多调度优先级
3. **资源预估**：根据拓扑结构估算峰值并发数、内存峰值、API调用次数

```
关键路径计算（简化）：

对每个节点 u，计算：
  earliest_start[u] = max(earliest_finish[predecessor(u)])
  earliest_finish[u] = earliest_start[u] + estimated_duration[u]

关键路径 = argmax(earliest_finish[root])
```

### 4.4 调度执行：事件驱动 vs 轮询

| 模型 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **事件驱动** | 上游完成 → 触发下游 | 延迟低、资源利用好 | 实现复杂 |
| **轮询** | 定期检查依赖是否满足 | 实现简单 | 延迟高、资源浪费 |

**生产级引擎选择事件驱动**。当一个节点完成时，立即检查其所有下游节点的依赖是否满足，如果满足则立即提交执行。这是LangGraph、Airflow 2.x、Temporal的核心调度模型。

### 4.5 结果聚合与数据传递

节点间的数据传递有三种策略：

| 策略 | 实现 | 适用场景 |
|------|------|---------|
| **全局状态** | 共享State对象，节点读写同一个State | LangGraph的默认模式 |
| **消息传递** | 上游输出作为消息推送给下游 | 通信密集型Agent |
| **共享存储** | 数据写入Redis/S3，下游按key读取 | 大数据量、跨进程 |

LangGraph选择了**全局状态**模式——所有节点共享一个TypedDict，每个节点的输出通过更新State来传递。这种设计简单直接，但在节点数超过100时会遇到状态膨胀问题。

### 4.6 错误恢复：三级容错

```
┌──────────────────────────────────────────┐
│           三级错误恢复策略                  │
│                                          │
│  Level 1: 节点重试                        │
│    策略：指数退避重试，最多3次              │
│    适用：瞬时错误（网络抖动、API限流）       │
│                                          │
│  Level 2: 分支降级                        │
│    策略：失败分支走备选路径                 │
│    适用：主路径不可用（主搜索源挂了）        │
│                                          │
│  Level 3: 子图隔离                        │
│    策略：隔离失败子图，返回部分结果          │
│    适用：非关键路径节点失败                 │
└──────────────────────────────────────────┘
```

关键原则：**非关键路径的失败不应该阻塞关键路径的执行。** 引擎需要区分节点的"必要性"——核心推理节点失败 = 整体失败；辅助节点失败 = 降级继续。

实际工程中的一个经典陷阱：**重试风暴**。当某个LLM API返回503时，10个并行节点同时重试，瞬间产生30个请求（每个重试3次），反而加剧了API过载。解决方案是引入**抖动退避**（Jittered Backoff）——在指数退避的基础上加入随机抖动，错开重试时间。

```python
import random

def jittered_backoff(attempt: int, base: float = 1.0, max_delay: float = 30.0) -> float:
    """抖动退避：避免重试风暴"""
    delay = min(base * (2 ** attempt), max_delay)
    return delay * (0.5 + random.random())  # 50%~100%的随机抖动
```

## §5 检查点与状态持久化

### 5.1 为什么需要检查点？

Agent工作流可能执行数分钟甚至数小时。LLM调用超时、进程重启、资源不足……任何一种情况都可能导致执行中断。如果没有检查点，一切从头开始。

**检查点的本质**：在DAG的每个层级完成时，将当前State序列化到持久存储。恢复时，从最近的检查点开始，跳过已完成的节点。

### 5.2 检查点存储模型

```
┌─────────────────────────────────────────────┐
│          检查点存储架构                        │
│                                              │
│  ┌──────────┐    ┌──────────┐               │
│  │ 执行引擎  │───▶│ 检查点    │               │
│  │          │    │ Manager  │               │
│  └──────────┘    └────┬─────┘               │
│                       │                      │
│            ┌──────────┼──────────┐           │
│            ▼          ▼          ▼           │
│      ┌──────────┐ ┌──────┐ ┌──────────┐    │
│      │ SQLite   │ │Redis │ │ PostgreSQL│    │
│      │ (本地)   │ │(缓存)│ │ (生产)    │    │
│      └──────────┘ └──────┘ └──────────┘    │
└─────────────────────────────────────────────┘
```

### 5.3 LangGraph的检查点实现

LangGraph通过`MemorySaver`（开发）或`PostgresSaver`（生产）实现检查点。核心接口极其简洁：

| 组件 | 开发模式 | 生产模式 |
|------|---------|---------|
| **存储后端** | 内存（MemorySaver） | PostgreSQL（PostgresSaver） |
| **序列化** | Pickle | JSON + 二进制混合 |
| **并发支持** | 单线程 | 行级锁 |
| **恢复语义** | 精确恢复 | 最终一致性 |

断点续跑的关键配置：
```python
# 为每个节点配置断点
from langgraph.checkpoint.memory import MemorySaver

graph = builder.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["search_web", "search_knowledge"],  # 在这些节点前可中断
)
```

运行时，执行到断点节点前会暂停。恢复时，通过`thread_id`定位到对应检查点继续执行。

### 5.4 检查点的工程权衡

| 权衡维度 | 频繁检查点 | 低频检查点 |
|---------|-----------|-----------|
| **恢复速度** | 快（跳过少） | 慢（重复执行多） |
| **存储开销** | 大 | 小 |
| **写入延迟** | 频繁写入影响执行速度 | 几乎无开销 |
| **适用场景** | 高价值长任务 | 低价值短任务 |

**经验法则**：每完成一个"资源密集型"节点（LLM调用、工具执行）后做一次检查点；纯计算节点可以不保存。

## §6 资源隔离与并发控制

### 6.1 为什么并发控制是DAG引擎的命门？

DAG的自动并行是优势，但如果不限制并发，会引发三个灾难：

1. **LLM API限流**：GPT-4的RPM限制通常是500-1000，10个并行LLM调用就可能触发
2. **内存溢出**：每个Agent节点都持有上下文，20个并行LLM调用可能吃掉数GB内存
3. **下游服务过载**：100个并行搜索请求打到同一个搜索引擎，直接触发限流

### 6.2 三级并发控制机制

```
┌─────────────────────────────────────────────────────────┐
│              三级并发控制机制                               │
│                                                          │
│  Level 1: 全局Semaphore                                 │
│    控制整个DAG的最大并行节点数                              │
│    实现：asyncio.Semaphore(max_concurrent)               │
│    适用：简单场景，节点类型单一                              │
│                                                          │
│  Level 2: 分类Worker Pool                               │
│    不同类型的节点使用不同的资源池                            │
│    实现：LLM Pool(size=10), Tool Pool(size=50)           │
│    适用：节点类型差异大                                    │
│                                                          │
│  Level 3: 背压机制（Backpressure）                       │
│    下游处理不过来时，上游自动减速                             │
│    实现：有界队列 + 生产者等待                              │
│    适用：跨服务调度，生产级系统                              │
└─────────────────────────────────────────────────────────┘
```

### 6.3 分类Worker Pool的设计

这是生产级系统最常用的方案。核心思想：**按资源需求将节点分组，每组有独立的资源池。**

```
┌─────────────────────────────────────────┐
│         分类Worker Pool架构               │
│                                          │
│  ┌─────────────┐  ┌─────────────┐       │
│  │ LLM Pool    │  │ Tool Pool   │       │
│  │ max=10      │  │ max=50      │       │
│  │ [████░░]    │  │ [██░░░░░]   │       │
│  │ 已用: 6     │  │ 已用: 2     │       │
│  └─────────────┘  └─────────────┘       │
│                                          │
│  ┌─────────────┐  ┌─────────────┐       │
│  │ Memory Pool │  │ IO Pool     │       │
│  │ max=20      │  │ max=30      │       │
│  │ [███░░]     │  │ [░░░░░]     │       │
│  │ 已用: 3     │  │ 已用: 0     │       │
│  └─────────────┘  └─────────────┘       │
└─────────────────────────────────────────┘
```

### 6.4 背压（Backpressure）机制

背压的核心问题：**当消费速度跟不上生产速度时，如何优雅地降级？**

常见策略：
- **有界队列**：队列满了，生产者等待（阻塞）或丢弃（丢弃策略）
- **速率限制**：消费端控制吞吐量，超出时拒绝新任务
- **动态降级**：检测到队列积压时，自动降低并行度（如将LLM并发从10降到5）

```
背压示意：

生产者(节点A) → [有界队列, 容量=100] → 消费者(LLM Worker)

当队列满时：
  策略1: 生产者阻塞等待
  策略2: 生产者降速（sleep）
  策略3: 丢弃低优先级任务
```

在Airflow 2.x中，背压通过`max_active_runs`和`pool`实现——当一个DAG的活跃运行数达到上限时，新触发的运行会等待。

## §7 实战：用LangGraph构建一个完整的DAG Agent工作流

### 7.1 场景：多源知识问答系统

用户提出一个问题，系统需要：
1. 解析问题意图
2. 从多个知识库并行检索
3. 对检索结果做相关性过滤
4. 融合多源结果
5. 生成最终答案

### 7.2 DAG结构设计

```
           ┌─ [向量检索1] ─→ [过滤1] ──┐
[意图解析] ─┼─ [向量检索2] ─→ [过滤2] ──┼─→ [融合] → [生成答案] → [输出]
           └─ [关键词检索] ─→ [过滤3] ──┘
                                        ↑
                                   [质量评估]（条件分支：结果不足时触发二次检索）
```

### 7.3 关键设计决策

**状态定义**：使用TypedDict定义全局状态，所有节点共享
```python
from typing import TypedDict, Annotated
from operator import add

class QAState(TypedDict):
    query: str
    intent: str
    search_results: Annotated[list, add]  # 多源结果追加合并
    filtered_results: list
    merged_results: list
    answer: str
    quality_score: float
```

**条件分支**：质量评估节点根据分数决定是否需要二次检索
```python
def quality_gate(state: QAState) -> str:
    """条件路由：决定下一步走哪条路"""
    if state["quality_score"] < 0.6:
        return "retry_search"    # 质量不够，重新检索
    elif state["quality_score"] < 0.8:
        return "expand_context"  # 质量一般，扩展上下文
    else:
        return "generate_answer" # 质量足够，直接生成

graph.add_conditional_edges("quality评估", quality_gate, {
    "retry_search": "二次检索",
    "expand_context": "上下文扩展",
    "generate_answer": "生成答案",
})
```

### 7.4 LangGraph的执行引擎工作流

```
┌───────────────────────────────────────────────────────┐
│            LangGraph执行引擎工作流                       │
│                                                        │
│  1. 用户调用 graph.invoke(input)                       │
│  2. 引擎加载DAG拓扑，执行拓扑排序                        │
│  3. 识别Level 0节点（意图解析），提交执行                  │
│  4. 意图解析完成 → 触发3个搜索节点并行执行                 │
│  5. 3个搜索完成 → 触发3个过滤节点并行执行                  │
│  6. 3个过滤完成 → 触发融合节点                           │
│  7. 融合完成 → 触发质量评估                              │
│  8. 质量评估路由 → 生成答案（或回退到二次检索）             │
│  9. 每个关键节点后自动保存检查点                          │
│ 10. 全部完成，返回最终State                              │
└───────────────────────────────────────────────────────┘
```

### 7.5 LangGraph vs Airflow vs Temporal：选型对比

| 特性 | LangGraph | Airflow | Temporal |
|------|-----------|---------|----------|
| **定位** | Agent工作流引擎 | 通用数据流水线 | 通用工作流引擎 |
| **DAG构建** | Python代码 | Python/DAG文件 | 代码定义 |
| **状态模型** | 全局State | XCom传递 | Workflow Context |
| **检查点** | 内置 | 无原生支持 | 重试即检查点 |
| **条件分支** | `add_conditional_edges` | BranchOperator | Activity返回决定 |
| **动态DAG** | 支持 | 有限支持 | 完全支持 |
| **Agent适配** | 天然适配 | 需要适配层 | 需要适配层 |
| **监控** | LangSmith | Airflow UI | Temporal UI |
| **适用规模** | 单Agent/小规模多Agent | 大规模批处理 | 企业级长时间工作流 |

**选型建议**：
- Agent开发阶段 → **LangGraph**（迭代快，调试方便）
- 数据密集型Agent → **Airflow**（成熟的调度和监控）
- 企业级生产工作流 → **Temporal**（最强的容错和状态管理）

## §8 面试深度：如何设计一个支持百万任务/天的Agent调度系统

### 8.1 系统架构全景

```
┌─────────────────────────────────────────────────────────┐
│               百万任务/天 Agent调度系统架构                 │
│                                                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ API网关   │→ │ 任务入口  │→ │ 优先级队列 │              │
│  │ (限流)    │  │ (验证)   │  │ (Redis)   │              │
│  └──────────┘  └──────────┘  └─────┬─────┘              │
│                                     │                     │
│                              ┌──────▼──────┐             │
│                              │  调度器      │             │
│                              │ (Worker分配) │             │
│                              └──────┬──────┘             │
│                                     │                     │
│            ┌────────────────────────┼────────────────┐   │
│            ▼            ▼           ▼                ▼   │
│     ┌──────────┐  ┌──────────┐ ┌──────────┐  ┌──────┐  │
│     │ Worker 1 │  │ Worker 2 │ │ Worker N │  │ GPU  │  │
│     │ (CPU)    │  │ (CPU)    │ │ (CPU)    │  │Pool  │  │
│     └──────────┘  └──────────┘ └──────────┘  └──────┘  │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │              状态存储层                             │   │
│  │  PostgreSQL(状态) + Redis(缓存) + S3(检查点)       │   │
│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

### 8.2 核心设计问题

**Q1: 如何处理百万级并发任务？**

关键在于**分层调度**：
- **入口层**：API网关做限流（令牌桶），防止突发流量压垮系统
- **队列层**：Redis Sorted Set做优先级队列，按优先级和创建时间排序
- **调度层**：调度器从队列取任务，按Worker能力分配（CPU密集型 → CPU Worker，GPU密集型 → GPU Worker）
- **执行层**：Worker池水平扩展，每个Worker独立消费

**Q2: 如何保证任务不丢失？**

采用**At-least-once**语义：
- 任务从队列取出后，进入"处理中"状态
- Worker完成/失败后，显式更新状态
- 定期扫描"处理中"超过阈值的任务，重新入队（超时恢复）

**Q3: 如何处理DAG内部的依赖？**

DAG级别的调度和任务级别的调度是两个层次：
- **DAG级**：一个Agent工作流作为一个DAG，提交时解析依赖
- **任务级**：DAG内每个节点作为独立任务，由调度器按依赖关系分发

这种分层设计让每个层次关注自己的问题：DAG级关注拓扑和依赖，任务级关注执行和资源。

### 8.3 关键性能指标

| 指标 | 目标值 | 说明 |
|------|-------|------|
| 任务提交延迟 | < 100ms | 从API到进入队列 |
| 调度延迟 | < 500ms | 从就绪到开始执行 |
| 端到端延迟（P99） | < 30s | 简单任务 |
| 任务吞吐量 | > 1000/min | 峰值处理能力 |
| 检查点写入延迟 | < 100ms | 不阻塞执行 |
| 恢复时间（RTO） | < 30s | 从故障到恢复执行 |

## 总结

DAG执行引擎是Agent系统从"玩具"走向"生产"的关键基础设施。它解决的核心问题是：**如何高效、可靠、可观测地执行复杂的多步骤工作流？**

三个关键洞察：
1. **DAG的本质是将隐式依赖显式化**——一旦依赖关系被显式建模，并行、恢复、监控都变得自然
2. **检查点是DAG引擎的生命线**——没有检查点，长时间运行的Agent工作流就是定时炸弹
3. **并发控制决定DAG的上限**——DAG能自动并行是优势，但无限并行是灾难。分级资源池+背压机制是生产标配

DAG引擎的设计不仅是技术选型问题，更是对"任务依赖"这一本质问题的工程回答。掌握它，你就能在面试中清晰地解释：为什么Agent需要DAG，DAG如何工作，以及如何让它在生产环境中稳定运行。
