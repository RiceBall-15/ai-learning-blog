# Agent规划失败恢复：当CoT/ToT/GoT走错路时的自救策略

> 系列文章：面试方向4「自主规划与推理」深度补充。本文聚焦一个被大多数教程忽略的核心问题——**规划失败之后怎么办？**

我们在前序文章中详细讨论了CoT、ToT、GoT等推理框架如何帮助Agent进行复杂任务规划。但实际工程中有一个残酷的现实：**规划失败是常态，不是例外。** 一个能在100次规划中成功80次的Agent，如果没有恢复机制，整体可靠性可能还不如一个简单但有回滚能力的Agent。

这篇文章就来深入拆解：当Agent的规划"走错路"时，有哪些系统化的自救策略。

---

## §1 规划失败的五大模式

在讨论恢复策略之前，我们需要先识别敌人。通过分析大量实际部署中的Agent系统日志，我们总结出规划失败的五大典型模式：

| 失败模式 | 表现 | 根因 | 出现频率 |
|---------|------|------|---------|
| **死循环（Loop）** | Agent反复回到同一状态，执行重复动作 | 缺乏状态感知；规划器未记录已访问状态 | 高 |
| **方向偏离（Drift）** | 逐步偏离原始目标，最终产出无关结果 | 中间决策累积偏差；缺乏目标锚定 | 高 |
| **过度分解（Over-decomposition）** | 子任务无限细分，总任务数爆炸 | 分解策略缺乏粒度约束 | 中 |
| **资源耗尽（Exhaustion）** | Token预算/时间预算/工具调用次数用尽 | 无资源感知的规划器 | 中 |
| **矛盾目标（Conflict）** | 子任务之间互相矛盾，无法并行或顺序执行 | 顶层规划未做一致性检查 | 低 |

```
┌─────────────────────────────────────────────────────────────────────┐
│                     Agent 规划失败模式分布                           │
│                                                                     │
│  死循环 ████████████████████░░░░░░░░░░  ~40%                       │
│  方向偏离 ██████████████████░░░░░░░░░░  ~35%                       │
│  过度分解 █████████░░░░░░░░░░░░░░░░░░░  ~15%                       │
│  资源耗尽 ████░░░░░░░░░░░░░░░░░░░░░░░  ~6%                        │
│  矛盾目标 ██░░░░░░░░░░░░░░░░░░░░░░░░░  ~4%                        │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.1 死循环模式

这是最常见的失败模式。典型场景：Agent使用WebSearch工具搜索一个不存在的信息，返回空结果后换个关键词再搜，再搜，再搜……直到Token预算耗尽。

**本质问题**：规划器没有"记忆"自己已经尝试过什么。CoT是无状态的线性推理，天然缺乏环路检测；ToT虽然有树形结构，但如果评估函数不够灵敏，也会在无效分支上持续展开。

### 1.2 方向偏离模式

这种模式更隐蔽。Agent每一步推理看起来都合理，但整体方向逐渐偏离了原始目标。比如用户要求"分析A公司Q3财报"，Agent从财务指标分析开始，逐步深入到行业对比，再深入到宏观经济分析，最后在分析美联储政策——虽然每一步推理逻辑上都是通的。

**本质问题**：缺少"目标锚定检查"。GoT的图结构理论上可以通过边权重来控制方向，但实际实现中很少做。

### 1.3 过度分解模式

Agent把一个任务分解成太多子任务，每个子任务又继续分解，导致执行效率极低。例如"写一篇文章"被分解成"确定主题→确定结构→写每一段→检查语法→格式化"，而每个步骤又被独立执行和验证，10个步骤变成了50个步骤。

### 1.4 资源耗尽模式

Agent没有资源预算意识，在一个子任务上消耗了全部预算，导致其他子任务完全无法执行。这在多步骤任务中尤为致命。

### 1.5 矛盾目标模式

这种模式在多Agent协作中更常见，但单Agent也可能出现。比如Agent同时计划"快速完成任务"和"详细验证每一步"，这两个目标在有限资源下是矛盾的。

## §2 失败检测机制：如何知道规划走错了路

检测失败是恢复的前提。我们需要一套多层次的检测体系：

```
┌─────────────────────────────────────────────────────────────────────┐
│                      失败检测架构                                     │
│                                                                     │
│  ┌──────────┐   ┌──────────────┐   ┌──────────────┐                │
│  │ 即时检测  │   │   中期检测    │   │   终态检测    │                │
│  │ (每步)    │   │  (每N步)     │   │  (任务结束)   │                │
│  └────┬─────┘   └──────┬───────┘   └──────┬───────┘                │
│       │                │                  │                         │
│  ·状态重复检测    ·目标偏移评估      ·结果质量评估                    │
│  ·工具异常检测    ·资源消耗审计      ·与原始需求对比                  │
│  ·Token预警      ·进度里程碑检查    ·用户满意度反馈                  │
│       │                │                  │                         │
│       └────────────────┼──────────────────┘                        │
│                        ▼                                            │
│              ┌──────────────────┐                                   │
│              │   综合判定模块    │                                   │
│              │  触发恢复策略     │                                   │
│              └──────────────────┘                                   │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.1 自动检测机制

**状态重复检测**：维护一个已访问状态的哈希集合。每步执行前对比当前状态与历史状态，如果相似度超过阈值（例如Jaccard相似度 > 0.8），触发死循环警报。

**目标偏移检测**：定期（每N步）将当前推理内容与原始目标做语义相似度对比。可以使用Embedding模型计算cosine similarity，当相似度从初始值下降超过一定百分比时触发偏移警报。

```python
def detect_drift(original_goal: str, current_trace: str, 
                 embed_model, threshold: float = 0.3) -> bool:
    """检测规划是否偏离原始目标"""
    goal_emb = embed_model.encode(original_goal)
    trace_emb = embed_model.encode(current_trace)
    similarity = cosine_similarity(goal_emb, trace_emb)
    return similarity < (1.0 - threshold)  # 偏离超过threshold则触发
```

**资源消耗审计**：在规划器中内嵌预算感知模块，追踪Token使用量、工具调用次数、已执行步骤数，当任意指标超过预算的70%时发出预警，超过90%时强制进入降级模式。

**工具异常检测**：监控工具调用的返回值。连续N次返回错误、空结果或超时，触发工具层面的失败检测。

### 2.2 人工干预触发点

在生产环境中，全自动检测不够。需要设置明确的人工介入点：

| 触发条件 | 干预方式 | 适用场景 |
|---------|---------|---------|
| 高风险操作执行前 | 人工审批（Human-in-the-loop） | 数据删除、资金操作、外部API调用 |
| 连续失败超过N次 | 弹窗确认是否继续 | 所有需要工具交互的任务 |
| 任务耗时超过预期2倍 | 通知用户并等待指令 | 长时间运行的批处理任务 |
| 检测到方向偏离 | 展示当前进展供用户确认 | 多步骤复杂任务 |

### 2.3 检测的时效性权衡

检测本身也有成本。过于频繁的检测会拖慢Agent执行效率。实践中推荐的策略是：

- **轻量级检测**（状态重复、Token计数）→ 每步执行
- **中等成本检测**（目标偏移、资源审计）→ 每5-10步执行
- **重量级检测**（结果质量评估、与需求对比）→ 任务完成时执行

## §3 即时回滚策略：检查点保存 + 状态恢复 + 重试

当检测到失败后，最直接的恢复手段是"回到上一个好状态"——即回滚。

### 3.1 检查点设计

```
┌─────────────────────────────────────────────────────────────────────┐
│                        检查点层次结构                                 │
│                                                                     │
│  Level 0: 任务初始状态                                               │
│  ├── Level 1: 第一步完成后                                          │
│  │   ├── Level 2: 子任务A完成                                       │
│  │   └── Level 2: 子任务B进行中                                      │
│  ├── Level 1: 第二步完成后                                          │
│  └── Level 1: 第三步进行中 ←── 当前状态                             │
│                                                                     │
│  保存内容：                                                          │
│  · 推理链（CoT/ToT/GoT完整记录）                                    │
│  · 工具调用历史（入参+返回值）                                       │
│  · 中间结果（结构化存储）                                            │
│  · 资源消耗快照（剩余Token/时间）                                    │
└─────────────────────────────────────────────────────────────────────┘
```

检查点设计的关键决策：

**保存频率**：不是每步都保存（成本太高），而是在关键节点保存——子任务完成时、状态显著变化时、工具调用成功返回时。这类似于数据库的WAL（Write-Ahead Logging）策略。

**保存粒度**：保存完整的推理链太重。实际中保存"增量"更高效——每个检查点只记录相对于上一个检查点的差异（delta）。

**存储位置**：内存级检查点用于快速回滚；持久化检查点用于跨会话恢复。两者配合使用。

### 3.2 状态恢复策略

恢复不总是简单的"回到上一步"。根据失败类型，有三种恢复策略：

| 恢复策略 | 适用场景 | 操作 | 风险 |
|---------|---------|------|------|
| **完全回滚** | 死循环、严重偏离 | 回到最近的健康检查点，丢弃所有后续工作 | 可能丢失已完成的有价值工作 |
| **部分回滚** | 方向偏离、中间错误 | 回到出错步骤之前，保留之前的有效工作 | 需要精确识别"出错点" |
| **跳过恢复** | 单个工具/子任务失败 | 跳过失败步骤，用替代方案或标记为降级完成 | 可能影响最终结果质量 |

### 3.3 重试策略

回滚后的重试不是简单地"再做一遍"。如果用同样的方法重试，只会再次失败。有效的重试策略：

**换路径重试**：在ToT框架中，回滚到分支节点，选择另一条未尝试的路径。

**换策略重试**：修改提示词、调整参数、使用不同的工具。比如WebSearch失败后，切换到特定数据库查询。

**降低难度重试**：将复杂子任务进一步简化后重试。比如"完整分析X"降级为"列出X的关键数据点"。

**换Agent重试**：在多Agent系统中，将失败任务分配给具有不同能力或视角的Agent。

## §4 降级执行：当高级规划失败时退化到简单策略

降级（Degradation）是工业系统中常见的容错策略。在Agent系统中，降级意味着从复杂推理模式退化到简单模式。

### 4.1 降级梯度

```
┌─────────────────────────────────────────────────────────────────────┐
│                     推理降级梯度                                      │
│                                                                     │
│  ┌──────────┐                                                       │
│  │   GoT    │  图推理：多路径探索+全局优化                            │
│  └────┬─────┘  失败                                                  │
│       ▼                                                              │
│  ┌──────────┐                                                       │
│  │   ToT    │  树推理：分支探索+最优路径选择                          │
│  └────┬─────┘  失败                                                  │
│       ▼                                                              │
│  ┌──────────┐                                                       │
│  │   CoT    │  链推理：线性步骤推导                                   │
│  └────┬─────┘  失败                                                  │
│       ▼                                                              │
│  ┌──────────┐                                                       │
│  │ 直接推理  │  无Chain，直接生成答案                                 │
│  └────┬─────┘  失败                                                  │
│       ▼                                                              │
│  ┌──────────┐                                                       │
│  │ 检索增强  │  回退到RAG，从知识库直接检索答案                       │
│  └────┬─────┘  失败                                                  │
│       ▼                                                              │
│  ┌──────────┐                                                       │
│  │ 求助人类  │  输出最佳猜测+请求人工指引                             │
│  └──────────┘                                                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 降级决策逻辑

何时触发降级？关键判断依据：

1. **时间预算消耗比**：如果已消耗50%的时间预算但进度不足20%，触发一级降级
2. **失败次数**：连续3次推理失败触发一级降级，连续5次触发二级
3. **复杂度检测**：如果当前推理链深度超过阈值但尚未收敛，主动降级

### 4.3 降级的质量保证

降级后的结果质量可能下降，但可以通过以下方式保证"降级不降质"：

- **降级标注**：在最终输出中标注"此结果基于简化推理，建议人工复核"
- **降级缓存**：将降级模式的结果缓存，当用户后续追问时，用更高级的推理重新生成
- **降级学习**：记录每次降级的触发条件和降级路径，用于后续优化降级决策

## §5 Reflexion机制：从失败中学习避免重复犯错

Reflexion（Shinn et al., 2023）是目前最系统的"从失败中学习"框架。核心思想：Agent不仅在做任务，还在对自己的表现做"元认知"分析。

### 5.1 Reflexion流程

```
┌─────────────────────────────────────────────────────────────────────┐
│                      Reflexion 循环                                  │
│                                                                     │
│  ┌─────────────┐     ┌─────────────┐     ┌──────────────┐          │
│  │  执行任务    │────▶│  评估结果    │────▶│  生成反思     │          │
│  │ (Actor)     │     │ (Evaluator) │     │ (Reflector)  │          │
│  └─────────────┘     └─────────────┘     └──────┬───────┘          │
│         ▲                                        │                  │
│         │            ┌──────────────┐            │                  │
│         └────────────│  经验记忆库   │◀───────────┘                  │
│                      │  (Memory)    │                                │
│                      └──────────────┘                                │
└─────────────────────────────────────────────────────────────────────┘
```

**执行阶段**：Agent正常执行任务，记录完整的推理轨迹。

**评估阶段**：通过环境反馈（测试结果、工具返回值、用户反馈）评估执行质量。不是简单的"成功/失败"二分类，而是细粒度的错误分析。

**反思阶段**：Agent用自然语言描述"这次失败的原因是什么"、"下次应该怎么做"。这比传统ML的error gradient更灵活——它生成的是可解释的、可迁移的经验。

**记忆阶段**：将反思结果存入长期记忆库，下次执行类似任务时作为上下文提供给规划器。

### 5.2 Reflexion的关键算法

```python
class ReflexionAgent:
    def __init__(self, actor, reflector, memory, max_retries=3):
        self.actor = actor
        self.reflector = reflector
        self.memory = memory
        self.max_retries = max_retries

    def run_with_reflection(self, task):
        for attempt in range(self.max_retries):
            # 检索相关历史经验
            relevant_experiences = self.memory.retrieve(task)
            # 执行任务（带上历史经验作为参考）
            result = self.actor.execute(task, context=relevant_experiences)
            # 评估结果
            evaluation = self.actor.evaluate(task, result)
            if evaluation.is_sufficient():
                # 成功：存储正面经验
                self.memory.store(task, result, evaluation, "success")
                return result
            # 失败：生成反思
            reflection = self.reflector.reflect(
                task=task, result=result, evaluation=evaluation,
                previous_reflections=[e.reflection for e in relevant_experiences]
            )
            # 存储反思经验
            self.memory.store(task, result, evaluation, reflection)
        return self.handle_final_failure(task)
```

### 5.3 Reflexion的实战经验

在实际部署中，Reflexion有几个关键的工程细节：

**反思的质量**：不是所有LLM都能生成高质量的反思。GPT-4级别的模型生成的反思明显优于小模型。对于小模型，可以用GPT-4生成反思示例来微调。

**经验库的检索**：不是所有历史经验都有用。需要按任务类型、失败模式做语义检索，只提供最相关的历史经验（通常3-5条），否则会污染当前推理上下文。

**反思的时效性**：工具的API可能更新，环境可能变化。过于陈旧的经验可能反而有害。建议设置经验的"保质期"，超过N天的经验自动衰减权重。

## §6 动态重规划：执行过程中发现偏差时的实时调整

静态规划（先规划后执行）在简单任务中有效，但在复杂任务中几乎必然失败。动态重规划是更实际的选择。

### 6.1 Plan-Execute-Observe-Replan循环

```
┌─────────────────────────────────────────────────────────────────────┐
│                    动态重规划状态机                                    │
│                                                                     │
│   ┌───────┐    规划    ┌────────┐    执行    ┌────────┐            │
│   │ 初始  │──────────▶│ 当前计划 │──────────▶│ 执行中 │            │
│   └───────┘           └────────┘            └───┬────┘            │
│                                                  │                  │
│                                          观察结果                    │
│                                                  │                  │
│                                    ┌─────────────▼─────────────┐    │
│                                    │      偏差评估              │    │
│                                    │  偏差 < 阈值？             │    │
│                                    └─────┬───────────────┬─────┘    │
│                                          │ 是            │ 否       │
│                                          ▼              ▼           │
│                                    ┌──────────┐  ┌──────────┐      │
│                                    │ 继续执行  │  │ 重规划    │      │
│                                    │ 下一步骤  │  │          │      │
│                                    └──────────┘  └────┬─────┘      │
│                                                       │            │
│                                                       ▼            │
│                                                ┌───────────┐       │
│                                                │ 生成新计划 │       │
│                                                └─────┬─────┘       │
│                                                      │             │
│                                                      ▼             │
│                                                回到执行阶段         │
└─────────────────────────────────────────────────────────────────────┘
```

### 6.2 偏差评估方法

如何判断"执行结果与计划偏差"？三种方法的对比：

| 方法 | 原理 | 优点 | 缺点 |
|-----|------|------|------|
| **基于规则** | 预定义的偏差阈值和规则 | 快速、确定性高 | 不够灵活，需要人工定义规则 |
| **基于模型** | LLM判断当前结果是否符合预期 | 灵活、语义理解能力强 | 有延迟、成本高、判断不一致 |
| **混合方法** | 规则先筛，模型再判 | 平衡速度和准确性 | 实现复杂度高 |

**推荐方案**：混合方法。用规则做第一层快速筛选（比如结果为空、返回错误、关键字段缺失），规则通过后再用LLM做语义层面的偏差判断。

### 6.3 重规划策略

当偏差被确认后，重规划不是"推倒重来"，而是有策略地调整：

**局部重规划**：只调整受影响的后续步骤，已完成的步骤保持不变。这是最常用的策略。

**全局重规划**：当偏差严重到影响整体目标时，重新从头规划。成本高但必要。

**约束松弛重规划**：当原计划在约束条件下无法完成时，主动松弛部分约束（比如放宽时间要求、降低输出质量要求），在新约束下重新规划。

## §7 多Agent协作中的规划冲突：目标不一致时的协调

单Agent的规划失败已经很复杂，多Agent系统中的规划冲突更是工程噩梦。

### 7.1 常见冲突类型

```
┌─────────────────────────────────────────────────────────────────────┐
│                    多Agent规划冲突类型                                │
│                                                                     │
│  Agent A ──写代码──▶ 代码文件 v1                                    │
│  Agent B ──写测试──▶ 测试文件 (基于 v0 接口)                        │
│                        ▲                                             │
│                        └── 冲突！接口不匹配                          │
│                                                                     │
│  ── 资源竞争 ──                                                      │
│  Agent A ──读取数据库──▶ 数据读取中...                               │
│  Agent B ──修改数据库──▶ 等待... (锁冲突)                           │
│                                                                     │
│  ── 目标冲突 ──                                                      │
│  Agent A: 优化性能  →  复杂实现，运行快                              │
│  Agent B: 保证可读  →  简单实现，运行慢                              │
│                    →  两个目标无法同时满足                            │
└─────────────────────────────────────────────────────────────────────┘
```

### 7.2 冲突解决策略

**全局协调者（Orchestrator）模式**：

指定一个专门的协调Agent，负责分配任务、检测冲突、仲裁分歧。协调者不执行具体任务，专注于全局一致性。

**合同网协议（Contract Net Protocol）**：

源自分布式AI的经典协议。任务发布→Agent投标→协调者选择最优Agent。自然地避免了冲突，因为每个任务只分配给一个Agent。

**基于约束满足的协调**：

将多Agent协作建模为约束满足问题（CSP）。每个Agent的计划是变量，约束包括时间约束、资源约束、依赖约束。用CSP求解器找到满足所有约束的联合计划。

### 7.3 通信机制

多Agent间的通信不是"越多越好"。过多的通信会导致协调开销大于并行收益。推荐的通信策略：

| 通信类型 | 频率 | 内容 | 目的 |
|---------|------|------|------|
| 心跳消息 | 每N步 | 状态摘要、资源使用 | 保持协调者对全局状态的感知 |
| 事件通知 | 触发时 | 关键事件（完成、失败、阻塞） | 协调者及时响应异常 |
| 数据交换 | 需要时 | 结构化的中间结果 | Agent间协作完成依赖任务 |

## §8 实战：构建一个带自动恢复的Agent规划系统

将前面所有机制整合到一个可工作的系统中：

### 8.1 系统架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                   自动恢复Agent规划系统                               │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────┐      │
│  │                    用户接口层                              │      │
│  └──────────────────────────┬────────────────────────────────┘      │
│                              │                                      │
│  ┌──────────────────────────▼────────────────────────────────┐      │
│  │                    编排层 (Orchestrator)                   │      │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │      │
│  │  │  规划器   │  │  执行器   │  │  检测器   │  │  恢复器   │ │      │
│  │  │ Planner  │  │ Executor │  │ Monitor  │  │ Recover  │ │      │
│  │  └──────────┘  └──────────┘  └──────────┘  └──────────┘ │      │
│  └───────────────────────────────────────────────────────────┘      │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────┐      │
│  │                    记忆层 (Memory)                        │      │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐                │      │
│  │  │ 工作记忆  │  │ 经验记忆  │  │ 检查点   │                │      │
│  │  │ Working  │  │ Reflexion│  │ Snapshot │                │      │

│  └───────────────────────────────────────────────────────────┘      │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────┐      │
│  │                    工具层 (Tools)                          │      │
│  │  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐         │      │
│  │  │Search  │  │ Code   │  │ DB     │  │ API    │  ...    │      │
│  │  └────────┘  └────────┘  └────────┘  └────────┘         │      │
│  └───────────────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────────────┘
```

### 8.2 核心组件设计

**编排层**是系统的大脑，包含四个协同组件：

**规划器（Planner）**：接收用户任务，生成初始计划。内置降级策略——默认使用CoT，复杂任务升级到ToT，关键任务使用GoT。

**执行器（Executor）**：按照计划逐步执行，每步执行前创建检查点，执行后记录结果到工作记忆。

**检测器（Monitor）**：并行运行，持续监控执行状态。使用§2中的多层检测机制，产生"健康信号"（绿/黄/红）。

**恢复器（Recover）**：当检测器发出黄色信号时，通知规划器做局部调整；发出红色信号时，执行回滚、降级或重规划。

### 8.3 关键交互流程

```
用户提交任务
    │
    ▼
Planner 生成初始计划 + 查询 Reflexion 记忆库（有没有类似任务的历史经验？）
    │
    ▼
Executor 开始执行第一步 → 创建 Checkpoint_0
    │
    ├──▶ 执行成功 → 记录结果 → 继续下一步
    │
    └──▶ Monitor 检测到异常（连续3次工具调用失败）
            │
            ▼
        Recover 介入：
            ├── 尝试1：换工具/换参数重试
            ├── 尝试2：部分回滚到 Checkpoint_0，局部重规划
            ├── 尝试3：降级执行（简化子任务）
            └── 尝试4：完全回滚，全局重规划
    │
    ▼
任务完成（或达到最大重试次数）
    │
    ▼
评估最终结果 → 生成 Reflexion 经验 → 存入记忆库
```

### 8.4 实际部署中的关键参数

这些参数需要根据具体场景调优，但提供参考值：

| 参数 | 参考值 | 说明 |
|------|--------|------|
| 检查点最大数量 | 20-50 | 防止检查点占用过多内存 |
| 回滚最大深度 | 3-5步 | 避免无限回滚 |
| 降级触发阈值 | 连续失败3次 | 平衡重试成本和降级质量 |
| 目标偏移阈值 | cosine sim < 0.5 | 过于严格会频繁触发，过于宽松则无法检测 |
| 反思记忆库大小 | 50-100条 | 只保留最有效的经验 |
| 最大重试次数 | 3次 | 超过后降级或请求人工介入 |

## §9 面试深度：如何设计一个鲁棒的Agent规划系统

面试中这类问题考察的是系统思维和工程深度。以下是高频问题和参考回答框架。

### 9.1 高频面试题

**Q1: 如果让你设计一个Agent系统，如何保证规划的可靠性？**

回答框架（STAR法则）：

1. **防御性设计**：假设规划会失败，从第一天就设计恢复机制，而不是事后补救
2. **分层检测**：每步轻量检测 + 中期语义检测 + 终态质量检测
3. **渐进恢复**：先重试→再回滚→再降级→再请求帮助，逐步升级
4. **经验积累**：Reflexion机制让系统越用越好
5. **可观测性**：完整记录规划过程，便于调试和优化

**Q2: CoT/ToT/GoT在规划恢复方面各有什么优劣？**

| 方面 | CoT | ToT | GoT |
|------|-----|-----|-----|
| 失败检测 | 难（线性，无分支点） | 易（分支评估） | 最易（图结构，多角度评估） |
| 回滚能力 | 弱（只能回到开头） | 中（回滚到分支节点） | 强（回滚到任意节点） |
| 替代路径 | 无（只有一条链） | 中（同层其他分支） | 强（任意可达节点） |
| 恢复成本 | 低（但效果差） | 中 | 高（但效果好） |
| 适用场景 | 简单任务 | 中等复杂度 | 高复杂度、高可靠性要求 |

**Q3: 在实际生产中，你会选择什么方案？为什么？**

经验性回答：大多数场景下，**混合方案**是最佳选择。用CoT做快速路径（80%的简单任务），用ToT做中等复杂度任务，用GoT只处理关键路径上的高价值任务。同时配合Reflexion记忆库，让系统不断积累经验。这样既控制了成本，又保证了关键场景的可靠性。

**Q4: Reflexion和传统RLHF有什么本质区别？**

核心区别：

| 维度 | RLHF | Reflexion |
|------|------|-----------|
| 反馈来源 | 人类标注 | 环境自动反馈+自生成 |
| 优化方式 | 更新模型参数 | 更新提示/策略（无需训练） |
| 适用范围 | 模型训练阶段 | 推理阶段（运行时） |
| 迁移性 | 低（绑定特定模型） | 高（经验可跨模型迁移） |
| 成本 | 高（需要人类标注） | 低（自动运行） |

**Q5: 如何处理LLM固有的不确定性对规划的影响？**

LLM的输出不确定性是规划失败的根本原因之一。应对策略：

1. **确定性锚点**：在规划中引入确定性组件（如规则引擎、工具调用），减少对LLM不确定输出的依赖
2. **多次采样取最优**：对关键决策点采样多次，选择一致性最高的结果
3. **概率规划**：在规划中标注置信度，低置信度的步骤触发更多验证
4. **环境反馈校准**：通过工具返回值验证LLM推理的正确性

### 9.2 加分回答要点

如果面试官对以上回答满意，可以进一步展开以下话题：

**成本控制**：恢复机制本身也有成本。最优策略是"预防 > 检测 > 恢复"——提升初始规划质量比事后的恢复更重要。可以用历史数据驱动的策略来优化资源分配。

**可观测性**：设计完整的日志和追踪系统（类似OpenTelemetry），记录每一步的输入/输出/决策依据。这不是锦上添花，而是生产环境的刚需。

**A/B测试**：不同的恢复策略适合不同的场景。通过A/B测试持续优化恢复策略的选择逻辑。

**从SRE视角看Agent可靠性**：借鉴Google SRE的SLO/SLI概念——定义Agent的"可靠性目标"（如95%的任务在预算内完成），基于这个目标反向设计检测和恢复策略。

## 总结

Agent规划失败恢复不是一个单一技术，而是一个**系统工程**。它需要：

1. **识别模式**——知道会怎么失败，才能提前防备
2. **实时检测**——在失败扩展前及时发现
3. **分级恢复**——根据失败严重程度选择合适的恢复策略
4. **持续学习**——每次失败都变成未来的经验
5. **系统整合**——将所有机制整合成一个协调工作的系统

在面试中，能够系统性地讨论这些问题，而不是只停留在"加个重试"的层面，会显著提升你的竞争力。
