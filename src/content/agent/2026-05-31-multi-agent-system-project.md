# 多Agent系统实战：从需求分析到上线的完整项目构建

> 这是面试方向3（多Agent协同）的深度补充。之前我们聊了理论框架和常见模式，这篇文章直接上手——从零构建一个真实的多Agent系统，覆盖需求分析、架构设计、通信机制、生产化改造的全链路。

## §1 项目背景：构建一个「AI研究团队」多Agent系统

### 1.1 业务场景

假设你所在的公司要做一个「AI研究助手」产品：用户输入一个研究主题（比如「2026年大语言模型的发展趋势」），系统自动完成文献检索、数据分析、报告撰写、质量审校，最终交付一份结构化的研究报告。

这个任务的复杂度决定了单Agent方案的天花板太低：

- 涉及多种工具调用（搜索引擎、数据库、文档生成器）
- 需要多轮推理和迭代修正
- 不同环节对模型能力的要求不同（检索需要精准、写作需要创造力、审校需要批判性思维）
- 最终输出需要多维度质量保证

因此，我们决定采用多Agent架构，构建一个模拟真实研究团队的AI协作系统。

### 1.2 团队角色定义

我们定义了四个核心Agent角色：

| 角色 | 类比人类 | 核心职责 | 模型选型 |
|------|----------|----------|----------|
| 🔍 研究员 (Researcher) | 研究助理 | 信息检索、资料收集、事实核查 | GPT-4o（强推理） |
| 📊 分析师 (Analyst) | 数据分析师 | 数据提取、趋势分析、观点归纳 | Claude Sonnet（结构化输出） |
| ✍️ 写手 (Writer) | 内容编辑 | 报告撰写、逻辑组织、可读性优化 | GPT-4o（创造性写作） |
| ✅ 审校 (Reviewer) | 质量总监 | 事实核查、逻辑验证、质量把关 | Claude Opus（批判性思维） |

### 1.3 预期收益

相比单Agent方案，多Agent架构的核心优势：

```
单Agent方案：一次调用完成所有工作
  ↓ 问题：上下文窗口限制、角色混淆、质量不可控
  ↓ 结果：输出质量中等，迭代成本高

多Agent方案：专业化分工 + 协同工作流
  ↓ 优势：角色专注、工具专用、质量有保障、可独立优化
  ↓ 结果：输出质量高，但系统复杂度增加
```

关键决策点：**何时引入多Agent系统？**

| 维度 | 单Agent够用 | 需要多Agent |
|------|------------|-------------|
| 任务复杂度 | 单一任务、步骤少 | 多步骤、多维度、有依赖关系 |
| 质量要求 | 可接受中等质量 | 需要专业级输出 |
| 工具调用 | 少量、类型相似 | 多种、类型差异大 |
| 迭代需求 | 一次性完成 | 需要多轮反馈修正 |
| 可维护性 | 简单、快速修改 | 需要独立演进各模块 |

**决策原则：如果一个任务可以被清晰地拆分为多个独立子任务，且每个子任务有不同的最优策略，那么多Agent架构值得引入。**

### 2.2 四大设计维度

多Agent系统的设计可以分解为四个核心维度：

```
          ┌─────────────┐
          │   角色定义    │
          │  (Who)      │
          └──────┬──────┘
                 │
    ┌────────────┼────────────┐
    │            │            │
┌───▼────┐ ┌────▼────┐ ┌────▼────┐
│通信拓扑 │ │任务分解  │ │结果聚合  │
│(How    │ │(What    │ │(Where   │
│Talk)   │ │Do)      │ │Go)      │
└────────┘ └─────────┘ └─────────┘
```

- **角色定义**：每个Agent是什么、负责什么、有什么约束
- **通信拓扑**：Agent之间如何传递信息（星型/总线/点对点）
- **任务分解**：复杂任务如何拆解为子任务（DAG/递归/动态）
- **结果聚合**：多个Agent的输出如何合并为最终结果

这四个维度的不同组合，决定了系统的整体架构风格。

## §3 Agent角色设计

### 3.1 角色定义模板

每个Agent角色需要明确定义四个要素：

```
┌─────────────────────────────────────────┐
│            Agent 角色定义模板              │
├─────────────────────────────────────────┤
│  📋 职责 (Responsibility)               │
│    → 这个Agent负责什么？边界在哪？        │
│                                         │
│  🔧 工具 (Tools)                        │
│    → 可以调用哪些工具？限制是什么？        │
│                                         │
│  💬 提示词 (System Prompt)              │
│    → 如何引导Agent的行为模式？            │
│                                         │
│  🚫 约束 (Constraints)                  │
│    → 不能做什么？输出格式要求？            │
└─────────────────────────────────────────┘
```

### 3.2 各角色详细设计

#### 研究员Agent (Researcher)

| 维度 | 内容 |
|------|------|
| 职责 | 根据研究主题进行信息检索，收集相关文献、数据、观点；对信息来源进行初步事实核查 |
| 工具 | Web搜索API、学术数据库API、网页内容提取器、事实核查数据库 |
| 提示词核心 | "你是专业研究助理。搜索时优先使用权威来源（学术论文 > 行业报告 > 新闻 > 博客）。每个信息必须标注来源URL和可信度评分。" |
| 约束 | 不做分析判断（留给分析师）、不写文章（留给写手）、单次检索不超过20条结果 |
| 输出格式 | JSON数组，每条包含：`{title, source, url, credibility_score, summary, key_data_points}` |

#### 分析师Agent (Analyst)

| 维度 | 内容 |
|------|------|
| 职责 | 对研究员收集的资料进行结构化分析，提取关键趋势、数据点、矛盾观点，形成分析框架 |
| 工具 | 数据处理库、图表生成器、统计分析工具 |
| 提示词核心 | "你是数据分析师。分析时遵循MECE原则（相互独立、完全穷尽）。识别数据中的趋势、异常和矛盾。输出时用结构化格式，每个结论都要有数据支撑。" |
| 约束 | 不编造数据、不确定的标注"待验证"、数据矛盾时明确指出 |
| 输出格式 | 结构化分析报告，包含：趋势摘要、数据洞察、观点对比、待验证问题 |

#### 写手Agent (Writer)

| 维度 | 内容 |
|------|------|
| 职责 | 基于分析师的输出，撰写结构清晰、逻辑严密、可读性强的研究报告 |
| 工具 | Markdown生成器、格式化工具、引用管理器 |
| 提示词核心 | "你是资深技术写手。写作遵循金字塔原理：结论先行，分层论证。每个段落有且只有一个核心观点。引用分析师提供的数据点，不要自行添加未经验证的信息。" |
| 约束 | 不添加分析师未提供的数据、不改变原始数据含义、遵循公司写作规范 |
| 输出格式 | 完整研究报告（Markdown），包含：摘要、引言、主体（分章节）、结论、参考文献 |

#### 审校Agent (Reviewer)

| 维度 | 内容 |
|------|------|
| 职责 | 对写手的输出进行全面质量审核，包括事实准确性、逻辑连贯性、数据一致性、语言规范性 |
| 工具 | 事实核查API、语法检查器、一致性检测器、评分系统 |
| 提示词核心 | "你是质量总监。审核标准：1）所有数据引用必须可在原文中找到出处；2）逻辑推理必须无跳跃；3）结论必须有充分支撑。发现严重问题时，有权否决并要求重写。" |
| 约束 | 必须给出具体修改意见、评分必须客观（基于标准而非偏好）、否决需要说明具体原因 |
| 输出格式 | `{pass: bool, score: 0-100, issues: [{type, location, severity, description, suggestion}]}` |

### 3.3 角色间的边界清晰度

角色边界模糊是多Agent系统最常见的设计缺陷。我们用「职责矩阵」来保证边界清晰：

| 任务 | Researcher | Analyst | Writer | Reviewer |
|------|:---------:|:-------:|:------:|:--------:|
| 信息检索 | ✅ 主导 | ❌ | ❌ | ❌ |
| 数据分析 | 📖 提供数据 | ✅ 主导 | ❌ | ❌ |
| 报告撰写 | ❌ | 📖 提供分析 | ✅ 主导 | ❌ |
| 质量审核 | ❌ | ❌ | ❌ | ✅ 主导 |
| 事实核查 | ✅ 初步核查 | 📖 标注存疑 | ❌ | ✅ 最终核查 |
| 结论形成 | ❌ | 📖 提供洞察 | 📖 撰写表述 | ✅ 审核验证 |

> ✅ = 主导责任　📖 = 提供输入　❌ = 不参与

## §4 通信机制实现

### 4.1 三种通信模式对比

多Agent系统的通信机制是架构设计中最关键的决策之一。我们对比了三种主流模式：

| 特性 | 消息总线 (Message Bus) | 共享记忆 (Shared Memory) | 直接通信 (Direct Communication) |
|------|----------------------|------------------------|-------------------------------|
| 架构 | 所有Agent通过消息队列通信 | Agent读写共享状态存储 | Agent之间点对点调用 |
| 耦合度 | 低（发布-订阅模式） | 中（共享数据结构） | 高（需要知道对方地址） |
| 扩展性 | ⭐⭐⭐ 最佳 | ⭐⭐ 一般 | ⭐ 最差 |
| 实现复杂度 | 中等 | 较低 | 低 |
| 调试难度 | 较高（异步） | 低（状态可查） | 中等 |
| 适合场景 | 大规模、异步任务 | 状态频繁共享的协作 | 小规模、同步交互 |
| 实际延迟 | 取决于队列 | 低（内存/Redis） | 低（直接调用） |
| 容错能力 | ⭐⭐⭐ 强 | ⭐⭐ 一般 | ⭐ 弱 |

### 4.2 我们的选择：混合架构

在实际项目中，我们采用了**混合通信架构**——不同阶段使用不同模式：

```
┌─────────────────────────────────────────────────┐
│                  混合通信架构                      │
│                                                  │
│  阶段1：任务分发    →  消息总线 (异步分发)          │
│  ┌──────┐    ┌─────────┐    ┌──────┐            │
│  │编排器 │───▶│消息队列  │───▶│各Agent│            │
│  └──────┘    └─────────┘    └──────┘            │
│                                                  │
│  阶段2：协作执行    →  共享记忆 (状态同步)          │
│  ┌──────┐    ┌─────────┐    ┌──────┐            │
│  │研究员 │◀──▶│共享状态  │◀──▶│分析师│            │
│  └──────┘    └─────────┘    └──────┘            │
│                                                  │
│  阶段3：审核反馈    →  直接通信 (同步交互)          │
│  ┌──────┐    ┌─────────┐    ┌──────┐            │
│  │写手  │◀──▶│  审校    │◀──▶│重写  │            │
│  └──────┘    └─────────┘    └──────┘            │
└─────────────────────────────────────────────────┘
```

### 4.3 共享记忆层设计

共享记忆是多Agent协作的核心基础设施。我们设计了三层记忆结构：

```
┌─────────────────────────────────────────┐
│            三层记忆结构                    │
├─────────────────────────────────────────┤
│                                         │
│  L1: 工作记忆 (Working Memory)           │
│  ├── 当前任务的中间状态                   │
│  ├── 各Agent的当前输出                    │
│  └── 生命周期：单次任务                   │
│                                         │
│  L2: 对话记忆 (Conversation Memory)      │
│  ├── Agent间的交互历史                   │
│  ├── 审校反馈和修改记录                   │
│  └── 生命周期：单次任务（可回溯）          │
│                                         │
│  L3: 知识记忆 (Knowledge Memory)         │
│  ├── 历史研究报告                        │
│  ├── 常用知识库（领域术语、模板）          │
│  └── 生命周期：持久化                     │
│                                         │
└─────────────────────────────────────────┘
```

### 4.4 消息格式标准化

Agent之间的通信需要统一的消息格式：

```python
# 统一消息结构（伪代码，展示架构思想）
Message = {
    "message_id": "uuid",
    "sender": "researcher",
    "receiver": "analyst",          # 或 "broadcast"
    "type": "data交付|请求|反馈|否决",
    "payload": { ... },             # 具体数据
    "metadata": {
        "task_id": "research_001",
        "step": 2,
        "timestamp": "2026-05-31T10:00:00Z"
    }
}
```

## §5 任务分解与调度

### 5.1 任务分解策略

复杂研究任务的分解遵循**DAG（有向无环图）**模型：

```
用户输入：「2026年大语言模型发展趋势」
                    │
            ┌───────▼───────┐
            │  编排器：任务分解 │
            └───────┬───────┘
                    │
    ┌───────────────┼───────────────┐
    │               │               │
    ▼               ▼               ▼
┌────────┐   ┌────────┐   ┌────────┐
│子任务1  │   │子任务2  │   │子任务3  │
│文献检索  │   │行业报告 │   │专利分析 │
│(Researcher)│ │(Researcher)│ │(Researcher)│
└────┬───┘   └────┬───┘   └────┬───┘
     │            │            │
     └────────────┼────────────┘
                  │
            ┌─────▼─────┐
            │ 子任务4     │
            │ 数据综合分析 │
            │ (Analyst)  │
            └─────┬─────┘
                  │
            ┌─────▼─────┐
            │ 子任务5     │
            │ 报告撰写    │
            │ (Writer)   │
            └─────┬─────┘
                  │
            ┌─────▼─────┐
            │ 子任务6     │
            │ 质量审校    │
            │ (Reviewer) │
            └─────┬─────┘
                  │
            ┌─────▼─────┐
            │ 最终输出    │
            └───────────┘
```

### 5.2 调度器设计

调度器的核心职责是决定「何时执行什么、由谁执行、依赖是否满足」：

```
调度决策流程：

1. 解析任务DAG → 拓扑排序
2. 检查就绪条件 → 依赖任务是否完成？
3. 分配Agent → 根据角色匹配
4. 执行监控 → 超时/失败处理
5. 结果收集 → 写入共享记忆
6. 触发下游 → 通知依赖任务就绪
```

### 5.3 并行与串行决策

并非所有子任务都需要串行执行。调度器需要判断：

| 子任务组合 | 执行模式 | 原因 |
|-----------|---------|------|
| 文献检索 + 行业报告 + 专利分析 | 并行 | 三个检索任务互不依赖 |
| 数据综合分析 | 依赖上述三个 | 需要所有检索结果 |
| 报告撰写 | 依赖分析 | 需要分析结论 |
| 质量审校 | 依赖撰写 | 需要完整报告 |
| 审校不通过 → 重写 | 条件触发 | 仅在否决时执行 |

### 5.4 动态任务调整

静态DAG在复杂场景下不够灵活。我们引入了**动态任务调整机制**：

- **任务分裂**：如果某个子任务过于复杂（比如检索范围太广），自动拆分为更细粒度的子任务
- **任务合并**：如果两个子任务高度相关（比如两个相似主题的检索），合并以减少冗余
- **任务注入**：分析师发现需要额外信息时，动态向研究员发起新的检索任务

## §6 冲突解决与质量控制

### 6.1 多Agent系统的质量挑战

多Agent系统相比单Agent，引入了新的质量问题：

| 质量问题 | 表现 | 解决方案 |
|---------|------|---------|
| 信息不一致 | 研究员A和B找到矛盾数据 | 冲突检测 + 优先级裁决 |
| 上下文丢失 | Agent间传递时丢失关键信息 | 结构化消息 + 信息冗余 |
| 角色越界 | 分析师自己加了未验证数据 | 职责边界约束 + 审校检查 |
| 质量退化 | 多轮修改后质量反而下降 | 评分监控 + 回退机制 |

### 6.2 审校Agent的否决权机制

审校Agent是系统的质量门禁，拥有**有条件的否决权**：

```
审校流程：

写手输出报告
      │
      ▼
┌─────────────┐
│  审校Agent   │
│  评分 < 60?  │──── 是 ───▶ 否决 → 要求重写
└──────┬──────┘                │
       │ 否                     │
       ▼                        ▼
  评分 >= 60              重写（最多3次）
       │                        │
       ▼                        ▼
  有严重问题? ─── 是 ───▶ 部分否决 → 针对性修改
       │ 否
       ▼
  通过 → 交付用户
```

否决权的约束（防止无限循环）：

1. **最多否决3次**：超过3次后强制升级为人工审核
2. **否决理由必须具体**：不能只说"质量不行"，必须指出具体问题和位置
3. **评分趋势监控**：如果连续3次评分都在60-70之间波动，触发系统告警
4. **版本控制**：每次修改都保留历史版本，可回退

### 6.3 一致性检查机制

Agent间的信息一致性是多Agent系统的独特挑战：

```
一致性检查维度：

1. 数据一致性
   Researcher说「2025年市场规模100亿」
   Analyst引用「市场规模100亿」
   Writer写「市场规模100亿」
   → 三方一致 ✅

2. 结论一致性
   Analyst结论：「趋势向上」
   Writer结论：「趋势平稳」
   → 冲突！触发审校Agent裁决 ⚠️

3. 引用一致性
   Writer引用的每个数据点，必须能在Researcher的原始输出中找到出处
   → 引用链完整性检查 🔍
```

### 6.4 质量评分体系

```
最终报告质量评分（满分100）：

├── 事实准确性 (30分)
│   ├── 数据引用有出处：15分
│   └── 无虚构信息：15分
│
├── 逻辑连贯性 (25分)
│   ├── 论点有论据支撑：15分
│   └── 段落间逻辑顺畅：10分
│
├── 分析深度 (25分)
│   ├── 趋势洞察质量：15分
│   └── 观点多样性：10分
│
└── 表达质量 (20分)
    ├── 语言流畅度：10分
    └── 结构清晰度：10分

通过标准：总分 >= 75，且无单项低于60
```

## §7 生产化改造

### 7.1 从Demo到生产的关键差距

很多人在做多Agent系统时，Demo跑通就认为完成了。实际上，Demo和生产之间有巨大的鸿沟：

| 维度 | Demo阶段 | 生产阶段 |
|------|---------|---------|
| 错误处理 | 简单try-catch | 全链路降级 + 自愈 |
| 日志 | print语句 | 结构化日志 + 分布式追踪 |
| 监控 | 看终端输出 | 指标采集 + 告警 + 仪表盘 |
| 成本 | 不考虑 | Token预算 + 模型路由 |

| 安全 | 无 | 输入校验 + 权限控制 |
| 测试 | 手动测试 | 自动化测试 + 回归 |

### 7.4 降级策略

当某个Agent不可用时，系统不能直接挂掉：

| 降级场景 | 策略 | 用户感知 |
|---------|------|---------|
| Researcher超时 | 使用缓存的历史检索结果 | 报告可能不够新 |
| Analyst不可用 | Writer直接基于原始资料写作 | 分析深度降低 |
| Writer超时 | 切换到轻量模型生成 | 文字质量略降 |
| Reviewer不可用 | 跳过审校，直接输出 | 无质量保证 |
| 所有Agent不可用 | 返回"系统繁忙"提示 | 明确告知 |

### 7.5 成本控制

多Agent系统的成本控制比单Agent复杂得多：

```
成本控制策略：

1. 模型路由 (Model Routing)
   ├── 简单任务 → 轻量模型 (GPT-4o-mini, Claude Haiku)
   ├── 中等任务 → 中等模型 (GPT-4o, Claude Sonnet)
   └── 关键任务 → 顶级模型 (Claude Opus, GPT-4.5)

2. Token预算管理
   ├── 每个Agent分配Token上限
   ├── 超限时自动切换到轻量模型
   └── 总预算告警阈值

3. 缓存复用
   ├── 相似研究主题 → 复用历史检索结果
   ├── 共同知识 → 缓存到知识库
   └── 模板化内容 → 减少重复生成

4. 并行优化
   ├── 独立子任务并行执行 → 减少总时间
   └── 批量API调用 → 降低请求开销
```

## §8 性能优化

### 8.1 并行执行优化

多Agent系统最大的性能优势来自并行化。我们对比了串行和并行的执行效率：

| 任务流程 | 串行耗时 | 并行耗时 | 提升 |
|---------|---------|---------|------|
| 3个检索任务 | 90s (30s×3) | 35s (max 30s + 调度开销) | 61% |
| 分析 → 撰写 → 审校 | 180s (60+60+60) | 180s (必须串行) | 0% |
| **整体任务** | **270s** | **215s** | **20%** |

**关键洞察：并行化的收益取决于任务DAG中的关键路径长度。**

### 8.2 缓存策略

```
三层缓存架构：

┌─────────────────────────────────────┐
│  L1: Agent内部缓存                    │
│  ├── 短期结果缓存 (TTL: 5min)        │
│  └── 用途：避免重复调用相同工具       │
├─────────────────────────────────────┤
│  L2: 任务级缓存                       │
│  ├── 检索结果缓存 (TTL: 1h)          │
│  ├── 分析中间结果缓存 (TTL: 30min)   │
│  └── 用途：相似任务复用               │
├─────────────────────────────────────┤
│  L3: 知识库缓存                       │
│  ├── 历史报告 (永久)                  │
│  ├── 领域知识 (每周更新)              │
│  └── 用途：长期知识复用               │
└─────────────────────────────────────┘
```

### 8.3 模型路由策略

不同Agent对模型的要求不同，智能路由可以大幅降低成本：

| Agent | 任务类型 | 推荐模型 | Token成本比 |
|-------|---------|---------|------------|
| Researcher | 信息检索 + 格式化 | GPT-4o-mini | 1x |
| Analyst | 结构化分析 | Claude Sonnet | 3x |
| Writer | 创造性写作 | GPT-4o | 5x |
| Reviewer | 批判性审核 | Claude Opus | 10x |

路由决策逻辑：

```
if 任务复杂度 == "简单":
    使用轻量模型
elif 任务 == "关键质量节点":  # 审校、最终输出
    使用顶级模型
elif 任务 == "可重试":
    先用轻量模型，失败/质量不达标再升级
else:
    使用中等模型
```

## §9 面试题：如何设计一个百万用户的多Agent平台

### 9.1 题目

> 设计一个支持百万用户的多Agent平台，用户可以通过自然语言描述需求，系统自动调度多个Agent协作完成任务。请从架构、扩展性、成本、可靠性四个角度回答。

### 9.2 参考答案框架

#### 架构层

```
用户请求流：

百万用户 → CDN/负载均衡 → API网关 → 任务队列 → 调度器 → Agent集群 → 结果缓存 → 推送

关键技术选型：
├── 任务队列：Kafka / Redis Stream（支持百万级吞吐）
├── 调度器：分布式调度（一致性哈希分配任务）
├── Agent集群：K8s + HPA（自动扩缩容）
├── 共享记忆：Redis Cluster + PostgreSQL（热/冷数据分离）
└── 结果推送：WebSocket + 长轮询（实时进度更新）
```

#### 扩展性

| 扩展点 | 方案 | 挑战 |
|-------|------|------|
| 用户量扩展 | 无状态API + 有状态调度 | 任务队列的分区策略 |
| Agent类型扩展 | 插件化架构，动态注册 | 工具冲突、权限隔离 |
| 地域扩展 | 多区域部署 + 数据同步 | 跨区域一致性、延迟 |
| 模型扩展 | 模型路由层抽象 | 不同模型的兼容性适配 |

#### 成本控制

```
百万用户成本估算（假设日活10万，平均3次任务/天）：

日任务量：30万次
平均Token/任务：8,000 tokens
总Token消耗：2.4B tokens/天

成本优化策略：
├── 缓存命中率目标：60%（实际API调用：12万次/天）
├── 模型路由：70%轻量模型 + 20%中等 + 10%顶级
├── 预估月成本：$15,000 - $25,000（优化前约$50,000）
└── 关键：缓存 + 路由 可降低50%成本
```

#### 可靠性

| 故障场景 | 影响范围 | 恢复策略 |
|---------|---------|---------|
| 单个Agent崩溃 | 该任务 | 自动重启 + 任务重试（最多3次） |
| 消息队列故障 | 所有新任务 | 切换到备份队列（双写策略） |
| 共享记忆故障 | 任务状态丢失 | 本地快照 + 异步恢复 |
| 模型API限流 | 部分任务延迟 | 降级到备用模型 + 队列排队 |
| 区域故障 | 该区域用户 | 流量切换到健康区域 |

### 9.3 加分项

面试时可以补充以下深度见解：

1. **A/B测试框架**：不同Agent配置对用户满意度的影响
2. **用户反馈闭环**：用户对报告质量的评分如何反哺Agent优化
3. **冷启动问题**：新用户没有历史数据，如何保证初始体验
4. **安全防护**：恶意用户通过Agent注入攻击（Prompt Injection in Multi-Agent）

## §10 总结与实战建议

### 10.1 核心决策清单

构建多Agent系统前，先回答这5个问题：

| # | 问题 | 如果答案是「否」 |
|---|------|----------------|
| 1 | 任务是否可以清晰拆分为独立子任务？ | 考虑单Agent + 工具调用 |
| 2 | 不同子任务是否需要不同的最优策略？ | 可能不需要多Agent |
| 3 | 是否有明确的质量要求需要多角色把关？ | 单Agent可能足够 |
| 4 | 系统复杂度的增加是否被质量提升抵消？ | 权衡ROI |
| 5 | 是否有足够的基础设施支撑（队列、存储、监控）？ | 先建设基础设施 |

### 10.2 常见陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| 过度设计 | 3个Agent能解决的问题用了10个 | 从最小可行架构开始 |
| 角色模糊 | Agent之间职责重叠 | 用职责矩阵明确边界 |
| 通信瓶颈 | 所有Agent都向中心节点汇报 | 采用分布式通信 |
| 无限循环 | Agent互相否决导致死循环 | 设置最大重试次数 |
| 成本失控 | 不考虑Token消耗 | 预算机制 + 模型路由 |

### 10.3 演进路径

```
Phase 1: MVP（2-3周）
├── 2个Agent（研究员 + 写手）
├── 简单串行流程
└── 验证核心价值

Phase 2: 完善（4-6周）
├── 4个Agent完整角色
├── 共享记忆层
├── 审校机制
└── 基础监控

Phase 3: 生产化（4-6周）
├── 降级策略
├── 成本控制
├── 完整监控告警
└── 自动化测试

Phase 4: 规模化（持续）
├── 并行优化
├── 缓存策略
├── A/B测试
└── 用户反馈闭环
```
