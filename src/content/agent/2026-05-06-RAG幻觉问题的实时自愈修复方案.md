# RAG幻觉问题的实时自愈修复方案

## 前言

在开发RAG（检索增强生成）系统的过程中，我们发现了一个严重问题：即使系统检索到了正确的文档，大语言模型（LLM）仍可能生成与检索内容完全矛盾的答案。这种现象被称为"幻觉"，是RAG系统在生产环境中最头疼的问题之一。

经过数月的深入研究和实践，我们识别出了五种常见的失败模式，并构建了一个完整的检测、评分、修复和路由系统。这个系统不仅能够实时检测LLM生成的幻觉内容，还能自动修复大多数问题，为生产环境提供了可靠的保障。

## RAG幻觉的五种失败模式

### 1. 数值矛盾

LLM在处理具体数字时容易出现错误。例如，文档中明确写明"公司成立于2015年"，但LLM可能回答"成立于2018年"。这种数值错误在金融、医疗等需要精确数据的领域是致命的。

### 2. 虚假引用

模型会编造文档中不存在的引用。比如文档提到了产品A和B的功能，LLM却声称"根据文档，产品C也具备此功能"，但实际上文档中从未出现过产品C。

### 3. 否定翻转

这是最危险的错误类型之一。文档中说"此方法不支持XYZ功能"，LLM却回答"此方法支持XYZ功能"，完全颠倒了原意。在合规性要求高的场景下，这种错误可能造成严重后果。

### 4. 答案漂移

随着上下文增长，LLM逐渐偏离检索到的内容，开始基于自身训练数据而非检索文档生成答案。这种漂移是渐进的，早期答案可能还准确，但后期答案越来越不可靠。

### 5. 自信但未基于上下文的回答

LLM用非常自信的语气回答问题，但答案完全未基于提供的上下文，而是基于训练数据或常识。这种"一本正经胡说八道"的情况最难被用户识别。

## 自愈系统的核心架构

我们的自愈系统包含五大模块，协同工作形成完整的幻觉防护网。

### 1. 置信度评分模块

检测语言中的过度自信信号，使用正则表达式匹配高置信度词汇（如"definitely"、"certainly"）和低置信度词汇（如"might"、"possibly"），计算一个0-1的置信度分数。

```python
def score(self, answer: str) -> float:
    al    = answer.lower()
    words = len(answer.split()) or 1
    high  = sum(len(p.findall(al)) for p in self._HIGH_RE)
    low   = sum(len(p.findall(al)) for p in self._LOW_RE)
    return max(0.0, min(1.0,
        0.5 + min(high / (words / 10), 1.0) * 0.5
            - min(low  / (words / 10), 1.0) * 0.5
    ))
```

### 2. 忠实度评分模块

检查答案与检索上下文的关键词重叠度，评估答案是否真正基于提供的上下文生成。通过TF-IDF或简单的词频统计，计算答案中来自上下文的词的占比。

### 3. 矛盾检测模块

检测三种类型的矛盾：
- **数值矛盾**：比较答案和上下文中的数字、日期
- **否定矛盾**：检测否定词使用是否一致
- **时间矛盾**：检查时间线是否合理

### 4. 实体幻觉检测模块

使用spaCy的命名实体识别（NER）功能，提取答案中的实体（人名、地名、组织名等），然后检查这些实体是否存在于检索上下文中。如果答案中出现了上下文中没有的实体，标记为幻觉。

### 5. 答案漂移监控模块

使用SQLite持久化存储历史问题和答案，监控答案质量随时间的变化趋势。当检测到质量持续下降时，触发漂移警告。

## 三种自动修复策略

当检测到幻觉时，系统会根据错误类型选择合适的修复策略。

### 策略1：矛盾修复

直接替换错误数值和规范术语。适用于明确的数值错误和术语不一致问题。

```python
# 示例：修复数值错误
context = "公司成立于2015年，目前有150名员工"
answer = "公司成立于2018年"
fixed = replace_numbers(answer, extract_numbers(context))
# 结果："公司成立于2015年"
```

### 策略2：实体清理

移除包含幻觉实体的句子。当无法确定正确实体时，宁可删除也不保留错误信息。

```python
# 示例：移除幻觉实体
answer = "产品A、B和C都支持此功能"
context_entities = ["产品A", "产品B"]
cleaned = remove_sentences_with_unknown_entities(answer, context_entities)
# 结果："产品A和B都支持此功能"
```

### 策略3：基于上下文重写

从最高排名的上下文句子重建答案。当错误严重无法简单修复时，从最相关的上下文片段重新生成答案。

## 质量评分与路由系统

修复完成后，系统使用加权公式计算最终质量分数：

- **忠实度**：40% - 答案基于上下文的程度
- **一致性**：30% - 与上下文无矛盾
- **置信度**：20% - 语言的适度自信
- **延迟**：10% - 响应时间可接受

根据分数将答案路由到四个交付层级：

| 层级 | 分数范围 | 处理方式 |
|------|---------|---------|
| ACCEPT | ≥ 0.8 | 直接交付LLM答案 |
| HEALED_ACCEPT | ≥ 0.6 | 交付修复后的答案 |
| FALLBACK | ≥ 0.4 | 使用预设的兜底回复 |
| DISCARD | < 0.4 | 丢弃答案，触发人工审核 |

## 生产环境集成示例

系统支持同步和异步两种调用方式，可以无缝集成到现有的RAG流程中。

```python
# 基本使用
from hallucination_detector import (
    HallucinationDetector, HallucinationHealer,
    DetectorConfig, QualityScore
)

config   = DetectorConfig(db_path="drift.db", log_flagged=True)
detector = HallucinationDetector(config)
healer   = HallucinationHealer(detector)

# 在交付前检查每个LLM答案
report = detector.inspect(question, context_chunks, llm_answer)
score  = QualityScore.compute(report)

if score.routing == "accept":
    return llm_answer

# 尝试修复
result = healer.heal(question, context_chunks, llm_answer, report)
score  = QualityScore.compute(report, healing_result=result)

if score.routing == "healed_accept":
    return result.healed_answer

return fallback_response
```

## 性能与配置

系统在Python 3.12上测试通过：

- **纯正则表达式路径**：延迟低于10ms，适合对性能要求极高的场景
- **spaCy路径**：延迟低于50ms，实体识别更准确，适合需要高准确率的场景

对于法律、医疗等高风险领域，可以启用严格模式：

```python
config = DetectorConfig(
    db_path="drift.db",
    log_flagged=True,
    strict_mode=True,  # 更严格的评分标准
    min_accept_score=0.85  # 提高接受阈值
)
```

## 总结

RAG系统的幻觉问题是一个复杂但并非不可解决的挑战。通过构建多层次的检测机制、智能的修复策略和合理的路由系统，我们可以显著提升RAG系统的可靠性。

这个自愈层的优势在于：
1. **纯Python实现**：无需外部API或LLM评测器，部署简单
2. **低延迟**：10-50ms的检测延迟，适合实时场景
3. **可配置**：支持多种模式和严格程度调整
4. **可扩展**：易于添加新的检测和修复规则
