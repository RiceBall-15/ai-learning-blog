# Superpowers：给Coding Agent装上系统化开发方法论

> **来源**：[obra/superpowers](https://github.com/obra/superpowers) | Stars: 190,052 | 2025-10-09
>
> **核心定位**：不是另一个Agent，而是让现有Coding Agent学会系统化开发的"方法论插件"

## 问题：Agent为什么总写出"能跑但不可维护"的代码？

你让Claude Code实现一个功能，它确实写出来了。测试？没有。计划？没有。你追问"为什么这么写"，它给不出理由。

这不是模型能力问题，而是**流程缺失**：

| 问题 | 根因 | 后果 |
|------|------|------|
| **无脑写代码** | 拿到需求就直接实现 | 方向错了才返工 |
| **不写测试** | 没有TDD约束 | 无法验证正确性 |
| **无系统化** | 每次都是即兴发挥 | 质量不可控 |
| **无审查** | 写完就结束 | 技术债累积 |

Superpowers 的哲学很直接：**优秀的软件开发需要方法论，Agent也不例外**。

## 架构：纯Markdown的技能系统

Superpowers 没有Python代码、没有运行时、没有服务器——它是纯Shell/Markdown的技能文件集合，通过插件系统安装到你的Coding Agent中：

```
~/.claude/
└── plugins/
    └── superpowers/
        ├── SKILL.md              # 主技能入口
        ├── brainstorming.md       # 需求澄清
        ├── writing-plans.md       # 实现计划
        ├── test-driven-development.md  # TDD
        ├── systematic-debugging.md     # 调试方法论
        ├── requesting-code-review.md   # 代码审查
        └── ...                   # 更多技能
```

**为什么这样设计？**
- 零依赖：不需要pip install，不需要npm install
- 零延迟：没有HTTP请求，没有MCP调用
- 可读性：每个技能就是一个Markdown文件，任何人可以审查和修改
- 跨平台：只要Agent支持加载技能文件就能用

## 核心：7步闭环工作流

这是 Superpowers 的灵魂。它强制Agent走完一个完整的软件开发流程：

```
 用户输入需求
      │
      ▼
┌─────────────────────────────────────────────────────────┐
│ Step 1: 🧠 Brainstorming（苏格拉底式需求澄清）           │
│                                                         │
│   Agent 不直接写代码，而是先问你一系列问题：               │
│   - 这个功能的核心用户是谁？                             │
│   - 最重要的使用场景是什么？                             │
│   - 有哪些边界情况需要考虑？                             │
│   - 性能要求是什么？                                     │
│   - 哪些是"必须有"，哪些是"最好有"？                     │
│                                                         │
│   ★ 关键：Agent 会挑战你的假设，而不是盲目执行           │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 2: 🔀 Using Git Worktrees（隔离工作区）             │
│                                                         │
│   每个功能在独立的worktree中开发：                        │
│   git worktree add ../project-feature-x feature-x       │
│                                                         │
│   ★ 好处：                                              │
│   - 主分支永远干净                                       │
│   - 多个功能可并行开发                                   │
│   - 失败时直接删除worktree，不影响主分支                 │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 3: 📋 Writing Plans（2-5分钟粒度的实现计划）        │
│                                                         │
│   Agent 将任务拆解为多个2-5分钟的独立步骤：               │
│                                                         │
│   ┌────────────────────────────────────┐                │
│   │ Plan: User Authentication          │                │
│   ├────────────────────────────────────┤                │
│   │ 1. 创建User模型 (3min)             │                │
│   │ 2. 实现密码哈希 (2min)             │                │
│   │ 3. 创建登录/注册API (5min)         │                │
│   │ 4. 添加JWT token生成 (3min)        │                │
│   │ 5. 编写集成测试 (5min)             │                │
│   │ 6. 添加错误处理 (3min)             │                │
│   └────────────────────────────────────┘                │
│                                                         │
│   ★ 关键规则：                                           │
│   - 每步独立可测试                                       │
│   - 复杂步骤继续拆分                                     │
│   - 不跳过任何步骤                                       │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 4: 🤖 Subagent-Driven Development                  │
│         （子Agent并行开发 + 两阶段审查）                  │
│                                                         │
│   调度Agent（Orchestrator）将计划分配给子Agent：          │
│                                                         │
│   调度Agent                                              │
│     ├── Sub-Agent 1: 实现步骤1-2                        │
│     ├── Sub-Agent 2: 实现步骤3-4                        │
│     └── Sub-Agent 3: 实现步骤5-6                        │
│                                                         │
│   两阶段审查：                                           │
│   Stage 1: 子Agent完成 → 调度Agent审查代码质量           │
│   Stage 2: 所有子Agent完成 → 整体集成审查               │
│                                                         │
│   ★ 并行 + 审查 = 速度与质量兼得                        │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 5: 🔴🟢🔵 Test-Driven Development（强制TDD）        │
│                                                         │
│   严格的RED-GREEN-REFACTOR循环：                        │
│                                                         │
│   ┌─────┐    ┌─────┐    ┌──────┐                       │
│   │ RED │ ──►│GREEN│ ──►│REFACTOR                      │
│   └─────┘    └─────┘    └──────┘                       │
│   写失败测试   写最少代码   重构优化                     │
│   确认失败     让测试通过   保持通过                     │
│                                                         │
│   ★ 规则：                                              │
│   - 不允许先写实现再补测试                               │
│   - 每个功能至少一个失败测试起点                         │
│   - 重构时必须保证所有测试仍然通过                       │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 6: 🔍 Requesting Code Review（自动代码审查）        │
│                                                         │
│   任务完成后，Agent自动执行审查：                        │
│   - 安全扫描：硬编码密钥、SQL注入、XSS漏洞              │
│   - 代码质量：复杂度、命名规范、文档完整性              │
│   - 测试覆盖：边界情况、错误路径是否覆盖                │
│   - 性能审查：N+1查询、内存泄漏风险                     │
│                                                         │
│   ★ 不是人工审查的替代品，而是第一道过滤                │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│ Step 7: 🚢 Finishing a Development Branch               │
│         （合并/PR决策）                                  │
│                                                         │
│   Agent 帮你决定：                                       │
│   - 直接合并（小改动）还是创建PR（需要他人审查）         │
│   - PR描述自动生成                                       │
│   - 清理worktree                                         │
│   - 更新CHANGELOG（如果存在）                           │
└─────────────────────────────────────────────────────────┘
```

**这7步不是可选的**——Superpowers 会强制 Agent 遵循这个流程。即使你想跳过，Agent也会先完成前序步骤。

## 内置技能矩阵

Superpowers 提供了一套完整的软件开发技能：

| 技能 | 用途 | 触发时机 |
|------|------|---------|
| **brainstorming** | 苏格拉底式需求澄清 | 收到需求时 |
| **using-git-worktrees** | 隔离开发环境 | 开始新功能时 |
| **writing-plans** | 拆解实现计划 | Brainstorming完成后 |
| **subagent-driven-development** | 并行子Agent开发 | 计划拆解完成后 |
| **test-driven-development** | 强制TDD | 编写任何功能时 |
| **systematic-debugging** | 4阶段根因分析 | 遇到bug时 |
| **requesting-code-review** | 自动代码审查 | 任务完成时 |
| **receiving-code-review** | 处理审查反馈 | 收到审查意见时 |
| **dispatching-parallel-agents** | 并行任务分发 | 独立工作流存在时 |
| **simplifying-complexity** | 复杂度简化 | 方案过于复杂时 |
| **cross-check-systematic-reviews** | 交叉验证 | 关键决策时 |
| **asking-questions-instead-of-assuming** | 不假设，先问 | 信息不足时 |
| **writing-tests-for-existing-code** | 遗留代码测试 | 修改遗留代码时 |
| **refactoring-existing-code** | 安全重构 | 代码质量下降时 |
| **finishing-a-development-branch** | 分支清理 | PR合并后 |

### Systematic Debugging 的4阶段模型

这是 Superpowers 中调试方法论的核心：

```
┌─────────────────────────────────────────────────────┐
│            4阶段根因调试                              │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Phase 1: 🔍 Understand（理解问题）                  │
│  ─────────────────────────────────                  │
│  - 重现问题，确认触发条件                             │
│  - 收集错误信息、堆栈、日志                           │
│  - 确定影响范围                                      │
│  - ★ 关键：不急着看代码，先理解"什么是错的"          │
│                                                     │
│  Phase 2: 🧩 Hypothesize（形成假设）                 │
│  ─────────────────────────────────                  │
│  - 基于症状提出可能的根因                             │
│  - 排除不可能的原因                                  │
│  - 确定最可能的假设                                  │
│  - ★ 关键：一次只测试一个假设                        │
│                                                     │
│  Phase 3: 🔬 Test（验证假设）                        │
│  ─────────────────────────────────                  │
│  - 设计最小化测试来验证/排除假设                      │
│  - 添加临时日志或断点                                │
│  - 使用二分法定位                                    │
│  - ★ 关键：每次只改一个变量                          │
│                                                     │
│  Phase 4: ✅ Fix & Verify（修复并验证）               │
│  ─────────────────────────────────                  │
│  - 实施最小化修复                                    │
│  - 运行相关测试                                      │
│  - 验证修复不会引入新问题                             │
│  - ★ 关键：修复范围 = 问题范围，不多不少             │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**对比传统调试**：

| | 传统Agent | Superpowers Agent |
|--|----------|------------------|
| 看到报错 | 直接改代码猜测 | 先理解问题再行动 |
| 修复方式 | 大范围修改 | 最小化diff |
| 验证 | 改完就结束 | 必须跑测试 |
| 根因分析 | 经常只是修表象 | 强制4阶段 |

## 强制 TDD 的实际效果

Superpowers 的 TDD 不是建议，而是**强制执行**。让我们看一个实际场景：

```
用户: "添加用户头像上传功能"

传统Agent的响应：
  1. 直接写后端接口
  2. 直接写前端组件
  3. 结束
  （没有测试，不知道是否真的能用）

Superpowers Agent的响应：
  1. [Brainstorming] "上传的图片格式限制？大小限制？
     存储在哪里？需要裁剪吗？..."
  2. [Writing Plans] 拆解为5个2-5分钟步骤
  3. [RED] 先写失败测试：
     test_upload_avatar_returns_200()
     test_upload_avatar_validates_format()
     test_upload_avatar_validates_size()
     test_upload_avatar_saves_to_storage()
     test_upload_avatar_returns_url()
  4. [GREEN] 写最少代码让每个测试通过
  5. [REFACTOR] 优化代码结构
  6. [Code Review] 安全扫描 + 代码质量检查
  7. [Finish] 创建PR或直接合并
```

**强制TDD的价值**：
- **需求确认**：测试用例就是需求的可执行规范
- **信心保证**：改完代码，跑一下测试就知道是否break了什么
- **设计优化**：先写测试强制思考接口设计，代码自然更模块化
- **Bug预防**：边界情况在测试阶段就被发现，而不是生产环境

## 与 OpenSpace 的对比

| 维度 | **Superpowers** | **OpenSpace** |
|------|----------------|--------------|
| **核心理念** | 系统化开发流程 | 技能自动进化 |
| **适用场景** | 软件开发专用 | 通用Agent增强 |
| **进化能力** | ❌ 静态技能 | ✅ 自动进化 |
| **社区共享** | ❌ 不接受外部贡献 | ✅ 云端技能市场 |
| **部署复杂度** | 极低（一键安装） | 中等（MCP Server） |
| **依赖** | 纯Markdown/Shell | Python + LLM |
| **TDD** | ✅ 强制执行 | ❌ 无 |
| **子Agent调度** | ✅ 并行子Agent | ❌ 无 |
| **Token效率** | 一般（流程有开销） | 高（复用成功模式） |
| **记忆系统** | ❌ 无 | ❌ 无（靠社区） |

**互补而非替代**：
- Superpowers 解决"怎么开发"的流程问题
- OpenSpace 解决"技能怎么变好"的进化问题
- 两者可以同时使用：Superpowers 定义流程，OpenSpace 让流程自动优化

## 适合谁？

| 场景 | 适合程度 | 原因 |
|------|---------|------|
| 个人项目快速原型 | ⭐⭐ | 流程有开销，小项目可能过重 |
| 团队协作开发 | ⭐⭐⭐⭐⭐ | 强制TDD + 代码审查 = 代码质量保证 |
| 遗留代码修改 | ⭐⭐⭐⭐⭐ | Systematic Debugging + 先写测试再改 |
| 探索性编码 | ⭐⭐ | 计划驱动可能限制创意 |
| 生产级项目 | ⭐⭐⭐⭐⭐ | 流程就是质量的保障 |

## 哲学总结

Superpowers 的核心哲学可以归纳为三条：

1. **系统化优于即兴**：有流程的开发比拍脑袋的开发质量高10倍
2. **简化优于复杂**：如果方案太复杂，先简化再实现
3. **证据优于声明**：代码必须有测试证明正确性，不能"我觉得没问题"

> **一句话**：Superpowers 让你的Coding Agent从"能写代码的实习生"变成"遵循工程规范的工程师"。
