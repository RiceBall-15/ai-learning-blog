# Agent工具调用实战：从Function Calling到工具市场生态的完整指南

> 当Agent从"能聊天"进化到"能干活"，工具调用（Tool Calling）是那座关键的桥梁。本文从工程实战出发，完整梳理工具调用从原型到生产、从单工具到工具市场的全链路设计。

## §1 从硬编码到动态发现：工具调用的演进历程

### 1.1 四个阶段

工具调用的演进可以分为四个清晰的阶段，每个阶段解决不同的核心矛盾：

```
阶段一：硬编码 Prompt（2022）
├── 用自然语言在System Prompt里描述工具能力
├── 模型输出结构化JSON，解析后执行
├── 问题：上下文窗口被工具描述占满，无法扩展
│
阶段二：Function Calling（2023.06）
├── OpenAI推出function calling，工具描述与用户消息分离
├── 模型在专用通道返回函数名+参数，不再"伪装"成对话
├── 问题：每个Provider格式不同，工具绑定在会话级别
│
阶段三：Tool Protocol标准化（2024-2025）
├── MCP（Model Context Protocol）发布
├── 工具描述、执行、权限成为独立协议层
├── 问题：生态尚未统一，市场模式未成熟
│
阶段四：工具市场生态（2026）
├── 工具注册中心 + 动态发现 + 版本管理
├── 工具市场（Tool Store）商业模式涌现
├── 挑战：安全、信任、成本、治理
```

### 1.2 核心架构演进

早期的工具调用是**绑定式**的——工具定义写死在代码里，模型看到固定的工具列表。这带来了两个致命问题：

1. **扩展性瓶颈**：工具数量增长时，Prompt被工具描述占满，模型注意力分散
2. **运维噩梦**：每个工具的上下线都需要改代码、重新部署

现代架构演进到**发现式**——Agent运行时动态查询可用工具，按需加载，工具可以独立上下线。

```
┌─────────────────────────────────────────────────┐
│                 Agent Runtime                    │
│                                                  │
│  ┌──────────┐    ┌──────────────┐               │
│  │   LLM    │◄──►│ Tool Router  │               │
│  └──────────┘    └──────┬───────┘               │
│                         │                        │
│          ┌──────────────┼──────────────┐         │
│          ▼              ▼              ▼         │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ Tool Reg │  │ Tool Reg │  │ Tool Reg │      │
│  │ Center   │  │ Center   │  │ Center   │      │
│  └──────────┘  └──────────┘  └──────────┘      │
│     (本地)        (远程)       (市场)             │
└─────────────────────────────────────────────────┘
```

### 1.3 为什么工具调用比你想象的更难

很多人把工具调用理解为"模型输出JSON → 解析 → 执行"，但生产环境面临的真实挑战远不止此：

- **模型选错工具**：相似功能的工具怎么让模型选对的？
- **参数填充错误**：模型传了错误类型、缺少必填参数怎么办？
- **工具执行失败**：超时、网络错误、权限不足，Agent如何优雅降级？
- **工具结果过大**：返回了一个10MB的JSON，超出模型上下文怎么办？
- **并发冲突**：多个工具调用同时修改同一资源，如何保证一致性？
- **链式依赖**：工具B的结果是工具A的输入，如何处理中间态？

这些才是工具调用在生产中的真实痛点。

## §2 工具Schema设计模式：三家对比 + 最佳实践

### 2.1 三家Schema格式对比

| 维度 | OpenAI Function Calling | Anthropic Tool Use | Gemini Function Calling |
|------|------------------------|-------------------|------------------------|
| **描述字段名** | `function.description` | `tool.description` | `function_declarations[].description` |
| **参数格式** | JSON Schema（标准） | JSON Schema（标准） | JSON Schema（标准） |
| **多工具选择** | `tool_choice: "auto"/"none"/"required"/指定名` | `tool_choice: {"type": "auto"}` / 指定名 | `tool_config: {mode: "AUTO"}` |
| **并行调用** | 支持（返回多个tool_calls） | 支持（返回多个tool_use） | 支持（parallel_function_calling） |
| **工具类别** | 无 | 支持 `category: "search"/"tool"/"connector"` | 无 |
| **调用结果格式** | 单一JSON字符串 | 单一JSON（需手动wrap为content block） | JSON对象 |
| **强制调用工具** | `tool_choice: {"type": "function", "function": {"name": "xxx"}}` | `tool_choice: {"type": "tool", "name": "xxx"}` | `tool_config: {mode: "ANY"}` |
| **最大工具数** | ~128（实践建议<30） | ~128 | ~128 |

### 2.2 Schema设计的最佳实践

不管你用哪家Provider，Schema设计的好坏直接决定工具调用的成功率。以下是从实战中总结出的设计原则：

**原则一：描述是给模型看的，不是给人看的**

```json
{
  "name": "search_documents",
  "description": "搜索内部文档库。当用户询问公司政策、产品文档、技术规范、会议纪要时使用此工具。支持关键词搜索和语义搜索。"
}
```

好的描述要告诉模型**什么时候该用**这个工具，而不仅仅是它能做什么。

**原则二：参数命名要直觉化，避免缩写**

```json
// ❌ 差的命名
{"name": "q", "description": "str"}

// ✅ 好的命名
{"name": "query", "description": "搜索关键词", "type": "string"}
{"name": "max_results", "description": "最大返回条数，默认10，最大100", "type": "integer"}
```

**原则三：用`enum`约束离散选项，用`description`约束连续值**

```json
{
  "sort_by": {
    "type": "string",
    "enum": ["relevance", "date", "price", "rating"],
    "description": "排序方式"
  },
  "max_price": {
    "type": "number",
    "description": "最高价格（元），不设置则不限"
  }
}
```

**原则四：区分必填与可选，用`required`显式声明**

```json
{
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "搜索关键词"},
      "language": {"type": "string", "enum": ["zh", "en"], "description": "搜索语言，默认中文"},
      "date_range": {"type": "string", "description": "日期范围，格式YYYY-MM-DD~YYYY-MM-DD"}
    },
    "required": ["query"]
  }
}
```

**原则五：工具数量的黄金法则**

```
工具数量与模型选择准确率的关系（经验值）：

1-5个工具    → 选择准确率 ~98%
6-15个工具   → 选择准确率 ~95%
16-30个工具  → 选择准确率 ~88%
31-50个工具  → 选择准确率 ~78%
50+个工具    → 选择准确率急剧下降，需要路由机制
```

超过30个工具时，必须引入**工具路由层**（后文详述）。

### 3.2 工具描述的统一数据模型

无论工具来自内部开发、第三方市场还是MCP协议，都需要映射到统一的数据模型：

```python
@dataclass
class ToolDefinition:
    # 身份标识
    tool_id: str              # 全局唯一标识
    name: str                 # 工具名（模型可见）
    version: str              # 语义化版本号
    
    # 描述信息
    description: str          # 模型可见的描述
    category: str             # 分类：search/code/data/io
    tags: list[str]           # 标签
    
    # 接口定义
    input_schema: dict        # JSON Schema
    output_schema: dict       # 输出Schema（可选）
    
    # 运行时信息
    endpoint: str             # 执行端点
    runtime_type: str         # sync / async / streaming
    timeout_ms: int           # 超时时间
    
    # 元信息
    author: str               # 作者
    provider: str             # 提供者（internal / marketplace）
    auth_type: str            # 认证方式：none / api_key / oauth / mcp
    permissions: list[str]    # 需要的权限
```

### 3.3 版本管理策略

工具版本管理的核心挑战是：模型正在使用v1版本的工具，而你已经发布了v2，如何保证平滑过渡？

```
版本管理策略：

┌──────────────────────────────────────────────┐
│  策略一：语义化版本 + 向后兼容                   │
│  - 小版本（patch）：bug修复，不改变接口          │
│  - 中版本（minor）：新增参数，可选，向后兼容      │
│  - 大版本（major）：破坏性变更，需迁移           │
├──────────────────────────────────────────────┤
│  策略二：多版本并存 + 灰度切换                   │
│  - 保留最近3个版本的工具定义                     │
│  - 新会话默认用最新版本                         │
│  - 已有会话继续用旧版本                         │
│  - 通过流量百分比控制版本迁移                    │
├──────────────────────────────────────────────┤
│  策略三：工具兼容层                             │
│  - 新版本工具内嵌旧版本的参数适配器               │
│  - 签名检测自动路由到正确的执行逻辑              │
└──────────────────────────────────────────────┘
```

### 3.4 权限控制模型

工具权限控制不是简单的"能用/不能用"，而是需要细粒度的RBAC模型：

| 权限层级 | 示例 | 控制粒度 |
|---------|------|---------|
| **角色级** | admin / developer / user | 整个工具的访问控制 |
| **操作级** | read_only / read_write / execute | 同一工具的不同操作 |
| **参数级** | 只能查询，不能修改数据 | 参数值范围限制 |
| **环境级** | dev / staging / production | 不同环境可用工具不同 |
| **上下文级** | 对话场景 / 执行场景 | 同一用户不同场景权限不同 |

关键设计点：**权限应该在工具路由层拦截**，而不是在执行时才报错。Agent在规划阶段就应该知道哪些工具可用。

## §4 工具市场生态：从MCP协议到Tool Store

### 4.1 MCP协议解析

Anthropic提出的MCP（Model Context Protocol）是当前最成熟的工具互操作协议。它的核心思想是将工具能力从Agent内部解耦，通过标准化协议暴露给任何兼容的客户端。

MCP的核心架构：

```
┌──────────────┐          ┌──────────────┐
│  MCP Client  │  ──────► │  MCP Server  │
│  (Agent端)   │  标准协议  │  (工具端)    │
│              │          │              │
│  - 发现工具   │          │  - 暴露工具   │
│  - 调用工具   │          │  - 执行工具   │
│  - 获取结果   │          │  - 返回结果   │
│  - 权限协商   │          │  - 上传文件   │
└──────────────┘          └──────────────┘
```

MCP定义了三种核心能力：

| 能力 | 作用 | 典型场景 |
|------|------|---------|
| **Tools** | 定义可调用的函数 | 数据库查询、API调用 |
| **Resources** | 暴露可读取的数据源 | 文件系统、网页内容 |
| **Prompts** | 提供预定义的提示模板 | 代码审查模板、文档生成 |

MCP的传输层支持stdio（本地进程）和HTTP+SSE（远程服务），这让工具既可以本地运行，也可以部署为微服务。

### 4.3 工具市场的核心挑战

工具市场不仅仅是"上架 → 调用"这么简单，它面临几个深层挑战：

**信任问题**：Agent调用一个第三方工具，工具返回了恶意数据或错误结果，谁负责？
→ 解决方案：工具评分系统 + 执行结果验证 + 沙箱隔离

**兼容性问题**：工具A更新了接口，依赖它的Agent没有同步更新，导致调用失败？
→ 解决方案：版本锁定 + 向后兼容承诺 + 自动化兼容性测试

**发现效率问题**：1000+工具中，如何让Agent快速找到最合适的那一个？
→ 解决方案：语义索引 + 推荐系统 + 工具分类体系（后文详述）

**定价问题**：工具API的成本如何透明化？用户如何控制成本？
→ 解决方案：成本预估器 + 预算限制 + 按token计费

```
│ 工具筛选     │  根据权限、状态、版本过滤
│ (Filter)    │  过滤后：20个可用工具
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 工具排序     │  根据相关性评分、历史成功率、成本排序
│ (Rank)      │  Top 5候选工具
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 模型决策     │  LLM从Top 5中选择最合适的1-3个工具
│ (Decide)    │  生成工具调用计划
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 审批判断     │  是否需要人工审批？（敏感操作）
│ (Approve)   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 工具执行     │  并行/串行执行工具调用
│ (Execute)   │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 结果整合     │  合并工具结果，返回给LLM生成最终回答
│ (Integrate) │
└─────────────┘
```

### 5.3 工具选择器的核心设计

工具选择器是整个系统中最关键的组件。它的设计目标是：**用最少的Token，让模型做出最准确的选择。**

核心策略：

| 策略 | 描述 | 适用场景 |
|------|------|---------|
| **全量加载** | 所有工具描述放入上下文 | 工具<15个时 |
| **分类路由** | 先选分类，再选分类内的工具 | 工具15-50个 |
| **语义检索** | 基于用户意图向量检索最相关工具 | 工具50-500个 |
| **层级路由** | 多级路由：领域→子领域→具体工具 | 工具500+ |

当工具数量达到1000+时，推荐使用**三级路由**：

```
用户请求
    │
    ▼
┌──────────────────┐
│ Level 1: 领域路由  │  从~10个领域中选择
│ (Domain Router)   │  例如：代码、数据、通信、文件...
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ Level 2: 子类路由  │  从~50个子类中选择
│ (Category Router) │  例如：代码→Python、前端、DevOps...
└──────┬───────────┘
       │
       ▼
┌──────────────────┐
│ Level 3: 工具选择  │  从~20个具体工具中选择
│ (Tool Selector)   │  例如：Python→pandas、numpy、requests...
└──────────────────┘
```

## §6 工具调用安全：四层防护体系

### 6.1 安全架构总览

```
┌─────────────────────────────────────────────────┐
│                 安全防护四层架构                    │

│  │  - 合规报告                               │    │

│  └─────────────────────────────────────────┘    │
│  ┌─────────────────────────────────────────┐    │
│  │  Layer 3: 速率限制 (Rate Limiting)       │    │
│  │  - 工具级别限流                           │    │

└─────────────────────────────────────────────────┘
```

### 6.2 沙箱执行：为什么需要，怎么做

沙箱执行的核心原因是：**Agent调用的工具，尤其是代码执行类工具，不应该能影响主系统。**

沙箱执行的典型方案对比：

| 方案 | 隔离级别 | 启动时间 | 资源开销 | 适用场景 |
|------|---------|---------|---------|---------|
| **进程级** | OS进程隔离 | 毫秒级 | 低 | 简单计算、数据处理 |
| **容器级** | Docker/container | 秒级 | 中 | 代码执行、文件操作 |
| **VM级** | 完整虚拟机 | 十秒级 | 高 | 高风险代码、不可信工具 |
| **WASM级** | WebAssembly沙箱 | 毫秒级 | 极低 | 计算密集型、需极致隔离 |

生产环境推荐**混合策略**：低风险工具用进程级，代码执行用容器级，不可信的第三方工具用VM级。

### 6.3 审批机制设计

```
风险等级判定矩阵：

┌──────────────┬──────────────┬──────────────┬──────────────┐
│              │  读取操作     │  计算操作     │  写入操作     │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 内部工具      │   无审批      │   无审批      │  简单确认     │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 已认证第三方  │   无审批      │  简单确认     │  人工审批     │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 未认证第三方  │  简单确认     │  人工审批     │  人工审批     │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

审批机制的关键设计原则：

1. **审批结果可缓存**：同一用户的同一工具调用，在一定时间内不需要重复审批
2. **审批可撤销**：执行中发现问题，可以随时撤销
3. **审批带上下文**：审批人看到的是完整的调用意图，不是孤立的工具名
4. **自动升级**：低风险操作累积到一定量级后，自动升级为人工审批

### 6.4 速率限制策略

速率限制不是简单的QPS控制，需要多维度的限流策略：

- **工具维度**：每个工具独立的调用频率限制
- **用户维度**：每个用户的总调用次数限制
- **会话维度**：每个对话的工具调用轮次限制
- **成本维度**：每次调用的成本预估，累计成本超阈值触发限制
- **时间窗口**：滑动窗口限流 + 突发容量

### 6.5 审计日志设计

审计日志不仅是"记录调用了什么"，更要记录决策过程：

```yaml
audit_entry:
  trace_id: "tr-abc-123"
  timestamp: "2026-05-31T10:30:00Z"
  
  # 请求上下文
  user_id: "user-001"
  session_id: "sess-xyz"
  conversation_id: "conv-789"
  
  # 工具调用信息
  tool_id: "tool-search-docs-v2.1"
  tool_name: "search_documents"
  input_params:
    query: "Q3营收报告"
    max_results: 5

  # 决策链路
  decision_path:
    - step: "intent_analysis"
      result: "用户需要查找财务文档"

    - step: "tool_selection"
      selected_tools: ["search_documents"]
      selection_reason: "用户明确需要搜索文档"
  
  # 执行信息
  execution:
    duration_ms: 342
    status: "success"
    sandbox: "container-pool-3"
    cost_cents: 0.02
```

## §7 成本优化：工具调用缓存/结果复用/模型路由

### 7.1 工具调用的成本构成

一次完整的工具调用，成本不仅来自API调用本身：

```
总成本 = 模型推理成本 + 工具执行成本 + 网络传输成本 + 缓存存储成本

其中：
- 模型推理成本：约占 30-50%（选择工具 + 处理结果）
- 工具执行成本：约占 20-40%（第三方API调用）
- 网络传输成本：约占 5-15%（工具结果返回）
- 缓存存储成本：约占 2-5%（结果缓存、日志存储）
```

### 7.2 缓存策略矩阵

| 缓存层级 | 缓存内容 | 命中条件 | 失效策略 | 预期命中率 |
|---------|---------|---------|---------|-----------|
| **参数哈希缓存** | 完全相同参数的调用结果 | 参数完全一致 | TTL + 手动失效 | 5-15% |
| **语义相似缓存** | 语义相近查询的结果 | 向量相似度>0.95 | TTL + 基于时间衰减 | 15-30% |
| **中间结果缓存** | 工具调用链中的中间结果 | 相同上下文+相同工具序列 | 会话级别失效 | 10-20% |
| **预计算缓存** | 高频查询的预计算结果 | 预计算覆盖 | 定期刷新 | 20-40% |

关键设计：**语义缓存的相似度阈值需要精心调校**。阈值太低会返回不相关结果，阈值太高缓存命中率不足。建议从0.98开始，根据实际业务调优。

### 7.3 模型路由：用对的模型做对的事

不是每次工具调用都需要最强的模型。合理的模型路由可以节省60-80%的推理成本：

```
模型路由策略：

┌─────────────────────────────────────────────────┐
│  用户请求                                         │
│       │                                          │
│       ▼                                          │
│  ┌─────────────┐                                 │
│  │ 复杂度评估   │  评估任务复杂度、工具数量、推理深度  │
│  └──────┬──────┘                                 │
│         │                                        │
│    ┌────┼────┬─────────┐                         │
│    ▼    ▼    ▼         ▼                         │
│  简单  中等  复杂     极复杂                       │
│    │    │    │         │                         │
│    ▼    ▼    ▼         ▼                         │
│  小模型 中模型 大模型   超大模型                    │
│  (便宜) (均衡) (强)   (最强)                      │
│  $0.01 $0.05 $0.2   $1.0                       │
│                                                  │
│  路由依据：                                       │
│  - 工具数量：1个→小模型，3+个→中模型，5+个→大模型   │
│  - 推理深度：单步→小模型，多步推理→大模型            │
│  - 参数复杂度：简单参数→小模型，复杂嵌套→大模型      │
│  - 领域敏感度：通用→小模型，专业领域→大模型          │
└─────────────────────────────────────────────────┘
```

### 7.4 成本监控仪表板核心指标

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| **每次工具调用平均成本** | 总成本 / 总调用次数 | >预期值的150% |
| **缓存命中率** | 缓存命中数 / 总查询数 | <20% |
| **工具选择错误率** | 选错工具导致重试的比例 | >5% |
| **平均调用轮次** | 完成一次任务的平均工具调用次数 | >5次 |
| **成本/收入比** | 工具调用成本 / 用户付费 | >30% |

## §8 面试深度：如何设计一个支持1000+工具的Agent系统

这是面试中高频出现的系统设计题。下面给出一个结构化的回答框架。

### 8.1 问题拆解

1000+工具的Agent系统，核心挑战可以拆解为五个子问题：

```
挑战一：工具发现效率
→ 1000+工具不能全量加载到上下文，如何高效检索？

挑战二：选择准确性
→ 工具越多，模型选错的概率越高，如何保证准确率？

挑战三：执行可靠性
→ 工具来自不同提供者，质量参差不齐，如何保证执行结果可信？

挑战四：系统性能
→ 高并发场景下，如何保证低延迟？

挑战五：可维护性
→ 工具频繁上下线、版本迭代，如何保证系统稳定？
```

### 8.2 架构方案

**方案一：三级路由架构**

这是最核心的解决方案，前面已经详细介绍。关键点是路由本身也是一个LLM调用，但使用的是更小、更快的模型。

**方案二：工具索引层**

为所有工具构建向量索引，支持语义检索：

```
工具索引构建流程：

1. 工具注册时，将name + description + tags编码为向量
2. 存入向量数据库（如Milvus / Qdrant）
3. 用户请求到来时，将请求编码为向量
4. 向量检索Top-K最相关的工具（K=10~20）
5. 将检索到的工具描述加载到LLM上下文
6. LLM从这10-20个工具中做最终选择
```

向量索引相比传统关键词搜索的优势：

| 维度 | 关键词搜索 | 向量语义搜索 |
|------|-----------|-------------|
| 匹配方式 | 精确匹配/模糊匹配 | 语义相似度匹配 |
| 同义词 | 不支持 | 自动处理 |
| 多语言 | 需要分词器 | 原生支持 |
| 冷启动 | 需要关键词字典 | 无需额外配置 |

**方案三：工具组合模式**

复杂任务往往需要多个工具协作。设计工具组合模式，预定义常用工具组合：

```yaml
# 工具组合定义示例
tool_composites:
  - name: "data_analysis_pipeline"
    description: "数据分析全流程：获取数据→清洗→分析→可视化"
    tools:
      - tool_id: "db_query"
        step: 1
        dependency: null
      - tool_id: "data_clean"
        step: 2
        dependency: 1
      - tool_id: "stat_analysis"
        step: 3
        dependency: 2
      - tool_id: "chart_render"
        step: 4
        dependency: 3
```

**方案四：渐进式工具加载**

不是一开始就加载所有工具，而是根据对话上下文逐步加载：

```
对话轮次1：加载5个核心工具（通用搜索、文件操作...）
    │
    ├── 用户提到"数据库" → 加载3个数据库相关工具
    │
对话轮次2：现在有8个工具
    │
    ├── 用户提到"可视化" → 加载2个图表工具
    │
对话轮次3：现在有10个工具
    ...
```

这种策略的优势：
- 每轮对话的Token消耗可控
- 工具选择的准确率更高（候选集更小）
- 自然适配对话的渐进式需求

### 8.3 关键性能指标

一个支持1000+工具的系统，需要达成以下SLA：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| **工具检索延迟** | <50ms | 从用户请求到返回候选工具列表 |
| **工具选择延迟** | <2s | 模型从候选工具中做出选择 |
| **工具执行延迟** | <5s（P95） | 工具调用的端到端延迟 |
| **选择准确率** | >90% | 首次选择正确的比例 |
| **系统可用性** | 99.9% | 整体系统可用率 |
| **工具注册上线时间** | <1min | 新工具从注册到可用的时间 |

### 8.4 面试答题框架

建议按以下框架回答这类系统设计题：

1. **明确需求**（2分钟）：确认工具数量级、并发量、延迟要求、可用性要求
2. **整体架构**（5分钟）：画出三层架构（请求层→工具层→基础设施层）
3. **核心难点深入**（10分钟）：选1-2个核心难点深入展开（如工具路由、安全机制）
4. **权衡取舍**（3分钟）：讨论方案的trade-off，展示工程判断力
5. **扩展讨论**（可选）：如果时间允许，讨论成本优化、监控告警等

## 总结

工具调用是Agent从"聊天"到"干活"的关键能力。本文从演进历程、Schema设计、注册中心、市场生态、安全机制、成本优化到面试设计题，完整覆盖了工具调用的全链路。

核心要点回顾：

- **Schema设计是基础**：好的描述 > 好的参数设计 > 好的格式
- **路由机制是关键**：超过30个工具必须引入路由，超过500个需要多级路由
- **安全不能后补**：沙箱 + 审批 + 限流 + 审计，四层防护缺一不可
- **成本要算清楚**：模型路由 + 缓存 + 结果复用，三管齐下
- **工具市场是趋势**：MCP协议正在标准化工具生态，理解它对Agent架构至关重要

工具调用不是技术炫技，而是工程实践。真正考验一个Agent系统的，不是它能调用多少工具，而是它能在正确的时机、用正确的方式、调用正确的工具。
