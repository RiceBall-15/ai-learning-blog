# Agent架构全景：ReAct/Reflexion/LLMCompiler/ToolFormer/LATS深度对比

## 1. Agent架构演进时间线（2022-2026）

大语言模型从「聊天工具」进化为「自主Agent」，核心驱动力是**让LLM学会使用工具、规划任务、反思纠错**。以下是关键里程碑：

```
2022.10  ── ReAct (Yao et al.) ─────────────── 思考-行动循环范式诞生
2022.12  ── Toolformer (Meta) ─────────────── LLM自主学习调用工具
2023.03  ── Reflexion (Shinn et al.) ────────── 语言反馈+自反思机制
2023.05  ── Plan-and-Execute ──────────────── 规划与执行两阶段分离
2024.01  ── LLMCompiler (Kim et al.) ──────── 并行工具调用的DAG规划器
2024.05  ── LATS (Zhou et al.) ─────────────── 树搜索+反思的统一框架
2025-26  ── 多Agent协作/MoE Agent ─────────── 架构组合与规模化趋势
```

**核心趋势**：从单轮思考 → 多轮反思 → 并行规划 → 树搜索探索 → 多Agent协作，架构复杂度和能力上限持续攀升。

---

## 2. ReAct Agent：思考-行动循环

### 设计哲学

ReAct（Reasoning + Acting）是Agent架构的**开山之作**，核心思想极为简洁：让LLM交替进行「思考」和「行动」。

### 核心循环

```
┌─────────────────────────────────────────────┐
│              ReAct 循环                      │
│                                             │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐ │
│  │ Thought │───▶│  Act    │───▶│Observe  │ │
│  │ (推理)   │    │ (行动)   │    │ (观察)   │ │
│  └─────────┘    └─────────┘    └─────────┘ │
│       ▲                              │      │
│       └──────────────────────────────┘      │
│                  (循环)                      │
│                                             │
│  终止条件: 返回最终答案 / 达到最大轮次        │
└─────────────────────────────────────────────┘
```

### 实际运行示例

```
Query: 北京到上海的高铁需要多久？

Thought: 我需要查询北京到上海的高铁时刻表
Action: search("北京到上海 高铁 时刻")
Observation: G1次列车，北京南09:00出发，上海虹桥13:28到达，耗时4小时28分
Thought: 已经获取到答案，可以直接回复
Action: finish("北京到上海高铁约4小时28分")
```

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 通用问答、简单工具调用、信息检索 |
| 优势 | 实现简单、可解释性强、调试友好 |
| 局限 | 顺序执行慢、缺乏反思机制、容易陷入循环 |

## 3. Reflexion Agent：语言反馈+自反思

### 设计哲学

Reflexion的核心洞察：**人类不是一次做对，而是通过试错和反思来改进**。它在ReAct基础上加入了「经验记忆」和「反思总结」。

### 架构流程

```
┌──────────────────────────────────────────────────┐
│                Reflexion 架构                     │
│                                                  │
│  ┌──────────┐   ┌──────────┐   ┌──────────────┐ │
│  │ 执行器    │──▶│ 评估器    │──▶│  反思模块     │ │
│  │(Actor)   │   │(Evaluator)│   │(Reflector)   │ │
│  └──────────┘   └──────────┘   └──────────────┘ │
│       │              │               │           │
│       │              │          ┌────▼────┐      │
│       │              │          │ 经验记忆 │      │
│       │              │          │ Memory   │      │
│       │              │          └────┬────┘      │
│       │              │               │           │
│       └──────────────┴───────────────┘           │
│                     (下一轮改进)                   │
└──────────────────────────────────────────────────┘
```

### 关键机制

- **评估器**：判断当前任务是否完成（自动评估/人工反馈/测试用例）
- **反思模块**：生成自然语言反思，如「上次失败是因为搜索关键词不够精确，下次应该加入时间限定」
- **经验记忆**：将反思结果存入长期记忆，后续轮次可检索历史经验

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 代码生成、数学推理、需要试错的复杂任务 |
| 优势 | 自我改进、利用历史经验、提升成功率 |
| 局限 | 多轮执行成本高、依赖评估器质量、收敛不确定 |

## 4. LLMCompiler：并行工具调用的DAG规划器

### 设计哲学

LLMCompiler解决了ReAct的核心痛点：**串行执行太慢**。它让LLM先生成一个DAG（有向无环图）执行计划，然后并行调度独立任务。

### 架构设计

```
┌──────────────────────────────────────────────────┐
│              LLMCompiler 架构                    │
│                                                  │
│  ┌────────────┐                                  │
│  │   LLM规划器 │  输入: 用户意图                   │
│  │ (Planner)  │  输出: DAG执行计划                 │
│  └─────┬──────┘                                  │
│        │                                         │
│        ▼                                         │
│  ┌──────────────────────────────┐                │
│  │    DAG 执行计划              │                │
│  │                              │                │
│  │   ┌─────┐    ┌─────┐       │                │
│  │   │Task1│───▶│Task3│       │  Task1,2 并行   │
│  │   └─────┘    └─────┘       │  Task3 依赖1,2  │
│  │   ┌─────┐       │         │                │
│  │   │Task2│───────┘         │                │
│  │   └─────┘                  │                │
│  └──────────────────────────────┘                │
│        │                                         │
│        ▼                                         │
│  ┌────────────────┐  ┌────────────────┐          │
│  │ 工具执行器×N    │  │  结果聚合器     │          │
│  │ (并行调用)      │  │ (Join/Fuse)    │          │
│  └────────────────┘  └────────────────┘          │
└──────────────────────────────────────────────────┘
```

### DAG规划示例

```
用户: "比较北京和上海今天的天气，并推荐穿什么"

LLM生成的DAG:
  Task1: get_weather("北京", "今天")  ──┐
  Task2: get_weather("上海", "今天")  ──┼──▶ Task3: compare_weather(T1, T2)
                                       │
  依赖关系: Task3 依赖 Task1 + Task2
  并行度: Task1 和 Task2 可同时执行
```

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 多数据源查询、并行工具调用、延迟敏感场景 |
| 优势 | 显著降低延迟、资源利用率高、规划可审计 |
| 局限 | DAG生成出错难以自愈、不适合动态调整的场景 |

## 5. ToolFormer：LLM自主学习使用工具

### 设计哲学

ToolFormer的独特之处：**不通过提示工程教LLM用工具，而是通过微调让LLM「内化」工具使用能力**。

### 训练流程

```
┌──────────────────────────────────────────────────┐
│             ToolFormer 训练流程                   │
│                                                  │
│  Step 1: 标注数据生成                             │
│  ┌──────────────────────────────────────┐        │
│  │ 原文: "巴黎是法国首都"                │        │
│  │ 标注: "巴黎是法国首都                  │        │
│  │        [Calculator("法国人口")→6700万]"│        │
│  │        巴黎有约210万人口。"            │        │
│  └──────────────────────────────────────┘        │
│                                                  │
│  Step 2: 数据筛选                                │
│  ┌──────────────────────────────────────┐        │
│  │ 准则1: 工具调用确实提供了有用信息      │        │
│  │ 准则2: 不调用也能生成正确文本          │        │
│  │ (确保LLM不会过度依赖工具)              │        │
│  └──────────────────────────────────────┘        │
│                                                  │
│  Step 3: 微调                                   │
│  ┌──────────────────────────────────────┐        │
│  │ 标准语言建模 + 工具调用位置的损失计算   │        │
│  └──────────────────────────────────────┘        │
└──────────────────────────────────────────────────┘
```

### 内置工具类型

- **计算器**：数学运算
- **搜索引擎**：信息检索
- **翻译器**：多语言转换
- **日历**：日期查询
- **自定义API**：可扩展

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 需要频繁调用工具的通用对话、资源受限场景 |
| 优势 | 推理时无需提示工程、单次调用即可使用工具、降低延迟 |
| 局限 | 需要微调数据和算力、工具扩展性受限、无法动态发现新工具 |

## 6. Plan-and-Execute：两阶段分离

### 设计哲学

核心思想：**把「想」和「做」分开**。先由一个轻量级规划器制定全局计划，再由执行器逐步落实。

### 架构设计

```
┌──────────────────────────────────────────────────┐
│           Plan-and-Execute 架构                   │
│                                                  │
│  ┌────────────────────────────────────┐          │
│  │         阶段1: 规划 (Planning)      │          │
│  │                                    │          │
│  │  Planner LLM (大模型/强推理)        │          │
│  │  输入: 用户目标                      │          │
│  │  输出: [步骤1, 步骤2, ..., 步骤N]   │          │
│  └───────────────┬────────────────────┘          │
│                  │                               │
│                  ▼                               │
│  ┌────────────────────────────────────┐          │
│  │         阶段2: 执行 (Execution)     │          │
│  │                                    │          │
│  │  Executor LLM (小模型/快响应)       │          │
│  │  逐步执行每个步骤                    │          │
│  │  每步完成后更新计划状态              │          │
│  └───────────────┬────────────────────┘          │
│                  │                               │
│                  ▼                               │
│  ┌────────────────────────────────────┐          │
│  │         重规划 (Re-planning)        │          │
│  │                                    │          │
│  │  如果执行偏离计划 → 触发重新规划      │          │
│  └────────────────────────────────────┘          │
└──────────────────────────────────────────────────┘
```

### 与其他架构的关键区别

| 特性 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 规划粒度 | 每步决策 | 全局计划 |
| 规划成本 | 每轮都需大模型 | 仅首次和重规划 |
| 执行模型 | 同一模型 | 可用不同模型 |
| 可预测性 | 低 | 高 |

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 多步骤复杂任务、需要全局视角的任务 |
| 优势 | 计划可提前审核、支持模型解耦、执行成本可控 |
| 局限 | 计划可能过时、重规划机制复杂、初始规划质量依赖LLM |

## 7. LATS（Language Agent Tree Search）：树搜索+反思

### 设计哲学

LATS将**蒙特卡洛树搜索（MCTS）**思想引入Agent架构，通过系统性地探索多个可能的行动路径，结合反思机制选择最优解。

### 核心架构

```
┌──────────────────────────────────────────────────────┐
│                 LATS 树搜索架构                       │
│                                                      │
│                      根节点                           │
│                   (用户查询)                          │
│                   /      \                           │
│              行动A       行动B                        │
│             /    \         \                         │
│         行动C   行动D     行动E                       │
│         /        |         \                         │
│     [评估:7]  [评估:5]   [评估:9]                    │
│                                                      │
│  ┌─────────────────────────────────────────────┐     │
│  │              四个核心步骤                     │     │
│  │                                             │     │
│  │  1. Selection: UCB选择最有潜力的节点          │     │
│  │  2. Expansion: LLM生成候选行动               │     │
│  │  3. Simulation: 执行行动并评估结果           │     │
│  │  4. Backpropagation: 更新节点价值            │     │
│  │                                             │     │
│  │  + 反思机制: 评估不佳时生成自然语言反思       │     │
│  │    反思结果存入记忆，影响后续搜索             │     │
│  └─────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────┘
```

### 与ReAct的对比

```
ReAct:  A → B → C → D  (单路径，线性探索)
LATS:       A
           / \
          B   C
         / \   \
        D   E   F  (多路径，并行探索，选择最优)
```

### 适用场景与局限

| 维度 | 评价 |
|------|------|
| 适用场景 | 多步推理、需要全局最优的复杂任务、代码生成 |
| 优势 | 全局搜索、避免局部最优、结合反思提升质量 |
| 局限 | 计算成本高、搜索空间爆炸风险、实现复杂度大 |

## 9. 选型决策树

```
你的Agent需要什么能力？
│
├─ 需要使用工具？
│   ├─ 工具调用频繁且固定 → ToolFormer（微调）
│   ├─ 工具调用可并行 → LLMCompiler
│   └─ 简单工具调用 → ReAct
│
├─ 任务复杂度？
│   ├─ 简单单步 → ReAct
│   ├─ 中等多步 → Plan-and-Execute
│   ├─ 复杂需试错 → Reflexion
│   └─ 需要全局最优 → LATS
│
├─ 延迟要求？
│   ├─ 极低延迟 → LLMCompiler / ToolFormer
│   ├─ 中等延迟可接受 → ReAct / Plan-and-Execute
│   └─ 延迟不敏感 → Reflexion / LATS
│
├─ 容错要求？
│   ├─ 高容错 → Reflexion / LATS
│   └─ 可接受失败 → ReAct / LLMCompiler
│
└─ 资源预算？
    ├─ 预算有限 → ReAct / LLMCompiler
    └─ 预算充足 → LATS / Reflexion
```

**实战推荐组合**：

- **入门首选**：ReAct（LangChain/LangGraph直接支持）
- **生产环境**：Plan-and-Execute（可预测+成本可控）
- **代码生成**：Reflexion + 测试驱动
- **数据分析**：LLMCompiler（并行查询多数据源）
- **高精度场景**：LATS（牺牲成本换质量）

## 10. 面试深度：如何设计一个新的Agent架构？

### 面试官：如果让你设计一个新的Agent架构，你会怎么做？

### 回答框架

#### Step 1: 明确设计约束

```
在动手之前，先问自己：
1. 任务类型是什么？(对话/推理/代码/多模态)
2. 延迟和成本的SLO是什么？
3. 是否需要可解释性？
4. 错误容忍度多高？
5. 是否需要跨会话记忆？
```

#### Step 2: 选择核心循环模式

```python
# 候选循环模式
循环模式 = {
    "ReAct":    "串行思考-行动，简单可靠",
    "并行DAG":  "依赖分析后并行，效率优先",
    "树搜索":   "多路径探索，质量优先",
    "反思":     "试错+经验积累，自我改进",
    "混合":     "组合多种模式，灵活但复杂"
}
```

#### Step 3: 设计模块化架构

```
┌──────────────────────────────────────────┐
│           自定义Agent架构模板              │
│                                          │
│  ┌──────────┐  ┌──────────┐             │
│  │ 规划层    │  │ 记忆层    │             │
│  │ Planner  │  │ Memory   │             │
│  └────┬─────┘  └────┬─────┘             │
│       │              │                   │
│       ▼              ▼                   │
│  ┌─────────────────────────┐             │
│  │       核心循环引擎       │             │
│  │   (选择/扩展/执行/反思)   │             │
│  └───────────┬─────────────┘             │
│              │                           │
│       ┌──────┴──────┐                    │
│       ▼             ▼                    │
│  ┌──────────┐  ┌──────────┐             │
│  │ 工具层    │  │ 评估层    │             │
│  │ Tools    │  │ Evaluator│             │
│  └──────────┘  └──────────┘             │
└──────────────────────────────────────────┘
```

#### Step 4: 实现关键差异化

我的新架构设计思路——**自适应Agent（Adaptive Agent）**：

```python
class AdaptiveAgent:
    def __init__(self):
        self.regimes = {
            "simple":  ReActLoop(),       # 简单任务用ReAct
            "parallel": DAGPlanner(),      # 可并行用DAG
            "complex": LATSPlanner(),      # 复杂任务用LATS
        }
    
    def execute(self, task):
        # 1. 任务分类：评估复杂度
        complexity = self.classify(task)
        
        # 2. 动态选择循环模式
        loop = self.regimes[complexity]
        
        # 3. 执行并监控
        result = loop.run(task)
        
        # 4. 如果失败，升级模式
        if not result.success:
            return self.escalate_and_retry(task, complexity)
        
        return result
    
    def classify(self, task):
        """用小模型快速分类任务复杂度"""
        features = self.extract_features(task)
        if features.tool_count == 1:
            return "simple"
        elif features.dependency_level == "low":
            return "parallel"
        else:
            return "complex"
```

**核心创新点**：

1. **自适应模式切换**：根据任务复杂度动态选择最优循环模式
2. **渐进式升级**：简单模式失败后自动升级到更强的模式
3. **成本感知**：在质量和成本之间动态平衡
4. **统一记忆层**：所有模式共享经验记忆，跨模式学习

#### Step 5: 评估与迭代

```
评估维度：
├─ 任务成功率 (Success Rate)
├─ 平均延迟 (P50/P95/P99)
├─ 每任务成本 (Cost per Task)
├─ 模式切换准确率 (Classification Accuracy)
└─ 用户满意度 (Human Evaluation)
```
