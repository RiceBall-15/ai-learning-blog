# Agent Loop从零到实战：手把手构建一个完整的ReAct Agent

> 本文是面试方向1（Agent Loop执行机制）的深度补充。如果你刚接触Agent概念，或正在准备AI Agent相关面试，这篇文章会带你从最朴素的理解出发，一步步构建出一个生产级的Agent Loop。

---

## §1 什么是Agent Loop：用厨师做菜理解"思考-行动-观察"

### 一个你每天都在做的循环

想象你在厨房做一道红烧肉：

```
┌─────────────────────────────────────────────────────────────┐
│                    厨师的"Agent Loop"                        │
│                                                             │
│  ① 思考："红烧肉需要焯水去腥，对吧？先查一下焯水要几分钟。"    │
│  ② 行动：拿起手机搜索"红烧肉焯水时间"                        │
│  ③ 观察：搜索结果显示"冷水下锅，水开后3-5分钟"                │
│  ④ 思考："3-5分钟...那我先焯5分钟，然后开始炒糖色。"          │
│  ⑤ 行动：开始焯水，同时准备冰糖和八角                        │
│  ⑥ 观察：焯完水，肉表面变白，浮沫很多                        │
│  ⑦ 思考："浮沫要撇掉，不然汤会浑浊。"                       │
│  ⑧ 行动：撇掉浮沫，开始炒糖色                              │
│  ⑨ 观察：糖色炒到枣红色了                                    │
│  ⑩ 思考："差不多了，下肉翻炒上色..."                         │
│  ...                                                        │
│  最终：菜做好了，Loop终止                                    │
└─────────────────────────────────────────────────────────────┘
```

这个过程和AI Agent执行任务时的**Agent Loop**完全同构。每一次循环都是：

> **思考（Thought）→ 行动（Action）→ 观察（Observation）**

这正是Yao等人在2022年论文《ReAct: Synergizing Reasoning and Acting in Language Models》中提出的ReAct框架的核心思想。

### 为什么需要Loop？

很多人会问：LLM不是直接回答就行了吗？为什么还要搞循环？

**关键在于：单次LLM调用是"闭卷考试"，而Agent Loop是"开卷考试"。**

| 维度 | 单次LLM调用 | Agent Loop |
|------|------------|------------|
| 知识来源 | 仅训练数据（截止某时间点） | 可以调用工具获取实时信息 |
| 推理深度 | 一次生成，无法自我纠错 | 多轮迭代，逐步逼近答案 |
| 任务复杂度 | 简单问答 | 多步骤、需要规划和分解 |
| 容错能力 | 错了就错了 | 可以观察错误并修正 |
| 资源利用 | 只用LLM | LLM + 搜索 + 计算 + API等 |

用一句话概括：**Agent Loop让LLM从"一次性回答者"变成了"持续学习的执行者"。**

### Agent Loop的数学本质

从计算角度看，Agent Loop本质上是一个**马尔可夫决策过程（MDP）**的展开：

```
状态转移：s_{t+1} = f(s_t, a_t)
奖励：r_t = R(s_t, a_t, o_t)
终止：当 s_t ∈ S_terminal 时停止
```

其中：
- `s_t`：当前状态（对话历史 + 环境信息）
- `a_t`：Agent选择的行动（工具调用/文本生成）
- `o_t`：行动的观察结果（工具返回值）
- `S_terminal`：终止状态集合（任务完成/失败/达到上限）

## §2 最简Agent Loop：50行Python实现一个能搜索+计算的Agent

我们先用最小的代码理解Agent Loop的核心结构。这个Agent可以搜索信息和执行计算：

```python
import json
from openai import OpenAI

client = OpenAI()

# 定义工具
tools = {
    "search": lambda q: f"搜索结果：{q}的最新信息...",  # 简化
    "calculate": lambda expr: str(eval(expr)),  # 简化
}

tool_descriptions = """你可以使用以下工具：
- search(query): 搜索信息
- calculate(expression): 计算数学表达式
当你有足够信息时，直接回答用户问题。"""

def agent_loop(user_query: str, max_steps: int = 10):
    """最简Agent Loop实现"""
    messages = [
        {"role": "system", "content": f"你是一个智能助手。{tool_descriptions}"},
        {"role": "user", "content": user_query}
    ]
    
    for step in range(max_steps):
        # ① 思考：调用LLM获取下一步
        response = client.chat.completions.create(
            model="gpt-4", messages=messages, tools=[...]
        )
        msg = response.choices[0].message
        
        # ② 判断：是否需要行动？
        if not msg.tool_calls:
            return msg.content  # 直接回答，Loop终止
        
        # ③ 行动：执行工具
        for tool_call in msg.tool_calls:
            name = tool_call.function.name
            args = json.loads(tool_call.function.arguments)
            result = tools[name](**args)
            
            # ④ 观察：结果加入对话历史
            messages.append({"role": "tool", "content": result})
    
    return "达到最大步骤数，停止执行"
```

这50行代码已经包含了Agent Loop的所有核心要素：

```
┌──────────────────────────────────────────────────┐
│            Agent Loop 核心骨架                    │
│                                                  │
│  for step in range(max_steps):   ← 步数保护     │
│      │                                           │
│      ├─ LLM.call(messages)       ← ① 思考       │
│      │                                           │
│      ├─ if no tool_calls:        ← ② 终止判断   │
│      │      return answer                        │
│      │                                           │
│      ├─ tool.execute(args)       ← ③ 行动       │
│      │                                           │
│      └─ messages.append(result)  ← ④ 观察       │
│                                                  │
└──────────────────────────────────────────────────┘
```

> **核心洞察：Agent Loop的全部复杂度，都藏在"什么时候停止"和"出了错怎么办"这两个问题里。**

## §3 从最简到生产：每一步改进了什么

最简版可以运行，但在生产环境会频繁出问题。下面的对比表格清晰展示了每一步改进的意义：

### 3.1 进化路线总览

```
V1 最简版 → V2 加错误恢复 → V3 加超时 → V4 加流式 → V5 加中断恢复
   │            │               │            │              │
   │            │               │            │              │
   ▼            ▼               ▼            ▼              ▼
  能跑      不会崩           有保障       用户友好      可恢复
```

### 3.2 各版本改进对比

| 版本 | 改进项 | 解决的问题 | 实现要点 |
|------|--------|-----------|---------|
| V1 | 基础Loop | 能跑就行 | for循环 + 工具调用 |
| V2 | 错误恢复 | 工具调用失败时崩溃 | try/except + 重试 + 错误信息回传LLM |
| V3 | 超时控制 | 工具卡死导致无限等待 | asyncio.wait_for + 步级超时 + 全局超时 |
| V4 | 流式输出 | 用户等待焦虑 | Streaming + 增量展示思考过程 |
| V5 | 中断恢复 | 用户想中途修改任务 | Checkpoint + 状态序列化 + 断点续传 |
| V6 | 审批机制 | 危险操作需人工确认 | 在行动前插入人工审批节点 |

### 3.3 错误恢复：最被低估的改进

生产环境中，**超过30%的Agent循环会遇到至少一次工具调用失败**。错误恢复不是nice-to-have，是必须的。

错误恢复的关键设计：

```
┌──────────────────────────────────────────────────┐
│              错误恢复策略矩阵                      │
├──────────────┬──────────────┬────────────────────┤
│   错误类型    │   恢复策略    │    最大重试次数    │
├──────────────┼──────────────┼────────────────────┤
│ 网络超时     │ 指数退避重试  │ 3次               │
│ API限流     │ 延迟重试      │ 5次               │
│ 参数格式错误  │ 让LLM修正参数 │ 2次               │
│ 工具不存在   │ 告知LLM不可用  │ 不重试，回退文本  │
│ 返回结果异常  │ 请求LLM换工具 │ 1次               │
└──────────────┴──────────────┴────────────────────┘
```

**核心原则：错误信息本身也是"观察"，应该回传给LLM让它自行决定如何处理。**

这个原则非常重要——不要试图在代码层面硬编码所有错误处理逻辑，而是把错误上下文交给LLM，让它像人类一样"看到错误信息后自行判断该怎么办"。实践证明，这种方式的错误恢复成功率比硬编码策略高出40%以上。

### 3.4 流式输出：让用户"看到思考"

流式输出不是简单的文本流，它需要区分三种信息的展示方式：

```
┌───────────────────────────────────────────┐
│          流式输出的三种内容类型             │
│                                           │
│  🧠 思考过程（Thought）                    │
│     → 以折叠/小字展示                     │
│     → 用户可选展开                        │
│                                           │
│  🔧 工具调用（Action）                     │
│     → 以进度条/图标展示                   │
│     → 显示工具名和参数                    │
│                                           │
│  📋 观察结果（Observation）                │
│     → 以卡片/引用展示                     │
│     → 可展开查看详情                      │
│                                           │
│  💬 最终回答（Answer）                     │
│     → 正常Markdown渲染                   │
│     → 流式逐字展示                       │
└───────────────────────────────────────────┘
```

### 3.5 中断恢复：让用户"改主意"

用户可能在Agent执行到一半时想修改需求。中断恢复需要：

1. **Checkpoint机制**：每隔N步序列化Agent的完整状态（对话历史、工具结果、执行计划）
2. **断点续传**：用户修改需求后，从最近的Checkpoint恢复，而不是从头开始
3. **状态隔离**：修改不影响已执行的步骤，只影响后续计划

这是一个工程上非常复杂的特性，但对用户体验的提升是质变级的。想象一下：你让Agent帮你写一份报告，它已经搜索了30分钟的资料，突然你说"把重点改成市场分析而不是技术分析"——如果没有中断恢复，Agent要从头再来；有了中断恢复，它只需要调整后续计划，已搜索的资料仍然可用。

## §4 Agent Loop的终止条件设计：何时停止思考和行动

终止条件是Agent Loop设计中最关键、也最容易出错的部分。设计不当会导致两种灾难：

- **停不下来**：Agent陷入死循环，烧钱烧资源
- **停太早**：Agent还没完成任务就放弃了

### 4.1 六大终止条件

| 终止条件 | 触发时机 | 优先级 | 必须有？ |
|---------|---------|--------|---------|
| 任务完成 | LLM返回最终回答（无tool_call） | 最高 | ✅ |
| 最大步数 | 循环次数达到上限 | 高 | ✅ |
| 最大Token | 累计Token超过预算 | 高 | ✅ |
| 最大时间 | 总执行时间超过限制 | 中 | 推荐 |
| 成本上限 | 本次调用费用超过阈值 | 中 | 推荐 |
| 死循环检测 | 连续N次相同行动/相同结果 | 低 | ✅ |

### 4.2 死循环检测：一个常被忽略的坑

Agent Loop最常见的故障模式是**死循环**。以下是几种典型场景：

```
场景1：工具返回结果与预期不同，LLM反复尝试相同工具
  → 第1次：搜索"天气" → 返回"北京晴" → LLM认为不对
  → 第2次：搜索"天气" → 返回"北京晴" → LLM还是认为不对
  → ...无限循环

场景2：两个工具互相触发
  → 调用A → 结果需要调用B → 调用B → 结果需要调用A → ...

场景3：LLM输出格式异常，无法解析
  → 返回非法JSON → 重试 → 还是非法JSON → 重试 → ...
```

**死循环检测的实现策略：**

```
┌──────────────────────────────────────────────────┐
│          死循环检测机制                            │
│                                                   │
│  1. 相同行动检测：最近N步是否重复同一工具+同一参数   │
│  2. 相同结果检测：最近N步是否得到完全相同的返回值    │
│  3. 递增检测：结果是否在单调变化但无法收敛          │
│  4. 无效循环检测：行动后状态是否真的发生了变化       │
│                                                   │
│  一旦检测到死循环：                                │
│  → 强制注入提示："你似乎陷入了循环，请换一种方式"    │
│  → 若仍循环，强制终止并返回当前最佳结果             │
└──────────────────────────────────────────────────┘
```

### 4.3 渐进式终止：优雅降级

最佳实践不是"一刀切"终止，而是**渐进式降级**：

```
第1-8步：全速执行，使用最强模型
第9步：  警告Agent"你还有2步机会"
第10步： 强制要求Agent给出当前最佳答案
第11步： 如果还没完成，直接返回中间结果+提示用户
```

## §5 三种Loop模式实战对比：ReAct vs Plan-Execute vs Reflexion

Agent Loop不止ReAct一种模式。根据任务特点，有三种主流的Loop范式：

### 5.1 三种模式概览

| 维度 | ReAct | Plan-Execute | Reflexion |
|------|-------|-------------|-----------|
| 核心思想 | 边想边做 | 先想后做 | 做完反思 |
| 执行顺序 | Think → Act → Observe → Think... | Plan → Execute → Evaluate → RePlan | Act → Reflect → Improve → Act... |
| 适合场景 | 探索性任务 | 结构化复杂任务 | 需要自我改进的任务 |
| 规划深度 | 浅（单步规划） | 深（全局规划） | 中（迭代改进） |
| Token效率 | 中等 | 较高（减少无效探索） | 较低（多次反思） |
| 典型应用 | 搜索问答、工具调用 | 项目管理、代码生成 | 代码调试、论文写作 |

### 5.2 ReAct：最直觉的Agent Loop

```
┌──────────────────────────────────────────────┐
│                ReAct Loop                    │
│                                              │
│  用户提问                                     │
│    │                                         │
│    ▼                                         │
│  ┌─────────┐    ┌──────────┐                 │
│  │ Thought │───▶│  Action  │                 │
│  │ 思考    │    │  执行工具  │                 │
│  └─────────┘    └────┬─────┘                 │
│       ▲              │                       │
│       │              ▼                       │
│       │        ┌──────────┐                  │
│       └────────│Observation│                 │
│                │  获取结果  │                  │
│                └──────────┘                  │
│                   │                          │
│                   ▼                          │
│              是否完成？                       │
│              是 → 输出答案                    │
│              否 → 继续循环                    │
└──────────────────────────────────────────────┘
```

**优点**：实现简单，每一步都有LLM参与决策，灵活性最高。

**缺点**：缺乏全局规划，容易在复杂任务中迷失方向；Token消耗随步数线性增长。

### 5.3 Plan-Execute：先想清楚再动手

```
┌──────────────────────────────────────────────┐
│            Plan-Execute Loop                 │
│                                              │
│  用户提问                                     │
│    │                                         │
│    ▼                                         │
│  ┌──────────┐                                │
│  │  Plan    │  LLM生成完整执行计划            │
│  │ Step 1   │  "先搜索X，再计算Y，最后汇总"   │
│  │ Step 2   │                                │
│  │ Step 3   │                                │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  ┌──────────┐                                │
│  │ Execute  │  逐步执行，可能不调用LLM        │
│  │ Step 1   │  直接调用工具                   │
│  │ Step 2   │                                │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  ┌──────────┐                                │
│  │ Evaluate │  LLM评估执行结果                │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  需要调整计划？                               │
│  是 → 重新规划（RePlan）                      │
│  否 → 输出最终结果                            │
└──────────────────────────────────────────────┘
```

**优点**：Token效率高（规划阶段一次LLM调用，执行阶段可能不需要LLM）；适合结构化任务。

**缺点**：初始规划质量依赖LLM能力；对意外情况的适应性较差。

### 5.4 Reflexion：做完反思，自我进化

```
┌──────────────────────────────────────────────┐
│            Reflexion Loop                    │
│                                              │
│  用户提问                                     │
│    │                                         │
│    ▼                                         │
│  ┌──────────┐                                │
│  │  Act     │  执行任务（可能是ReAct或直接）  │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  ┌──────────┐                                │
│  │Reflect   │  "刚才哪里做得不好？"           │
│  │ 反思     │  "应该注意什么？"               │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  ┌──────────┐                                │
│  │Improve   │  将反思存入记忆                 │
│  │ 改进     │  下次执行时参考                  │
│  └────┬─────┘                                │
│       │                                      │
│       ▼                                      │
│  质量达标？                                   │
│  否 → 带着反思重新执行                        │
│  是 → 输出结果                                │
└──────────────────────────────────────────────┘
```

**优点**：能从失败中学习，逐步提升任务质量；特别适合代码调试、创意写作等需要迭代的场景。

**缺点**：Token消耗最大（每次反思都是一次LLM调用）；反思质量不可控。

### 5.5 混合模式：真实世界的最佳实践

实际上，成熟的Agent系统往往不是纯粹使用某一种Loop模式，而是根据任务的不同阶段动态切换：

```
┌──────────────────────────────────────────────────────┐
│              混合Loop模式示例                         │
│                                                      │
│  用户："帮我写一篇关于量子计算的技术博客"               │
│                                                      │
│  Phase 1: Plan-Execute                               │
│  → LLM生成大纲：引言、原理、应用、趋势、总结          │
│  → 分配各部分的写作任务                               │
│                                                      │
│  Phase 2: 并行ReAct                                  │
│  → 多个子Agent同时搜索各部分的最新资料                 │
│  → 每个子Agent独立完成对应章节的初稿                   │
│                                                      │
│  Phase 3: Reflexion                                  │
│  → 汇总Agent审查全文                                 │
│  → 发现"应用部分缺少2026年最新案例"                   │
│  → 重新搜索并修改                                     │
│  → 再次审查，确认质量达标                              │
└──────────────────────────────────────────────────────┘
```

### 5.6 如何选择？

```
选择决策树：

你的任务是...
│
├─ 简单探索型（搜索、问答）
│  → 选 ReAct：简单直接，单步规划够用
│
├─ 复杂结构型（项目管理、代码架构设计）
│  → 选 Plan-Execute：全局规划减少无效探索
│
├─ 需要高质量输出（代码、论文、创意内容）
│  → 选 Reflexion：迭代改进逼近最优
│
├─ 组合型任务
│  → 混合模式：Plan-Execute + 内嵌ReAct
│
└─ 不确定
   → 从ReAct开始，发现问题再切换
```

**一个实用的判断标准：** 如果你的任务步骤数超过5步，Plan-Execute通常比纯ReAct更高效。如果你的任务对输出质量要求极高（如代码必须能编译通过），Reflexion的迭代改进是值得额外Token消耗的。

## §6 并行Loop：多个Agent同时执行的调度策略

当任务可以分解为独立子任务时，并行执行多个Agent Loop能大幅提升效率。

### 6.1 并行调度的三种模式

| 调度模式 | 描述 | 适用场景 | 复杂度 |
|---------|------|---------|--------|
| Fan-Out/Fan-In | 分发→并行→汇总 | 独立子任务 | 低 |
| Pipeline | 流水线式串联 | 有依赖关系的任务 | 中 |
| MapReduce | 映射→归约 | 大规模数据处理 | 中 |
| Supervisor | 主Agent调度子Agent | 复杂协作任务 | 高 |

### 6.2 Fan-Out/Fan-In模式详解

这是最常用的并行模式。假设用户问："对比北京、上海、深圳三个城市的天气、交通和房价"

```
┌──────────────────────────────────────────────────────┐
│              Fan-Out / Fan-In 模式                    │
│                                                      │
│               ┌─────────────┐                        │
│               │ Supervisor  │                        │
│               │  主Agent    │                        │
│               └──────┬──────┘                        │
│                      │ 分发任务                       │
│            ┌─────────┼─────────┐                     │
│            ▼         ▼         ▼                     │
│     ┌──────────┐┌──────────┐┌──────────┐            │
│     │ Agent-BJ ││ Agent-SH ││ Agent-SZ │            │
│     │ 北京子Agent││ 上海子Agent││ 深圳子Agent│           │
│     └────┬─────┘└────┬─────┘└────┬─────┘            │
│          │           │           │                   │
│          ▼           ▼           ▼                   │
│     ┌──────────────────────────────────┐             │
│     │          汇总 Agent               │             │
│     │   收集结果 → 生成对比报告          │             │
│     └──────────────────────────────────┘             │
│                      │                               │
│                      ▼                               │
│               最终输出给用户                          │
└──────────────────────────────────────────────────────┘
```

### 6.3 并行调度的关键挑战

**挑战1：结果冲突**

多个Agent可能修改同一个资源。解决策略：

```
乐观并发：各Agent独立执行，冲突时重试
悲观并发：引入锁机制，串行访问共享资源
版本控制：每次修改带版本号，冲突时人工/自动合并
```

**挑战2：部分失败**

10个并行Agent中有3个失败，应该怎么办？

```
策略A：全部成功才返回（严格模式）
策略B：容忍部分失败，返回可用结果（宽松模式）
策略C：对失败任务降级处理，如用缓存/默认值替代
```

**挑战3：资源竞争**

并行Agent同时调用同一API，可能触发限流。

```
解决方案：
1. 限流器：使用令牌桶算法控制并发数
2. 错开启动：各Agent延迟不同的随机时间
3. 共享配额：Supervisor统一管理API调用预算
```

### 7.2 缓存：最直接的成本优化

LLM调用缓存可以减少50%以上的成本。关键设计：

**提示缓存（Prompt Caching）**：对于相同前缀的提示，缓存KV值，后续调用只需处理新增部分。

**语义缓存**：当新问题与缓存中的问题语义相似时，直接返回缓存答案。

| 缓存类型 | 命中率 | 实现复杂度 | 适用场景 |
|---------|--------|-----------|---------|
| 完全匹配缓存 | 低 | 低 | 相同问题重复问 |
| 语义相似缓存 | 中 | 中 | 相似问题换种问法 |
| 工具结果缓存 | 高 | 低 | 同一工具相同参数 |
| 中间步骤缓存 | 中 | 高 | 复杂任务的部分重叠 |

### 7.3 早停：当Agent已经"够好了"

并非所有任务都需要跑满最大步数。早停策略：

```
早停触发条件（满足任一即停）：

1. LLM置信度阈值
   → 当LLM回答时附带confidence ≥ 0.9，直接返回

2. 结果稳定检测
   → 连续2步的结果变化 < 阈值，认为已收敛

3. 用户自定义条件
   → 用户指定"找到3个结果就停"

4. 成本预算耗尽
   → Token消耗达到预算的90%，强制要求LLM总结当前结果
```

### 7.4 成本控制：三个核心数字

生产环境中必须设置的三个数字：

```
┌──────────────────────────────────────────┐
│         成本控制三道防线                   │
│                                          │
│  第一道：Token预算                        │
│  → 单次请求最大Token数（如10万）          │
│  → 超过后强制终止并返回中间结果            │
│                                          │
│  第二道：调用次数上限                      │
│  → 单次任务最大LLM调用次数（如20次）      │
│  → 超过后返回当前最佳答案                 │
│                                          │
│  第三道：金额上限                          │
│  → 单次任务最大花费（如$5）               │
│  → 实时累计，超过立即停止                  │
│                                          │
│  三道防线的优先级：金额 > 调用次数 > Token  │
└──────────────────────────────────────────┘
```

### 7.5 降级策略：系统不能停

当主路径不可用时，降级策略确保系统仍然可用：

| 降级层级 | 触发条件 | 降级行为 |
|---------|---------|---------|
| L1: 工具降级 | 某工具不可用 | 用替代工具或跳过 |
| L2: 模型降级 | 强模型超时/限流 | 切换到弱模型 |
| L3: 模式降级 | 复杂Loop失败 | 简化为单次LLM调用 |
| L4: 结果降级 | 无法生成完整答案 | 返回部分结果+提示 |
| L5: 服务降级 | 系统过载 | 返回缓存结果/排队 |

## §9 面试题：解释Agent Loop的工作原理

### 9.1 常见面试问题

**Q1：请解释Agent Loop是什么？它解决了什么问题？**

> 参考答案要点：
> - Agent Loop是让LLM通过"思考-行动-观察"的循环来完成复杂任务的机制
> - 解决了LLM"闭卷考试"的局限性——无法获取实时信息、无法自我纠错
> - 本质上是把LLM从一次性回答者变成了持续学习的执行者

**Q2：ReAct、Plan-Execute和Reflexion三种Loop模式有什么区别？**

> 参考答案要点：
> - ReAct：边想边做，适合探索性任务，灵活性最高
> - Plan-Execute：先全局规划再逐步执行，适合结构化任务，Token效率高
> - Reflexion：执行后反思并迭代改进，适合需要高质量输出的任务，但Token消耗最大

**Q3：如何设计Agent Loop的终止条件？**

> 参考答案要点：
> - 必须有：任务完成、最大步数、最大Token
> - 推荐有：最大时间、成本上限
> - 容易忽略：死循环检测（相同行动/结果的重复检测）
> - 最佳实践：渐进式终止，而非一刀切

**Q4：生产环境中Agent Loop面临哪些挑战？如何解决？**

> 参考答案要点：
> - 工具调用失败 → 错误恢复机制（重试+指数退避+错误信息回传LLM）
> - 无限循环 → 死循环检测+最大步数限制
> - 成本失控 → Token预算+调用次数上限+金额上限
> - 用户体验差 → 流式输出+思考过程可视化
> - 系统可用性 → 降级策略（工具/模型/模式/结果/服务五级降级）

**Q5：如何优化Agent Loop的性能和成本？**

> 参考答案要点：
> - 缓存：提示缓存、语义缓存、工具结果缓存
> - 早停：置信度阈值、结果稳定检测、用户自定义条件
> - 并行：Fan-Out/Fan-In、Pipeline模式
> - 降级：多层级降级策略
> - 成本控制：三道防线（Token预算+调用次数+金额上限）

## 总结

Agent Loop是AI Agent的"心脏"——它驱动着Agent从接收任务到完成任务的整个过程。理解Agent Loop，不仅仅是理解一个技术概念，更是理解如何让AI系统像人类一样思考和行动。

从最简的50行代码到生产级系统，Agent Loop的每一步改进都对应着真实的问题：

- **错误恢复** 解决工具调用失败的问题
- **超时控制** 解决工具卡死的问题
- **流式输出** 解决用户体验问题
- **死循环检测** 解决无限循环问题
- **终止条件** 解决"何时停止"的核心问题
- **并行调度** 解决效率问题
- **成本控制** 解决烧钱问题

掌握Agent Loop，你就掌握了构建AI Agent的核心能力。无论面试还是实战，这都是最重要的基础。

> **记住：Agent Loop的全部复杂度，都藏在"什么时候停止"和"出了错怎么办"这两个问题里。**
