## 说在前面

在AI系统架构中，**数据管道**（Data Pipeline）是最容易被忽视、却最容易出问题的环节。你可能花大量精力优化模型，但最终发现：模型效果的瓶颈不在算法，而在数据。

很多AI团队面临的真实困境：

- 模型训练的数据准备要跑一周，实验迭代极慢
- 特征计算逻辑分散在各个脚本中，难以复用和维护
- 训练时的特征和在线推理的特征不一致（Training-Serving Skew）
- 实时特征延迟太高，影响在线推理效果

今天我来完整梳理AI系统数据管道的架构演进，从传统批处理ETL到实时特征平台，帮你构建一个**可演进、可扩展、可维护**的数据基础设施。

## 二、架构演进：四个阶段

### 2.1 Phase 1：传统批处理ETL

**典型场景：** 离线模型训练，数据准备周期以天/周为单位。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Phase 1: 传统批处理ETL                             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐         │
│  │ 数据 │───▶│ 抽取 │───▶│ 清洗 │───▶│ 转换 │───▶│ 加载 │         │
│  │ 源   │    │ E    │    │ T    │    │ T    │    │ L    │         │
│  └──────┘    └──────┘    └──────┘    └──────┘    └──────┘         │
│                                                                      │
│  技术栈:                                                             │
│  ├── 调度: Airflow / Prefect / cron                                  │
│  ├── 处理: Spark / Hive / pandas                                     │
│  ├── 存储: HDFS / S3 / 数据仓库                                     │
│  └── 监控: 基本的日志和告警                                          │
│                                                                      │
│  优势:                                                               │
│  ├── 架构简单，易于理解                                              │
│  ├── 处理大规模数据（TB级）                                          │
│  └── 技术成熟，生态完善                                              │
│                                                                      │
│  痛点:                                                               │
│  ├── 延迟高（小时/天级别）                                           │
│  ├── 资源浪费（定时全量计算）                                        │
│  ├── 无法支持实时特征                                                │
│  └── 迭代周期长                                                      │
│                                                                      │
│  典型代码:                                                           │
│  ```python                                                          │
│  # Airflow DAG: 每天凌晨跑一次全量ETL                                │
│  @dag(schedule="0 2 * * *")                                         │
│  def daily_etl():                                                   │
│      raw = extract_from_source()     # 抽取全量数据                  │
│      cleaned = clean_and_validate(raw)  # 清洗                      │
│      features = compute_features(cleaned)  # 特征计算                │
│      load_to_warehouse(features)     # 写入数据仓库                  │
│  ```                                                                │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.3 Phase 3：Kappa架构——统一流处理

**典型场景：** 全面拥抱流处理，用一套代码处理所有数据。

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Phase 3: Kappa架构                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐     │
│  │ 数据源   │───▶│  Kafka   │───▶│  Flink   │───▶│ 特征存储 │     │
│  └──────────┘    │ (事件流) │    │ (流处理) │    │ (Redis/  │     │
│                  └──────────┘    └──────────┘    │  Feature  │     │
│                                                   │  Store)   │     │
│  核心原则:                                        └──────────┘     │
│  ├── 所有数据都是事件流                                            │
│  ├── 用同一套Flink代码处理实时和回放                                │
│  ├── 历史数据 = 从Kafka回放的流                                    │
│  └── 没有独立的批处理层                                            │
│                                                                      │
│  优势:                                                               │
│  ├── 统一技术栈，降低维护成本                                        │
│  ├── 真正的实时处理（毫秒级）                                       │
│  ├── 通过回放实现历史数据重算                                       │
│  └── 资源利用率高                                                    │
│                                                                      │
│  挑战:                                                               │
│  ├── Kafka存储成本（保留全量历史数据）                               │
│  ├── Flink开发门槛较高                                              │
│  ├── 有状态计算的容错复杂度                                          │
│  └── 需要成熟的运维体系                                              │
└─────────────────────────────────────────────────────────────────────┘
```

│                             │                                        │
│           ┌─────────────────┼─────────────────┐                     │
│           │                 │                 │                      │
│           ▼                 ▼                 ▼                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐             │
│  │  Metadata    │  │  Offline     │  │  Online      │             │
│  │  Store       │  │  Store       │  │  Store       │             │
│  │              │  │              │  │              │             │

│  │ 版本管理    │  │ Hive/S3      │  │ 亚毫秒读取   │             │
│  │ 血缘关系    │  │ 批量读取     │  │ 点查         │             │

│                                                                      │
│  关键设计决策:                                                       │
│  ├── 同步写入 vs 异步写入 (延迟 vs 一致性)                          │

**主流Feature Store对比：**

| 特性 | Feast | Tecton | Hopsworks | 自研 |
|------|-------|--------|-----------|------|
| 开源 | ✅ | ❌ | ✅ | - |
| 在线存储 | Redis/DynamoDB | 自有 | 自有 | 自定义 |
| 离线存储 | S3/BigQuery | S3 | HDFS/S3 | 自定义 |
| 流处理 | Spark/Flink | Flink | Spark/Flink | 自定义 |
| 延迟 | 10-50ms | <10ms | 10-50ms | 取决于实现 |
| 适用规模 | 中小型 | 大型 | 中大型 | 任意 |
| 运维复杂度 | 低 | 低(SaaS) | 中 | 高 |

        'topic' = 'user-events',
        'properties.bootstrap.servers' = 'kafka:9092',
        'format' = 'json',
        'scan.startup.mode' = 'latest-offset'
    )
""")

t_env.execute_sql("""
    CREATE TABLE user_features (
        user_id STRING,
        feature_name STRING,
        feature_value STRING,
        update_time TIMESTAMP(3),
        PRIMARY KEY (user_id, feature_name) NOT ENFORCED
    ) WITH (
        'connector' = 'redis',
        'host' = 'redis',
        'port' = '6379'
    )
""")

# 实时计算用户行为特征

    INSERT INTO user_features
    SELECT
        user_id,
        feature_name,
        feature_value,
        CURRENT_TIMESTAMP as update_time
    FROM (
        SELECT
            user_id,
            -- 最近1小时的交易次数
            CAST(COUNT(CASE WHEN event_type = 'purchase' 
                  AND event_time > CURRENT_TIMESTAMP - INTERVAL '1' HOUR 
                  THEN 1 END) AS STRING) as feature_value,
            'purchase_count_1h' as feature_name
        FROM user_events
        GROUP BY
            user_id,
            TUMBLE(event_time, INTERVAL '5' MINUTE)
        
        UNION ALL

            user_id,
            -- 最近24小时的总消费金额
            CAST(SUM(CASE WHEN event_type = 'purchase'
                  AND event_time > CURRENT_TIMESTAMP - INTERVAL '24' HOUR

### 4.3 Training-Serving Skew 防护

```python
# 特征一致性保障：训练和推理使用同一套特征定义
from dataclasses import dataclass
from typing import Callable, Any

@dataclass
class FeatureDefinition:
    """特征定义 —— 训练和推理使用同一个定义"""
    name: str
    description: str
    dtype: str
    # 特征计算逻辑（同一个函数用于训练和推理）
    compute_fn: Callable[[dict], Any]
    # 在线/离线存储路径
    online_key: str
    offline_column: str
    # 版本
    version: int = 1

# 特征注册表
FEATURE_REGISTRY = {
    "purchase_count_1h": FeatureDefinition(
        name="purchase_count_1h",
        description="最近1小时的交易次数",
        dtype="int",
        compute_fn=lambda events: sum(
            1 for e in events 
            if e["type"] == "purchase" 
            and e["time"] > now() - timedelta(hours=1)
        ),
        online_key="user:{uid}:purchase_count_1h",
        offline_column="purchase_count_1h",
    ),
    "total_amount_24h": FeatureDefinition(
        name="total_amount_24h",
        description="最近24小时的总消费金额",
        dtype="float",
        compute_fn=lambda events: sum(
            e["amount"] for e in events
            if e["type"] == "purchase"
            and e["time"] > now() - timedelta(hours=24)
        ),
        online_key="user:{uid}:total_amount_24h",
        offline_column="total_amount_24h",
    ),
}

class FeatureService:
    """统一的特征服务 —— 训练和推理使用同一接口"""
    
    def __init__(self, feature_store):
        self.store = feature_store
    
    def get_online_features(self, entity_id: str, feature_names: list[str]) -> dict:
        """在线推理：从Feature Store实时读取"""
        features = {}
        for name in feature_names:
            feat_def = FEATURE_REGISTRY[name]
            value = self.store.get(feat_def.online_key.format(uid=entity_id))
            features[name] = value
        return features
    
    def get_offline_features(self, entity_ids: list[str], feature_names: list[str]) -> list[dict]:
        """离线训练：从历史数据批量读取"""
        features_list = []
        for entity_id in entity_ids:
            features = {}
            for name in feature_names:
                feat_def = FEATURE_REGISTRY[name]
                value = self.store.query_offline(entity_id, feat_def.offline_column)
                features[name] = value
            features_list.append(features)
        return features_list
```

## 六、总结

AI数据管道不是简单的"数据搬运"，而是AI系统的**基础设施层**。一个设计良好的数据管道应该做到：

1. **延迟分级** —— 根据场景选择离线/近线/在线
2. **特征一致性** —— Training和Serving使用同一套特征定义
3. **可演进** —— 新需求上线周期 < 1天
4. **可观测** —— 数据质量、延迟、成本全链路监控
5. **可复用** —— 跨团队、跨模型共享特征

选择合适的架构阶段，不要过度设计。对于大多数团队，**Kappa架构 + Feast** 是当前最务实的选择。随着团队和业务增长，再逐步演进到完整的实时特征平台。

数据管道建设是一个持续的过程，关键是**小步快跑，持续演进**。
